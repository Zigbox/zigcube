# 0.5.2 retro

Zigcube 0.5.2 (release B7, tag `v0.5.2` at 144e41e, 2026-11-17) shipped B4 to B7: job
certificates, signed jobs, tenant placement and the API over mTLS, pinned to Zigbox v0.5.2.
The release PR was [#272](https://github.com/Zigbox/zigcube/pull/272).

## What was off

- **"The reviews' fixes are small, so `check` is enough."** After both release reviews, #272
  took four more fix passes before its CI went green: `zig fmt` walked `zig-pkg/`, a merge left
  `agent_gzipped` set in demo-b3 and demo-b4, a guest step counted upstream files under
  `/root/tls`, and demo-b4 used `bytes.fromhex` on bytes (fine only on Python 3.14) and a job
  name where it needed a run id. Each pass ended `check: PASS`, and none of those failures is
  visible to `check`: only the KVM demo jobs see them. Cost: about eight hours, overnight.
  Change: a fix session on a release branch does not report until the CI demo jobs its change
  can affect have run green on its head.
- **"The soak fits the pinned commit."** The 24-hour fleet soak and moving fix commits did not
  fit together; the owner shortened the soak for this release
  ([decision](../decisions/2026-11-15-0.5.2-soak-shortened.md)). Cost: an owner decision under
  time pressure. Change: none yet; 0.6.0's soak runs once, on a commit that already has the full
  review's fixes (`2026-11-16-0.6.0-first-public-preview.md`).
- **"Releasing by hand is one command."** Zigcube has no release workflow. The command given to
  the owner read the notes from a checkout the owner did not have, and the notes file is a
  release checklist, not notes. Cost: a failed command and a round trip with the owner. Change:
  Zigcube gets Zigbox's release workflow with one approval, as a 0.6.0 slice
  ([decision](../decisions/2026-11-17-zigcube-release-workflow.md)).
- **The self-hosted Mac runner kept dropping.** Mac jobs sat queued or lost the runner, and
  merges went ahead without them, noted in each merge message. Change: none in this repository;
  it is on the owner's list.

- **"CI time stays where the 2026-11-04 speed-up left it."** It did not. On the release commit,
  `ci` took 28 minutes, and two jobs set that: the sim-c1 negative tests (27 minutes) and the
  sim-c1 worlds (21 minutes). Every other job finished in 10 minutes or less, the KVM demos in
  5 to 7. Each fix pass on #272 waited on those two jobs, and so does every pull request that
  touches the core. Change: a CI-speed slice in 0.6.0 shards the negative tests and the worlds
  across matrix jobs, aiming for a 12-minute `ci`, and records the job times before and after.

## What worked

- The two independent release reviewers found different MUSTs (a crash loop on a bad trust
  policy, and a relay cancel under the Zigbox runtime). Keep two.
- Review items that were not MUSTs went to 0.6.0 in writing
  ([decision](../decisions/2026-11-17-0.5.2-known-issues-to-0.6.0.md)) rather than holding the
  release.
