## Goal

When a relayed job connects to its relay, the upstream gets a TLS 1.3 connection whose client
certificate says which run is calling: `spiffe://<cluster>/job/<name>` in the URI SAN, and the
image digest, placement epoch and the job's labels in the identity extension. The cluster CA
issues the certificate. It is valid only for the run's lifetime. A stock TLS server that pins
the cluster CA's certificate accepts it and can read those fields. The workload never holds the
key, and nothing it sends changes the identity.

## Fixed decisions

- **No interim.** Following O2, there is no `Zcube-Identity` header. The input's interim
  paragraph is cut.
- **The key is born in the supervisor and stays in memory.**
  - The job's supervisor makes a fresh Ed25519 key pair for each run (`secure_random.zig`).
  - It never writes the key to disk and never passes it to the container: not in its
    environment, its mounts, or its directory.
  - The key lives as long as the supervisor. An agent restart adopts the supervisor and so keeps
    the key. A supervisor that dies loses the key, and its run ends with it, as in B3.
- **Issuance: the server signs, for the current claim only.**
  - The agent sends the run's public key to the server, as a new agent API request beside the
    job reports, and gets back the leaf certificate.
  - The server issues only for the node that holds the job's current claim and placement epoch.
    It refuses an ended run, a stale epoch, and another node (a new code, below).
  - Until B7, the request is not authenticated beyond that claim check (O4). Record that in
    `docs/mtls.md`'s threat list.
  - The issuance check is core code (`peer_ca.zig` or a sibling). Signing uses `server_ca.zig`'s
    key.
- **The certificate.**
  - `x509`'s `workload` kind accepts the path `/job/<name>`. Today it accepts only
    `/service/<name>`; `x509_identity.spiffe_path` becomes one of two paths.
  - The issuer is the cluster CA. There is no intermediate.
  - `not_before` is the time of issue.
  - `not_after` is the run's start, plus `deadline_ms`, plus `grace_ms`, plus
    `workload_cert_slack_ms = 60_000`. It is never renewed.
  - `job_deadline_ms_max` (24 h) is under `x509_leaf_ttl_ms_max` (7 days). Add a comptime
    assert that this stays true.
  - The certificate carries all of the job's `labels`, nothing more.
- **Labels must fit the certificate.**
  - A job's labels can reach 6 × (32 + 128) bytes, but a certificate holds 256
    (`x509_labels_bytes_max`).
  - So admission refuses a relayed job whose labels exceed that bound, with ZC-E0130 naming
    `labels` and the bound.
  - A job without a relay is unaffected.
- **The upstream is checked too.**
  - Each `relays` entry gains `server_name` (a DNS name) and `server_ca` (a path to a PEM
    Ed25519 anchor).
  - The relay verifies the upstream's leaf with `verify_foreign_server` against that anchor and
    that name.
  - A bad entry is ZC-E0106, as in B3.
  - The pinned TLS client speaks only Ed25519. So Botpike's broker must present an Ed25519 leaf
    that its own anchor signs. The supervisor tells the owner this as a Botpike requirement. It
    is not a gap for this work to fill.
- **The relay's upstream connection becomes `tls_conn.zig` with `client_auth = .required`.**
  - It replaces B3's plain-TCP `connect_upstream` behind the same interface.
  - The copy loop (`relay_pump.zig`) moves application data through the TLS connection.
  - The byte bound and the idle bound count plaintext.
  - Plain TCP stays only for the fake-runtime tests that predate B4, behind a test-only option.
    It is never in a release build's config.
- **Fail closed (Zigcube #228).** A relayed run has no route out except its relay, and it never
  runs without one:
  - **No relay, no workload.** The supervisor opens the relay before it starts the command, as
    in B3. If the relay cannot be opened, or (with the real runtime) the listener cannot be taken,
    the command never runs or is killed before it can send. The ending names the cause (ZC-E0702
    or the open failure), and the run is not retried elsewhere.
  - **Relay gone, workload gone.** The relay lives in the supervisor, so if the relay is gone,
    the run is gone too. If the relay's threads stop while the command is still alive, for example
    because they panic or exit early, the supervisor kills the command. It then ends the run as
    killed and writes the cause to `relay.log`. A run never outlives its relay.
  - There is no "frozen" state. The ending is the freeze.
  - If the relay-stopped cause needs a code of its own, ask first; ZC-E0702 names only the
    listener that could not be taken.
  - Slice 2 tests both directions over the fake runtime, with a test-only fault for each: the
    relay fails to open, and the relay stops mid-run. Each fault has a tooth that skips the
    check, and each tooth must be caught. Slice 4 repeats the second test on the real runtime.
- **Revocation is the ending.**
  - B3 already closes every relayed connection before the ending is reported.
  - B4 bounds that time. A supervisor told to stop must end the run's relayed connections
    within `relay_cancel_ms_max = 2 * relay_poll_ms` (100 ms) of being told.
  - The demo measures the time from `zcube job cancel` to the upstream's read ending, and
    asserts it is under 10 s.
  - Bounds are the supervisor's choices for B4. A slice that wants another value asks first.

## Diagnostics

- **ZC-E0706** is approved: the server refused to issue a workload certificate. Its one line says
  why: not this node's claim, a stale epoch, or the run has ended. The agent records it in the
  relay log, and the run's relay stays closed.
- TLS failures to the upstream reuse the TLS codes, ZC-E0810 to ZC-E0819. ZC-E0814 means the upstream refused
  our certificate. They are recorded per connection, like ZC-E0701.
- Ask before adding any other code.

## Slices

1. **The certificate (core).** No sockets.
   - The `/job/` SPIFFE path.
   - The issuance rule (claim, epoch, lifetime, labels), as a pure function over the store's job
     and claim.
   - `not_after` arithmetic, with the comptime asserts.
   - Tests:
     - `x509_near_miss` rows for `/job/`;
     - a teeth test for each issuance check (wrong node, stale epoch, ended run, lifetime one
       millisecond long);
     - the x509 fuzzer extended to `/job/` names.
   - Admission's label bound (ZC-E0130).
2. **Issuance over the API and the TLS relay (fake runtime).**
   - The supervisor's key and the agent request.
   - ZC-E0706.
   - `relays.<name>.server_name` and `server_ca`.
   - `tls_conn` in the relay.
   - Tests against an in-process TLS test upstream that pins the CA:
     - it reads the job, digest, epoch and labels from the presented certificate;
     - each of these is refused: another job's certificate, an expired one, one from another CA,
       and no certificate.
   - `agent-smoke`'s relayed job goes through TLS.
   - The two fail-closed tests (above), each with its tooth.
   - A relayed run's spec asks for loopback-only networking, and the adapter refuses more (the
     fence comparison, row 2).
   - Fuzz the relay's copy loop over TLS records with short reads and writes.
   - Update `docs/api.md`, `docs/keys.md`, `docs/agent.md` and `docs/mtls.md`.
3. **Simulation** (after 1). The cluster simulation's relayed jobs get certificates. A check
   holds at every revision:
   - a certificate is issued only to the node holding the run's claim and epoch;
   - none outlives `start + deadline + grace + slack`;
   - no relayed connection is open after its run's ending is reported.

   Add a tooth that issues for a stale epoch. `sim-c1` runs it, and the fleet picks it up.
4. **Stock servers and the real runtime.**
   - `mtls-interop` gains a workload-certificate row. `openssl s_server -verify_return_error`
     and the JDK 21 server both pin the cluster CA, accept the relay, and print the SPIFFE ID
     and the extension. Both servers refuse each of the four bad cases.
   - Then `demo-b4`, on B3's VM rig with `--runtime zigbox`:
     - the workload connects to `ZCUBE_RELAY`, and the stock upstream logs the job's identity;
     - inside the container, a search of `/proc/self/mountinfo`'s mounts and of the
       environment finds no key bytes;
     - a cancel ends the upstream's connection within the bound;
     - when the relay is stopped mid-run, the workload is killed (fail closed);
     - the rows that `docs/decisions/2026-11-12-openshell-fence-comparison.md` adds: the
       workload cannot see, signal, trace or read its supervisor; IPv6 and UDP attempts fail.

   `demo-b4` is like `demo-b3`: it skips without `ZCUBE_REAL_HOST=1`, and CI runs it.

## Non-goals

- Server-side mTLS or API authentication (B7).
- Signed images (B5).
- Placement by tenant (B6).
- Certificate renewal.
- A revocation list or OCSP.
- An intermediate CA.
- Non-Ed25519 keys on either side.
- Identity for services (jobs only).
- Any header-based identity.
- More than one relay per job.
- Botpike's broker itself.
