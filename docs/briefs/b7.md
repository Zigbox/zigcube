## Goal

`zcube-server` serves its API over TLS 1.3 and requires a client certificate on every
connection, from the cluster CA. What a caller may do depends on who the certificate names:

- An agent may use the agent API for its own node only.
- A client with the `jobs` scope may create, read, cancel and watch jobs, and nothing else.
- A client with the `admin` scope may do everything.

Botpike's app gets a `jobs` certificate.

## Fixed decisions

- **The in-house scope widens to a TLS 1.3 server.**
  - The scope is still narrow: Ed25519 only, x25519 only, AES-128-GCM only, client
    authentication always required, and only certificates of this cluster's CA.
  - This is the decision `2026-11-04-in-house-tls-review-before-c6.md` asks for. B7's first
    slice records it in a decision file. The external review before C6 then covers the server
    too.
- **Two new certificate kinds.** Both are added to the `cluster` profile, with exact bytes like
  the others:
  - `node`: clientAuth, with `spiffe://<cluster>/node/<name>`. It is issued at join, beside the
    peer credential, and renewed in the same way.
  - `client`: clientAuth, with `spiffe://<cluster>/client/<name>`. It is issued by
    `zcube-server ca issue-client <name> --scope jobs|admin` on the server host, which writes a
    key and a certificate with mode 0600.
  - The scope is a field of the identity extension (its `version` becomes 2), so the server
    needs no table of clients.
  - Revocation reuses the server's `revoked` file (by name), which is read at start.
- **The server certificate.** It is of kind `server`, with the DNS name from
  `--tls-name NAME`. It is issued by the CA at start and renewed before expiry, and clients pin
  the CA.
- **The listeners.**
  - `--listen` serves TLS whenever the CA exists.
  - Plain HTTP stays only behind `--insecure-listen 127.0.0.1:PORT`, for loopback only: the
    flag refuses any other address. `zcube local` and the tests use it.
  - **Cut from the input:** there is no TLS front and no bearer key (O4).
- **Clients.**
  - `zcube`, `zcube-agent` and the console module's server mode gain `--ca`, `--cert` and
    `--key`, or a ZON config with the same keys.
  - The agent uses its `node` certificate.
  - The console in a browser cannot present a client certificate without browser setup, so it
    stays on `--insecure-listen` or behind the operator's own proxy. `docs/console.md` says so.
- **Scopes are checked in core code**, in the API handlers. The handler takes the caller's
  identity (kind, name, scope) as an argument, never a header. Its result is a refusal or a
  call. A refusal is `403` with ZC-E0822.
- **Bounds.** The handshake deadline and the record limits are the client's constants. Raise
  `http_connections_max` only if you ask first.

## Diagnostics

`ZC-E0822` is approved: the caller's certificate does not allow this request. Its one line
names the caller and the scope it would need.

The server's handshake failures reuse the TLS codes, `ZC-E0810` to `ZC-E0820`, logged on the
server side. A refusal of a client certificate is ZC-E0814 at the client.

Ask before adding any other code.

## Slices

1. **The TLS 1.3 server, with no HTTP.**
   - The state machine: ClientHello, the server's flight with a CertificateRequest, the
     client's Certificate, CertificateVerify and Finished, then the application data.
   - It shares the schedule and the wire code with the client.
   - It requires a client certificate and verifies it against the CA.
   - KeyUpdate in both directions.
   - Tests:
     - client against server in the same process;
     - a near-miss table for the client's flight;
     - a teeth test for every check;
     - a fuzzer, with its teeth, that drives the server with damaged client flights.
   - Record the decision that widens the scope.
2. **The `node` and `client` certificate kinds, the scope field, and `ca issue-client`.**
   - Near-miss rows for both kinds.
   - The x509 fuzzer covers the new kinds.
   - Agents get the `node` certificate at join and renew it.
3. **The API over TLS.**
   - `--listen` with TLS and `--insecure-listen` for loopback.
   - The caller's identity reaches the handlers, and the scope checks with ZC-E0822.
   - The `--ca`, `--cert` and `--key` options in the clients.
   - Tests: every endpoint called by each of an agent, `jobs` and `admin`, both allowed and
     refused (a table test).
   - An agent may write only under its own node's keys.
   - `agent-smoke`, `local-smoke`, `demo-c0` and `demo-c1` keep passing over the new
     listeners.
4. **Stock clients and the demo.**

     with a `client` certificate, against `zcube-server`. Each is accepted, and each is refused
     when it presents no certificate, an expired one, or one from another CA.
   - `demo-b7` covers these: a `jobs` client creates and cancels a job; the same client is
     refused `POST /v1/services`; a client with no certificate is refused at the handshake;
     an agent of node1 is refused a write under node2.
   - It runs over the fake runtime and needs no KVM.

## Non-goals

These are out of scope for B7:

- TLS 1.2.
- Any key type other than Ed25519.
- RSA or ECDSA certificates from other CAs.
- OCSP or a revocation list beyond the server's `revoked` file.
- Browser client certificates.
- Moving the peer protocol (the Noise handshake) to TLS.
- OIDC or any login.
- Per-job ownership ("a client sees only its own jobs"). That is a scope, not B7.
- The external review, which is C6's prerequisite.
