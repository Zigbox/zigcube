### 1. `zcube get nodes` and `get replicas -o wide`

All reads are `GET /v1/list` and `/v1/leases`, joined in the CLI like `get replicas` (the keys are the contract; there is no summary endpoint).

**Reads:** `/nodes/` (capacity, `mod_revision` = tenure, `lease`), `/node-status/` (`state`, `tenure`), `/allocations/` (`allocated`, `count`), `GET /v1/leases` (`ttl_ms`, `remaining_ms`), `GET /v1/status` (`time_ms`). The rows are the union of the node names under `/nodes/` and `/node-status/`, in name order, so a node whose registration is gone but whose status remains still shows.

```
$ zcube get nodes
NODE   STATUS  TENURE  LEASE      CAPACITY        ALLOCATED      LAST-HEARD
node1  ready   14      7.9s/10s   4000m / 8.0Gi   2000m / 1.0Gi  2s ago
node2  ready   17      8.4s/10s   4000m / 8.0Gi   2000m / 1.0Gi  1s ago
node3  ready   22      9.1s/10s   4000m / 8.0Gi   0m / 0B        0s ago
```

- `STATUS`: `state` of `/node-status/<node>`, or `-` when there is none yet. `TENURE`: the `/nodes/<node>` `mod_revision`, or `-` with no registration. If `/node-status` names an older tenure than `/nodes`, the status is shown with `*` (`ready*`: the judgement is for an earlier tenure; the scheduler does not count it, I7). `LEASE`: `remaining/ttl` from `/v1/leases` for the lease the key is on, `-` when none. `CAPACITY` is `cpu / memory` as declared; `ALLOCATED` is `/allocations/<node>` (`0m / 0B` when the key is absent). `LAST-HEARD`: `ttl_ms - remaining_ms` of the lease, against the server's clock: a keepalive creates no revision, so the lease is the only record of the last contact (`api.md`, `GET /v1/leases`). `-` when the node has no lease.
- `-o wide` adds `ADDRESS`, `AGENT`, `REPLICAS` (the `count` of `/allocations`) and `LEASE-ID`.
- `-o json`: `{"kind":"nodes","items":[{"name","status","status_tenure","tenure","lease":{"id","ttl_ms","remaining_ms"}|null,"capacity":{"cpu_millis","memory_bytes"}|null,"allocated":{"cpu_millis","memory_bytes"},"count","last_heard_ms_ago"|null,"address","agent_version"}]}`.
- No nodes: `no nodes`.
- `get nodes <name>` names one node; an unknown name is `ZC-E0101`.

**`get replicas -o wide`** already has `GEN`, `IMAGE` and `DETAIL`; C1 adds the placement: `CPU` and `MEMORY` (the `requests` of the replica's `/assigned` record, `-` while unassigned) before `IMAGE`, and `ASSIGNED` is not a column (the node is). `-o json` rows gain `requests` (`{"cpu_millis","memory_bytes"}` or null) and `tenure`/`assignment` revisions are not added (they are not what an operator reads). Additive.

Mechanical: none. Goldens: `get nodes` text, wide, JSON from a real run; the unit tests of the join over canned JSON.

### 2. `zcube why node <name>`

`why node` exists (`why.zig`, `node_state`: "registered on lease N"). It gains the facts an operator needs after a failover and the answer to HANDOFF's step 4:

- the state line: `node node3: ready (tenure 22), lease 9 with 0 replicas assigned, 0m of 4000m CPU and 0B of 8.0Gi memory in use` (a node with no `/node-status` says `registered, not yet judged`; one with no registration says `not registered` and, if a status remains, `last judged <state>`).
- when the node is `ready` and holds fewer replicas than another node, **one extra step** `type: "note"`: `replicas that are already running on other nodes are not moved back: the scheduler places a replica when it is created or its node is lost, and does not rebalance`. It is a statement of C1's rule (`c1.md` non-goals), not a reading of the store, and the step's type says so.
- the chain from the node's newest decision (`mark_ready`, later `mark_lost` with its `ttl` and last-heard time) as today.

`note` is a new step type, additive; the console renders an unknown type as plain text so an older console does not break.

### 3. `completeness` in `why`

`GET /v1/why` and `-o json` gain, beside `steps`:

```json
"completeness": {"verdict": "complete"}
"completeness": {"verdict": "truncated", "at": "<id of the last decision found, or the cited key>", "reason": "retention|subject_deleted|compacted"}
```

`authority.md` §5 names the reasons and says the chain stops "with `at` (the last step that was found) and `reason`". The key is `verdict` so it cannot be read as the `state` line.

- **`retention`**: a decision the chain cites has been removed (today's `gone` step), while the subject still exists.
- **`subject_deleted`**: the same, and the subject no longer exists (`state.exists` false): its 24 hours have run out.
- **`compacted`**: the chain ends at an `observed` or `desired` terminal whose cited revision is below the compaction point, and the decision embeds neither `cause_evidence` nor `cause_diagnostic`. Today `why` then reads the key *now* and shows that as the justification, which `authority.md` forbids. It now ends in a `gone` step (`the record <key> as it was at revision N is no longer kept`), and never shows the current value as the reason. A decision with `cause_evidence` is `complete` and its terminal step's text is the evidence as written (`<key> at revision N: <evidence>`); a diagnostic copy is rendered as today.
- Everything else (a terminal `observed`, `desired`, `lease_expired`, `resync` whose record was read at its revision) is `complete`.
- Text output: unchanged for a complete chain; a truncated chain ends with the `gone` step's one line, now naming the reason. `--verbose` adds a final line `completeness: complete` or `completeness: truncated (<reason>) at <at>`.
- Docs and console: `docs/api.md` (the shape, the three reasons, the `note` step and the `gone` step's `reason` member, which is added to the step too), `docs/cli.md`, `docs/console.md`, the console's Why view (a "complete" / "truncated: <reason>" pill under the headline) and `web/mock/transport.js` (the mock computes it the same way).
- **Not in this slice:** the `sim-c1` acceptance test over every decision (slice 5), and writing `cause_evidence` from the replica controller (it writes none today; only the scheduler and node controller do). Until it does, an `observed` terminal past compaction ends `truncated`/`compacted` for replica-controller decisions. That is correct and is reported as a gap.

### 4. `zig build bench-watch`

`c1.md` row "Watch fan-out", as written: 50 agents and 2,000 assignments in one process over SQLite; one new assignment wakes exactly one agent's poll; p99 time from commit to the agent's response under 250 ms. Not in `check`. A miss is reported, not tuned around.

**The agent endpoint today** wakes on `/replicas/` *or* `/assigned/` for any node (`agent_api.zig`, "the endpoint may wake on either prefix", slice 3 brief). So the benchmark's first run is expected to show every poll waking on an assignment for another node. This sub-slice therefore also changes the agent's watch to `/assigned/<node>/` alone (`authority.md` §2): an agent reconciles by level and lists `/assigned/<node>/` and joins each `/replicas` record, so a change to a replica's *spec* (a new generation) reaches an agent only through the replica controller replacing the replica (a new id, a new assignment), never through the spec key changing in place. **If that premise is wrong in the code, stop and report instead of widening the prefix.**

Output: one line per run, `bench-watch: agents 50 assignments 2000 woken 1 of 50 p50 .. ms p99 .. ms limit 250 ms PASS|MISS`; the exit code is non-zero on a miss or on more than one agent woken.

### 5. `demo/up.sh` and `demo/down.sh`

Shell scripts, with the written reason STYLE.md asks for at the top of each: the demo environment is for a person at a prompt, and `demo-c1` drives the same processes from Zig. `demo/up.sh [sqlite|postgres]` builds if needed, starts `zcube-server` and three `zcube-agent`s (`node1..3`, separate state dirs under `demo/run/`, capacity declared per agent), waits until `zcube get nodes` shows three, and prints how to use it. `demo/down.sh` kills the agents **and** their supervisors' containers, the server, and removes `demo/run/` (and the throwaway Postgres only if `up.sh` started it). Both are idempotent. "Power off" for the demo is `demo/kill-node.sh <node>` (`kill -9` of the agent and its containers), so the failover is one command for a person. `demo/` is ignored by `tidy` and by the docs-only CI rule only as far as its own files are `.sh`/`.md`: a changed script runs CI.

Tested by running them in this session from nothing: up, `get nodes`, apply, kill a node, down, and a second `down` (idempotent).

### 6. `zcube local up` and `zcube local down` (c1.md, "Local mode")

One command starts `zcube-server` on SQLite and one `zcube-agent` with `FakeRuntime` on the same machine, no database to install, no administrator step. `local down` stops both and **keeps the state**.

- State lives in `$XDG_STATE_HOME/zcube/local/` (else `$HOME/.local/state/zcube/local/`): `zcube.db`, the agent's state dir, `server.pid`, `agent.pid`, logs. `ZCUBE_LOCAL_DIR` overrides it (tests).
- `local up` starts the two processes detached (the `zcube-server` and `zcube-agent` that sit beside the `zcube` executable; `ZC-E0122` if they are not there), waits until `GET /v1/status` answers and `get nodes` shows the node, then prints the address and `zcube apply hello.zon` as the next step. Already running: it says so and starts nothing (`zcube local up` twice is not an error). Port: `127.0.0.1:7070`, or the next free one it prints; the CLI reads `$ZCUBE_SERVER`, so it prints the `export` line.
- `local down` sends SIGTERM to both pids, waits, then SIGKILL, and leaves the agent's containers to the next `local up` to adopt (the agent's restart rule). Not running: it says so, exit 0.
- New codes (registered, with explanation, goldens and error pages): `ZC-E0122` (environment) *the local server or agent binary can't be found or started*; `ZC-E0123` (environment) *the local server did not come up* (it names the log file). Raised only by `zcube local`.
- `zcube` is a client of the HTTP API and "opens no store and starts no process" (`docs/cli.md`). `local` is the one exception, so it lives in its own file (`cli_local.zig`), is not in the core, and `docs/cli.md` says so.

Tested: a unit test over the pure parts (paths, pid file parsing, the free-port choice); and run for real in this session: up, apply, `get replicas`, down, up again (the replicas adopted, not duplicated), down.
