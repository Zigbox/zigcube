## Goal

Make B1's jobs hold up under what Botpike will do to them, and leave the tree clean enough that
the fleet can run for 24 hours with no open issue. Concretely:

1. Every `sim-fleet` issue open against B1 is root-caused, fixed or shown to be a simulator bug,
   and closed with its cause.
2. No single bad record, oversized list or skewed clock can stop the scheduler or a controller
   for the whole cluster.
3. The job API answers a client's retries and watches the way docs/api.md says it does.
4. The job checks (J1 to J8) are strong enough that the fixes above are guarded by teeth.
5. The known CI flakes are root-caused or have a recorded cause, so the B2 release run is not
   decided by retries.

B2 adds no feature. Every user-visible change it makes is a fix to documented behaviour, or is
listed under "Owner decisions".

## Non-goals

  placement by tenant and API identity
  ([botpike-first-customer.md](botpike-first-customer.md)). They are new features, and B2 is
  hardening. See "Owner decisions" 1 for the name collision.
- **The Jepsen battery.** It is a C5 prerequisite
  ([../decisions/2026-11-03-jepsen-before-c5.md](../decisions/2026-11-03-jepsen-before-c5.md)), and
  B2's gate clause for it is vacuous.
- **Job logs.** They were cut from B1 (owner answer 4) and still need a Zigbox layout statement.
- **New bounds and defaults.** The exception is a change listed under "Owner decisions" and
  answered there. The `jobs_max`, window and retention constants stay as B1 set them unless the
  owner says otherwise.
- **Performance work beyond a measurement.** RB-S14 (two to four point reads per retained job per
  pass) gets a number in slice 2. It is fixed only if that number misses a bound, and none is set
  today.
- **Zigbox's supervisor.** `zigbox_supervisor.zig:525` delegates to `zigbox.wait`. Whether
  Zigbox's own wait has #113's pid-reuse window was not read. If it does, slice 6 reports it to
  Zigbox and does not patch around it.
- **The console.** No console item is open from B1's reviews.

## Owner decisions

These are not decided here. Each changes something user-visible or the plan itself.

1. **The name "B2".** [botpike-first-customer.md](botpike-first-customer.md) calls the relay "B2"
   (its section heading, and step 2 of its proposed order), and identity, signed images, placement
   and API identity are B3 to B6. With B2 the hardening release, does the relay become B3 and the
   rest shift by one? Or does hardening take another name, such as B1.1?
2. **Retry and idempotency semantics** (RB-S4, RB-S9). There are two choices to make:
   - Should a late `POST` retry (after `submit_by_ms`) for a job that still exists answer with
     the job (200) rather than 410 ZC-E0134?
   - Should idempotency treat `env` and `labels` as sets, so that the same pairs in another order
     match?

   Both change what a client sees. Botpike retries POSTs.
3. **Cancel during a partition** (RA-S1, #142, #143). Cancel takes effect only through a
   successful agent pass, so during a partition it waits until the node fences (J6's
   `stop_bound_ms` includes the fence term). Is that the stated bound, or should cancel have a
