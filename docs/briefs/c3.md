## Goal

SPEC Part II, "C3 · Rollout": a changed service is replaced a few replicas at a time, a replica
counts only when its health check passes, a rollout that goes wrong stops and returns to what ran
before, and the operator can pause, resume and roll back. This brief also folds in the three
inputs the owner set for C3 on 2026-11-04: the harder simulation fleet
(`docs/briefs/c3-sim-fleet.md`, which comes **first**), deb/rpm packages
(`c3-linux-packages.md`) and a signed macOS `zcube` (`c3-macos-cli.md`).

The demo (SPEC, in substance; the Zigbox VMs are the machines):

1. Deploy `app v1`, three replicas with a health check.
2. Apply `v2` with `max_surge 1`, `max_unavailable 0`. The service never has fewer than three
   ready replicas while it rolls; at the end all three run `v2`.
3. Apply `v3`, whose health check never passes. The rollout stops on its first new replica, rolls
   back on its own, and the three replicas end on **exactly** `v2`'s digest.
4. `zcube history` lists the generations with who applied each; `zcube rollback` returns to an
   earlier one; `zcube rollout pause` holds a rollout and `resume` continues it.

Acceptance (SPEC, verbatim): "No request errors during a healthy rollout at the demo load" and
"Rollback restores the previous digest exactly, never 'latest'". The SPEC's demo also runs a load
generator. With no network into containers (O2, recommended), C3 proves the first criterion as
"a rollout never takes a service below its minimum ready replicas, at any store revision", and
leaves request errors seen by a client to C4. That reading is the owner's to confirm.

## Non-goals

- **Real traffic and "zero errors" as a client sees them.** Containers run `--net none` today, and
  there are no endpoints. C3 proves availability as ready replicas at every store revision (O2).
  Traffic is C4 (Mesh).
- **Canary, blue/green, weighted traffic.** Only the rolling and recreate strategies.
- **TCP and HTTP health checks.** They need a network path into the container (O6).
- **Mixed versions** (agents one release behind the server). Parked by the owner. The release
  notes say "upgrade the server, then the agents".
- **Machines for the fleet** until items 3 to 5 of the fleet list are measured. PR-head runs, also
  parked.
- **A signed macOS `zcube-server` or `zcube-agent`; Windows; a hosted apt repository** (the
  owner signs and publishes; CI never does).

## What exists, and what is missing (gap analysis)

### In Zigcube

- **No health, no readiness.** `Runtime.Spec` and `Status` (`src/runtime.zig`: `starting`,
  `running`, `stopped`) have no exec and no health. `/observed` (keys.md, v1) is written on a
  status change only and has no health field. "Running" is the only signal.
- **The replica controller replaces stale replicas in one batch.** `replica_controller.zig` sees
  a replica whose `generation` is behind and writes `replace_replica` for all of them, with no
  surge, no unavailable limit and no wait for the new replica to be useful. A change of a
  three-replica service takes all three down together. This is the code C3 changes.
- **No history.** keys.md says the previous generation's spec is gone once the service record is
  overwritten; "who applied" survives only as the latest record's `applied_by` and the `apply`
  decisions' `change` text, which retention compacts. Rollback needs the old spec and `source`
  (a digest-pinned reference, so "exact digest" is a field copy), so a `/history` key is new.
- **No rollout state.** Nothing records "this service is mid-rollout from generation 6 to 7, paused
  or not, with this deadline". A restart of the server must not lose it, so it is a key.
- **Writer rules.** `/services` has one writer role, `api` (`src/writers.zig`). An automatic
  rollback is a new service generation, so it must go through the API's write path (O3).
- **`hold_failed_replica`.** A replica whose start fails with a user-blame cause is held
  (keys.md). During a rollout that is the sharpest failure signal and the rollout must read it.
- **Scheduler.** Placement is fit, spread, locality, least allocated, name. A surge replica needs
  headroom, and allocations count a replica until it is observed stopped. A full cluster stalls a
  `max_unavailable 0` rollout; that must end in a diagnostic and the progress deadline (below),
  not a hang.
- **Simulators.** `sim-cluster`'s `SimRuntime` has no health. `sim-c1` checks I1a to I7
  (authority.md) and has teeth tests. The fleet runs `sim-cluster`, `--c1` and `sim-swarm`.

### In Zigbox (pinned ba3c444, checked against `main` fd21d49)

- **`exec` exists** (`src/zigbox.zig`, `runtime/exec.zig`, M6b): `exec_start`, `exec_wait`,
  `exec_signal`; `ExecSpec` with `terminal = false` gives the caller's streams; `ExecExit.code` is
  the command's exit code. Constraints from its doc comment: an `ExecHandle` is about 600 KiB; the
  thread that starts a command must be the process's only thread at that moment and must be the
  one that waits; `exec_signal` may be called from another thread. **So a probe is a worker
  process, like C2's fetch worker, and a timeout is a signal from a timer thread started after
  `exec_start`.** `Options.keep_history = false` is needed, or every probe adds an entry to the
  container's exec history.
- **No health API of its own.** Zigbox has none; the check is Zigcube's.
- **Networking is `none` by default** (M5: `Network {none, host, user}`, `Publish` via pasta).
  Zigcube's `ZigboxRuntime` passes none of it, so containers are `--net none`. No host-side probe
  can reach a container.
- **No package writer in the module.** `docs/briefs/linux-packages.md` is an M8 input, not built.
- **Zigbox's macOS release path** is a brief (`M4b-mac.md`); I did not check how much is built.
- **Gap, not checked:** whether the supervisor's stop path gives a grace period (SIGTERM, wait,
  SIGKILL). `Runtime.signal` plus `stop_begin` suffice to build one in the agent if not.

## Design

### Keys and state added

Each key gets its keys.md section, versions, writer and retention **before** code (slice 5).

- **`/services/<name>` v4**: adds `health` (`command` argv, `interval_ms`, `timeout_ms`,
  `start_period_ms`, `failure_threshold`, `success_threshold`) and `rollout` (`strategy`
  rolling|recreate, `max_surge`, `max_unavailable`, `min_ready_ms`, `ready_timeout_ms`,
  `progress_deadline_ms`, `grace_ms`, `on_failure` rollback|pause). Replicas v4 carry `health`,
  since the agent runs the check. v3 records read as "no health, default rollout".
- **`/history/<service>/<generation>` v1** (writer `api`): the applied spec and `source` as the
  service record held them, `applied_by`, `request_id`, `applied_at`, `reason`
  (apply|rollback|auto_rollback, with `restores` = the generation copied). Immutable. At most
  `history_generations_max` (16) per service; the oldest is deleted by the apply that makes the
  17th. Deleted with the service.
- **`/rollouts/<service>` v1** (writer `rollout_controller`): `from`, `to` (generations), `phase`
  (progressing, paused, rolling_back, complete, failed), `started_at`, `deadline_at`, `ready_new`,
  `retired_old`, `budget` (how many old replicas the replica controller may retire now, how many
  new it may start), `cause_decision`. One per service; deleted a retention period after
  `complete`.
- **`/observed/<node>/<replica>` v2** (writer: the agent): adds `health`
  (unknown|healthy|unhealthy), `health_failures`, `last_probe_exit`. Still written on change only,
  so the controller needs its own timer for `min_ready_ms` (the rollout record's `deadline_at` and
  `next_at`; the C1 controllers already run on a `Clock`).
- **Decisions** get new actions (`rollout_start`, `rollout_step`, `rollout_pause`,
  `rollout_fail`, `rollback`) with causes, so `zcube why service <name>` shows "rolled back to
  generation 6 because replica app-31 stayed unhealthy for 40 s (ZC-W0306)".

### Controller design

A pure function, `rollout_plan(policy, desired, replicas, ready, phase, now)`, returns the budget:

```
ready_min   = desired - max_unavailable
live_max    = desired + max_surge
may_start   = min(live_max - live, desired - new_live)         (new replicas)
may_retire  = max(0, ready_now - ready_min)  - already stopping (old replicas, ready first)
```

The rollout controller writes only the plan into `/rollouts` (and decisions). The **replica
controller stays the only writer of `/replicas`** and obeys the budget: it starts a new replica
only within `may_start` and retires an old one only within `may_retire`. A stale replica that is
not ready costs nothing to retire. A replica that fails on its own (a crash, a lost node) is
replaced under the same rules as today and never waits for the budget. Level-triggered, no
recursion, no per-pass allocation beyond the arena: every loop is bounded by `replicas_max`.

Failure ends in `failed` when any of these holds, each with a coded decision: a new replica is
not ready within `ready_timeout_ms`; a new replica is held (`hold_failed_replica`) or restarts more
than `rollout_restarts_max`; the whole rollout passes `progress_deadline_ms`; surge cannot be
placed. `on_failure rollback` (the default, as the demo's step 3 needs) calls the API's rollback
handler with `reason auto_rollback` (O3); `pause` leaves the rollout `paused` and says so.
A user `pause` freezes the budget at zero for the rollout's own work; `resume` restores it and
extends `deadline_at` by the paused time. A newer apply during a rollout restarts it from the
current mix of replicas (the new target replaces the old one). An automatic rollback is a CAS on
the service record's revision, so it never lands over a newer user apply (check R8).

Drain: a retired replica is stopped with `grace_ms`: SIGTERM through `Runtime.signal`, wait,
then kill. It counts as live until observed stopped, so the surge bound holds.

### Probing on the agent

A `zcube-agent probe` worker process (the single-threaded exec owner, as C2's fetch worker) runs
one check, `exec_start` then `exec_wait`, with a timer thread sending `exec_signal` at
`timeout_ms`. The agent schedules probes per replica at `interval_ms`, at most
`probes_concurrent_max` at once, and writes `/observed` v2 when `health` changes. A start period
excludes early failures. The `Runtime` gains a non-blocking pair, `probe_begin` and `probe_poll`
(the `stop_begin` precedent, P2), so the core still has no thread or blocking call. `FakeRuntime`
and `SimRuntime` script outcomes (a file `<state-dir>/faults/<replica id>` with `unhealthy`, as
`oom` and `lost` do today).

### Simulation: checks and teeth

A new `sim-c3` family on the cluster simulator (`--c3`, as `--c1` is), with scripted health and
two new fault profiles in the fleet's list: `bad_release` (the target generation never becomes
healthy) and `flaky_health` (probes flap). Checks, at every revision unless noted:

| Check | Statement |
|---|---|
| R1 min available | Every retirement by a rollout leaves `ready >= desired - max_unavailable` on the controller's view at the revision before it. (Faults such as a lost node can lower `ready` by themselves; the check is that the rollout never causes the drop.) |
| R2 surge bound | Live replicas of a service (until observed stopped) are at most `desired + max_surge`, in every state the rollout runs in. |
| R3 only applied versions | Every replica's `(generation, source)` equals a `/history` record or the service record. No replica runs a version that was never applied. |
| R4 pause holds | While `/rollouts.phase = paused`, the rollout starts and retires nothing (failure replacement of same-generation replicas still happens). |
| R5 rollback exactness | When a rollback completes, every live replica's spec and `source` equal `/history[restores]` byte for byte; after a rollback of generation g the digest is the one g held. |
| R6 history | `/history/<g>` never changes; `generation` strictly increases; a rollback writes a new generation. |
| R7 progress (liveness, when `--liveness`) | Once faults heal, a rollout reaches `complete` or `failed`-then-rolled-back within `progress_deadline_ms` plus the heal time. |
| R8 user wins | An auto-rollback never replaces a newer user apply. |

Teeth (`sim-c3-teeth-budget|pause|rollback|history|race`) each switch on one test-only fault and
must fail the matching check. The fleet runs `sim-c3` as a fourth kind (`--kind sim-c3`).

### Diagnostics

Codes to reserve in `src/diag/codes.zig` (all with goldens; the registry's current highest are
E0124, W0119, E0303, E0515, W0501): **01xx** E0125 invalid `health`, E0126 invalid `rollout`
policy, E0127 nothing to roll back to, E0128 rollback target not in history (compacted), E0129 no
rollout to pause or resume; **03xx** E0304 rollout failed (a replica did not become ready), E0305
rollout stalled (surge cannot be placed), E0306 `progress_deadline_ms` passed, W0304 rollout paused
by `on_failure`, W0305 rolled back automatically (the summary names the failing replica and the
generation restored); **05xx** E0516 the probe could not run (exec refused, with the Zigbox code
as the cause), W0502 probe timed out. Blame: E0125 to E0129 user; E0304 and E0306 user (the new
version is at fault); E0305 environment; E0516 environment, or internal if exec's own contract
broke. Numbers are fixed in slice 5; the registry decides collisions.

## How demo-c3 runs

- **Machines.** The same three QEMU guests as demo-c2 (`zigbox_vm.Session`), `zcube-server` on the
  host with SQLite, each guest running `zcube-agent --runtime zigbox`. **Real Zigbox, not
  `FakeRuntime`:** the only new thing C3 asks of Zigbox is `exec`, and a demo that fakes it proves
  nothing the simulations did not. The rollout logic itself is proven by `sim-c3`; the demo proves
  that a real probe, a real stop and a real pull behave as the simulation assumed.
- **Images.** Three public, digest-pinned Alpine tags with different digests stand for `v1`,
  `v2`, `v3`; the app is a `sh -c` that creates `/tmp/ready` after a delay (and, for `v3`, never).
  The check is `test -f /tmp/ready`. The tags and digests are fixed in slice 12 and recorded.
- **Witness.** The driver follows the store's watch from before step 1 and asserts R1, R2, R3 and
  R5 at **every revision**, not by sampling; this is what "zero errors" means in C3 (O2).
- **Asserted:** each step above; `zcube rollout status` text; the exact digests at every replica
  after step 3; `zcube why` names the failing replica; refusals asserted by code and summary
  (ZC-E0125, E0126, E0127, E0128, E0129); an apply during a rollback wins; the server restarted
  mid-rollout resumes it; the agent restarted mid-rollout keeps its containers.
- **Not asserted (cuts, recorded in `docs/demos/c3.md`):** traffic; a node lost mid-rollout is the
  simulation's, not the demo's; the packages and the macOS build have their own checks.
- About 8 to 10 minutes, KVM job, 40-minute timeout, as demo-c2.

   C4 (Mesh). *Recommended: yes, and say so in the README.* The alternative is plumbing Zigbox's
   `Publish` through `ZigboxRuntime` first, which is C4's work and would put C3 behind it.
3. **May the rollout controller roll back by calling the API's rollback handler?** That makes the
   controller cause a write to `/services`, which only the `api` role owns. The handler does the
   write (so authority.md I4 still holds by role), marks it `applied_by "rollout-controller"`, and
   it is a CAS on the service's revision. *Recommended: yes.* The alternative, a "target
   generation" in `/rollouts` that the replica controller prefers over the service record, leaves
   `zcube get service` showing a spec that is not the one running.
4. **Defaults when a service has no `rollout` block.** *Recommended:* `rolling`, `max_surge 1`,
   `max_unavailable 0`, `min_ready_ms 5000`, `ready_timeout_ms 120000`, `progress_deadline_ms
   600000`, `grace_ms 10000`, `on_failure rollback`, for every service, including those with no
   health check (ready after `min_ready_ms` of running). This changes what C0 to C2 services do on
   a change (one at a time, not all at once); slice 7 re-runs those demos and reports any
   assertion it had to change. The alternative is to keep the old batch replace for services
   without `health`, and carry two behaviours.
5. **History retention.** *Recommended:* 16 generations per service, deleted with the service, the
   oldest deleted by the apply that overflows it. A rollback to a compacted generation is ZC-E0128.
6. **Health check kinds.** *Recommended:* command only in C3. TCP and HTTP checks wait for a
   network path into the container (C4).
7. **How is a version named?** The spec says v1, v2, v3; Zigcube numbers generations and records
   image tags. *Recommended:* users address generations (`rollback --to 7`), `zcube history` shows
   generation, image reference, digest, who and when, and the demo's `v1`, `v2`, `v3` are image
   tags.
8. **Where does a rollout's cause live after retention compacts decisions?** *Recommended:* in the
   `/history` record's `reason` and `restores` and in the last rollout record; decisions are for
   the live chain, as today. `zcube why` after compaction says so.
9. **Zigbox's package writer.** *Recommended:* ask Zigbox to export it from the pinned module
   (ZB-1) and have slice 13 wait; do not copy it. If it is not in the pin when slices 5 to 12 are
   done, cut the deb/rpm packages to the release after C3 and say so in the C3 demo document. The
   three unknowns in `c3-linux-packages.md` get these defaults: `zcube-server` built per
   distribution (Ubuntu 24.04 and one RHEL 9 compatible first), and the `zigbox` package keeps
   Zigbox's version number with the Zigcube version in its description and release notes.
10. **How do packages and macOS relate to the ship gate?** *Recommended:* `demo-c3` is the rollout
    demo only. Packages (their VM install demo) and the macOS build (the owner's Mac check) are
    required before the C3 release tag, but if either misses, it moves to the next release and
    the rollout ships, in keeping with "cut scope, keep the demo".
11. **Is the server's own upgrade in scope?** A server restarted mid-rollout resumes it (demo
    asserts it). Rolling the *agents* of a cluster through a package upgrade is mixed-version work,
    parked. *Recommended: confirm it stays parked.*
