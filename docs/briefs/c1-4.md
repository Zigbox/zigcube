# C1 slice 4 · Node controller and auditor

*Written 2026-11-02 by the slice-4 implementer from `docs/briefs/c1.md` (slice 4), `docs/briefs/c1-3.md` (its handoff) and `docs/authority.md` §2, §3 and §5. Read those first. Where this brief and `authority.md` disagree, `authority.md` wins and the disagreement is reported.*

## Goal

A node whose lease ends is marked `lost`; `lost_grace_ms` later the scheduler moves its replicas to the survivors; its observed records are removed a page at a time. The allocation accounting is audited, never silently repaired, and an operator can check and repair it. Decisions are counted in summaries, and retention keeps every decision a live subject's chain needs.

## Scope, in sub-slices (one commit or more each)

**4a. Lost nodes (node controller).**
- A node whose `/node-status` is `ready` for tenure `T` and whose `/nodes/<node>` record is gone gets `lost` for tenure `T`, with a `mark_lost` decision whose cause is `lease_expired` (`lease`, `ttl_ms`) and whose evidence is `{"lease":…, "ttl_ms":…, "last_heard_ms":…}` (`c1.md`, "Lease timeout printed at failover"). The write compares `/nodes/<node>` absent and the status at the revision read.
- The controller learns `lease`, `ttl_ms` and the last keepalive from `Store.lease_list` while the node is ready (`last_heard_ms = now − (ttl − remaining)`), and re-samples at each lease's predicted expiry, so the last sample before an expiry has seen the last keepalive. That memory is a cache: after a server restart it is empty, and `mark_lost` then says `last_heard_ms` is unknown and takes `lease` from `/nodes/<node>` read at the tenure revision (when not compacted).
- A node that registers again (any new tenure) is judged `ready` as in slice 3, whatever its old state.
- **Observed removal.** For a `lost` node, the node controller deletes `/observed/<node>/…` a page at a time (`observed_removals_per_txn` per transaction, each page with one `remove_observed` decision on the node, cause the `mark_lost` decision). Only records whose `tenure` is not the node's current tenure (or absent) are removed, so a node that re-registered keeps its new observations. Writer table: `/observed/` gains the `node_controller` role for deletes.

**4b. Moving replicas off a lost node (scheduler).**
- The scheduler's world includes nodes that have a status or an allocation record but no `/nodes` record.
- An assignment on a node that is `lost` (for the tenure the status judged, with no newer `/nodes` record), once `now ≥ status.at_ms + lost_grace_ms`, is **moved** to the best node that fits (`move_replica`, compare set of 8), with a `place_replica` decision whose cause is the `mark_lost` decision. If no node fits it is **released** (compare set of 2, `release_replica`, same cause), and the replica is then held like any unassigned one. Before the grace has passed the scheduler wakes at `at_ms + lost_grace_ms`, never earlier.
- `lost_grace_ms` is a parameter of `ControlPlane` and the scheduler (default `constants.lost_grace_ms`); the server flag and the `ttl` inequality check are slice 6/7 (the agent side of the lease is slice 6).
- **The move keeps the replica id.** `authority.md` §2 and slice 3's brief make the move the reaction to a lost node; the old instance on a partitioned node is told apart by its placement epoch (`/assigned` revision) and tenure, not by a new id. §3's sentence "a replacement has a new replica id" describes the replica controller's replacements; reported, not changed.

**4c. The allocation auditor (`ZC-B0003`).**
- A core step, role `allocation_auditor`, run by `ControlPlane` after the scheduler. It reads `/assigned/` and `/allocations/` at one revision, reconstructs each node's tally, and on a mismatch with no open finding writes `/audit/allocations/<node>` and an `allocation_mismatch` decision on the node (cause `observed`, `/allocations/<node>` at its revision; evidence both tallies and the read revision; `cause_diagnostic` the new `ZC-B0003`, "allocation accounting disagrees with assignments"). A finding whose node is consistent again is deleted with an `audit_clear` decision. Compares: `/allocations/<node>` at the revision read and the finding at the revision read (0 for absent).
- `GET /v1/status` gains `findings`: the open findings, `node`, both tallies, `revision` (additive).

**4d. Check and repair.**
- `GET /v1/check/allocations` runs the reconstruction at one revision and returns per node `{node, recorded, reconstructed, consistent, finding}`; `zcube check allocations` prints it and exits 1 if any node is inconsistent.
- `POST /v1/repair/allocations/{node}?confirm=true` (`zcube repair allocations <node> --confirm`; without `--confirm` it refuses with a `ZC-E` diagnostic saying what it would do). The server runs the scheduler's `repair_allocation` in the request: it requires an open finding, reconstructs, and writes the reconstructed tally to `/allocations/<node>` with a `repair_allocation` decision citing the finding's decision and the operator (the request id; writes are unauthenticated). Compares: the node's placement set minus the readiness compare (a repair is allowed on a lost node), i.e. `/allocations/<node>` and `/audit/allocations/<node>` at the revisions read. The auditor's next pass clears the finding.

**4e. Decision summaries.** `controller.put_decision` also writes `/decision-summaries/<kind>/<name>/<action>/<cause-kind>` (one more op; it reads the record and compares it at the revision read, or absent; two decisions in one batch for the same summary update one put). Every batch bound that assumed 2 ops per decision is re-derived. `why` shows the summary beside the chain, never as a step (text: one line; JSON: `summaries`, additive).

**4f. Reachability-based retention** (`authority.md` §5). Roots are, for each live subject, its newest decision of each action; a pass walks each root's chain (the `why` walk, bounded by `why_steps_max`) and pins every decision on it; only an unpinned decision beyond the per-subject budget (200, 7 days) is evicted; a deleted subject's decisions stay 24 hours. A deleted subject's summaries are removed with its last decisions.

**4g. Simulation.** `sim-cluster` (and `sim-c0` where it applies) checks after every step: I6 (already), the auditor never opens a finding on a healthy run, I7 (no assignment committed onto a node whose status was not `ready` for its tenure at that revision), a lost node's assignments are moved no earlier than its `lost` `at_ms + lost_grace_ms`, and every summary's `count` equals the decisions written for it (while none were pruned).

## Tests

- Node controller: lost on lease expiry with the `ttl` and last-heard evidence; not lost while the record exists; ready again on re-registration; observed removed in pages, a re-registered node's new observations kept; a restart with no memory still marks lost.
- Scheduler: no move before the grace, a move at it (compare set of 8, cause the `mark_lost`), a release when nothing fits and then a hold, conflict when the status moved between plan and commit.
- Auditor: a corrupted `/allocations` record opens one finding (ZC-B0003, one decision, not one per pass), the scheduler then places nothing on that node but still releases, repair writes the reconstruction, the next audit clears the finding. Conformance on memory, SQLite and Postgres for the auditor and the repair transactions.
- Summaries: counts exact across passes and within one batch; a summary is never a cause.
- Retention: a crash loop of more than 200 `replace_replica` decisions never evicts the service's `apply` or the chain of a live replica; an unpinned old decision is evicted; a deleted subject's decisions go after 24 hours.
- CLI goldens for `check allocations` and `repair allocations`, error pages for `ZC-B0003` and the repair refusal.
