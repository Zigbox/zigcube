## Goal

One line of config gives a service a public HTTPS address (SPEC):

```zig
.{ .name = "hello", .image = "...", .replicas = 3, .port = 8080, .public = "hello.example.dev" }
```

The demo:

1. Add `public = "hello.<demo-domain>"` to the service and apply it.
2. From a laptop outside the cluster, open the URL. The certificate is valid and the hello page loads.
3. Roll out a new version while a browser refresh loop runs. There are no errors, and the new version appears.
4. Remove the `public` line. The URL stops answering, and the certificate is kept for reuse.

Acceptance (SPEC):

- Certificates renew automatically and are stored encrypted in the control plane.
- The edge can reach only services that declare `public`.

C5 ships in **Zigcube 0.6.0** together with C3 and C4 (owner's release order; `docs/decisions/2026-11-14-zigcube-versions-follow-zigbox.md`). 0.6.0 is the first release gated on the Jepsen battery. That battery is a C5 prerequisite (`docs/decisions/2026-11-03-jepsen-before-c5.md`), so this brief also says what Zigcube owes it.

## Non-goals

- HTTP/2, HTTP/3, WebSockets upgrade (the edge offers ALPN `http/1.1` only; a browser falls back), gRPC, TCP or UDP passthrough.
- Wildcard certificates, DNS-01, other ACME CAs than Let's Encrypt (and its staging) and a test server, EAB, certificate revocation through ACME.
- Paths or several services under one host, rewrites, header policy, rate limiting, WAF, caching, compression.
- Load balancing the edges themselves: DNS points at edge nodes. Anycast, health-checked DNS and a cloud load balancer are out.
- RSA keys and certificates anywhere. P-256 only.
- A second server or HA control plane (still the leader-lease prerequisite).
- Client certificates from browsers on the public port.
- External key stores (cloud KMS and the like) for the sealing key: the owner slotted them into **C8** (`docs/decisions/2026-11-15-c5-acme-in-server-sealing-key-file.md`). C5 keeps the key's loading in one shell function and builds nothing more.

## Settled here

| Topic | Decision | By |
| --- | --- | --- |

| Port | The service's `port` field (C4). `public` without a `port` is refused at apply. | Brief |

## Design

### The edge role

`zcube-agent --edge` marks the node record `edge: true` and starts `zcube-agent edge` under a supervisor. The edge process:

- listens on `:443` (TLS, public mode) and `:80` (ACME challenges plus a redirect) on the node's public address (`--edge-listen`, default `0.0.0.0`);
- watches `/edge-routes` (the compiled host → service:port table) and `/edge-certs/<host>` (sealed), and `/acme-challenges/<token>`;
- for each request, takes a ready endpoint of the service from the C4 mesh table (the same endpoints a mesh caller uses) and dials it over mTLS as `/edge/<node>`.

The destination's supervisor checks the grant. Without `public` there is no grant, so the edge cannot reach the service. That is the second acceptance criterion, and it is enforced by the destination, not by the edge's good behaviour. `sim-c5` checks it (E2), and a tooth makes the edge skip its route table (it must still fail at the destination).

The edge never holds the sealing key. The server unseals a certificate's key and hands it over mTLS to the edge that asks for it. The edge proves `/edge/<node>`, the node record says `edge: true`, and the edge keeps the key in memory only. The store stays sealed: the first acceptance criterion holds for the control plane, and a stolen edge disk holds nothing.

### Public TLS (the widening)

B7's server grows a third mode, `Public`, next to mTLS and `Browser`:

- No CertificateRequest. The handshake ends at the client's Finished.
- The certificate is chosen by SNI from a table of P-256 chains (leaf plus intermediates as Let's Encrypt serves them). No SNI, or an unknown name, ends with `unrecognized_name`.
- ALPN: if offered, `http/1.1` must be among the protocols, or the handshake ends with `no_application_protocol`.
- Groups: Chromium 153 sends key shares for X25519MLKEM768 and x25519 (b7-slice6). The server takes the x25519 share. A client that offers x25519 without a share would need HelloRetryRequest, which B7 does not have; such a client is refused, and the count is reported (`edge_handshakes_refused{reason}`). Firefox and Safari send an x25519 share today. Slice 1 records the three browsers' ClientHellos as fixtures.
- Signature: `ecdsa_secp256r1_sha256` in CertificateVerify, through `x509_p256.sign` (low S).

The whole mode is in the core (pure, `tls_server.zig`), with the B7 fuzzers extended to it and teeth for each check skipped.

**Risk.** C5 puts the in-house TLS server on the internet for the first time. B7's decision planned an external review of it before C6. The owner moved that review to before 0.6.0, and the adversarial Fable release review of 0.6.0 counts as it: that reviewer reviews `tls_conn.zig`, `tls_server.zig` and the public mode explicitly (Q2, `docs/decisions/2026-11-15-c5-public-tls-mode.md`). The mode is used by the edge's listeners only.

### ACME

It costs no dependency, because std has every primitive: the HTTPS client and its public-root verification, ECDSA P-256, SHA-256, JSON and base64url. What it costs instead:

- About 1,500–2,000 lines to own: JWS signing, the RFC 8555 order state machine, the CSR, error mapping, nonce and rate-limit handling, and the in-tree fake.
- No library has met Let's Encrypt's edge cases before us. The fake ACME server must be strict, and an interop run against Pebble (Let's Encrypt's test server) and LE staging is required. That run is test-only tooling, out of `check`, like `mtls-interop`.
- `std.crypto.tls.Client` is the only TLS client that talks to the ACME directory. It verifies against the host's system roots. A host without a CA bundle fails with a coded error (`--acme-ca-bundle FILE` overrides).
- Port 80 must reach every edge from the internet. The cluster's operator owns that.
- Let's Encrypt's rate limits (50 certificates per registered domain per week, 5 duplicate certificates per week, 5 failed validations per host per hour). The demo and CI use staging. Production is used only for the recorded demo run.
- P-256 only. Let's Encrypt issues ECDSA, and the edge needs no RSA.

The machine is in the core (`acme.zig`): given the current order record and a response, it returns the next request to make, or a record to store. The shell does HTTP and the clock. The order's state is in the store (`/acme-orders/<host>`), so a server restart resumes rather than reorders. Diagnostics carry the ACME problem document's `type` and `detail` (DIAGNOSTICS.md: cause and fix, e.g. "Let's Encrypt could not reach http://hello.example.dev/.well-known/... (connection refused): port 80 on the edge nodes must be open to the internet").

### Store keys (docs/keys.md additions)

| Key | Value | Writer |
| --- | --- | --- |
| `/edge-routes` | host → service, port, generation; compiled by `mesh_plan` | controller |
| `/edge-certs/<host>` | sealed: P-256 key, chain, `notAfter`, issuer, sealed-key id; clear: `notAfter`, `state` | ACME shell |
| `/acme-account` | sealed account key; clear: account URL, directory URL | ACME shell |
| `/acme-orders/<host>` | order URL, status, authorization URLs, retry-at | ACME shell |
| `/acme-challenges/<token>` | key authorization (public by design) | ACME shell |
| `/nodes/<node>` | adds `edge: bool`, `edge_addresses` | agent |

`zcube why service hello` says which step the certificate is at and why it waits ("order pending: waiting for Let's Encrypt to validate http-01 for hello.example.dev, 40 s").

### Diagnostics (proposed; each needs the owner's yes before it lands)

- `ZC-E0712` public host claimed by another service.
- `ZC-E0713` `public` without `port`.
- `ZC-E0714` grant names `edge` as its source.
- `ZC-W0705` no edge node is ready (a `public` service has nowhere to be served).
- `ZC-E0823` ACME error, with the problem type and detail.
- `ZC-W0806` certificate renewal failing, with days left.
- `ZC-E0824` sealed record does not open (wrong or missing sealing key).
- `ZC-E0825` no CA bundle for the ACME directory.

## Slices

*Prerequisites, not slices:* B4–B7 merged to `main` (the TLS server); C3 and C4 merged (the mesh, grants and `/service/` certificates); the Jepsen battery runnable (below). Each slice ends with `zig build check` PASS.

Needs Q2.
2. **Sealing** (S). `seal.zig` (core, XChaCha20-Poly1305 with the key path as AD) and the key file in the server's shell, created with `--create-store`, refused if missing afterwards (E0824). *Tests:* round trip, moved record refused, tampered byte refused. *Mechanical:* keys.md rows (Haiku).
3. **ACME** (L) [overnight]. `acme.zig` machine, JWS ES256, CSR, `acme_shell.zig`, `src/testing/fake_acme.zig` (strict: nonces, `badNonce`, rate limits, invalid challenges), renewal and retention, `zcube why`. `zig build acme-interop` runs Pebble (test-only, out of `check`). *Tests:* the fake through a full order, a crash at each step resumed without a second order, renewal timing, expiry warning. Needs 2, Q3.
4. **Edge process and routing** (L). `--edge`, the edge supervisor, `/edge/<node>` certificates, `public` → derived grants in `mesh_plan`, `/edge-routes`, the HTTP/1.1 proxy over C4 endpoints, the :80 responder, `zcube get edges`, limits. `zig build edge-smoke`: server, two agents (one edge), fake ACME, a local client with the fake's root: it routes, rolls out with zero errors, refuses a non-public service at the destination, and `public` removal stops answering with the cert kept. *Tests:* grant derivation, `edge` in a user grant refused (E0714), host claimed twice (E0712). Needs 1, 3, the limits confirmed.
5. **sim-c5** (M) [overnight]. The cluster simulation gains edges, a simulated ACME server and browsers. Checks: E1 (an edge serves a host only with a valid, unexpired certificate for it), E2 (no edge-sourced connection reaches a service without `public`, at every revision), E3 (no browser request fails during a rollout, M5 reused), E4 (a certificate is renewed before 7 days left, with the ACME server up), E5 (no clear key in any store record). Each check gets a tooth (`edge_skip_route`, `acme_renew_late`, `seal_skip`, `edge_any_endpoint`, `edge_cert_any_host`). *Mechanical:* registering the teeth in `build.zig` and the canary list (Haiku).
6. **demo-c5** (M). `zig build demo-c5` and `docs/demos/c5.md` (below). Not a simulation.

## How demo-c5 runs

There are two forms, because a real domain cannot run in CI on every pull request.

- **`zig build demo-c5` (CI and the container).** Real processes: `zcube-server`, three agents (one `--edge`), Pebble as the ACME server, and a Playwright Chromium that trusts Pebble's root and resolves `hello.demo.test` to the edge. It runs all four SPEC steps with every outcome asserted. The refresh loop is Chromium reloading every 100 ms through a rollout. It is honest about what it is not: not Let's Encrypt, and not the internet.
- **The recorded run (once per release, a dispatched job).** A `workflow_dispatch` job in `Zigbox/zigcube-jepsen` (Q1, `docs/decisions/2026-11-15-c5-demo-domain-ci-job.md`) follows the same script against Let's Encrypt production on a public address:
  1. It builds Zigcube's `dist` tarball from the commit it is given, and creates a VM with a reserved static IPv4 address in the Jepsen project, with :80 and :443 open for that run.
  2. It writes an A record `hello.demo.zigbox.org` (DNS-only, not proxied) to that address through the Cloudflare API, with the token from the repository secret `CLOUDFLARE_DNS_TOKEN` (Zone DNS Edit on `zigbox.org` only; never printed, never on a command line, passed through the environment or a 0600 file). It refuses to run if the name exists, deletes by the record id it created, and never touches the apex (a Cloudflare Worker) or any other record.
  3. It runs the four steps with a headless Chromium on the runner as the outside browser, and keeps the transcript and a screenshot as artifacts.
  4. It deletes the record, the VM and the address even on failure.

  The supervisor copies the transcript into `docs/demos/c5.md`; it is what the site's `recorded` badge cites. Pull-request CI never runs it, and it is dispatched by hand, once per release (Let's Encrypt allows 5 duplicate certificates a week). The domain is the supervisor's reading of the owner's "zgbox.org" as `zigbox.org`.

## Jepsen on Google Cloud (0.6.0 ship gate)

This follows `docs/decisions/2026-11-15-jepsen-on-google-cloud.md`: a throwaway cluster of 3–5 VMs per run, a few hours per run, GitHub Actions with Workload Identity Federation and no key files, and the harness in `Zigbox/zigcube-jepsen` (Clojure).

**What Zigcube provides** (one slice-sized PR, `J` below, not a C5 slice):

1. **A release tarball** for a pinned commit, `zig build dist`: `zcube`, `zcube-server`, `zcube-agent`, linux x86_64, ReleaseSafe, with a SHA-256. The workflow builds it from the commit it cites.
2. **A deployment recipe** in `ops/jepsen/`: systemd units for the server and the agent, a script to make a Postgres 16 primary and a synchronous standby (from `pg_dev pair-up`), and the files the server and agents read. Everything is idempotent and nothing is interactive.
3. **A workload client** with a history: `zcube jepsen-client --op apply|get|delete|watch --history FILE`, an EDN or JSON line per invocation and completion (`:invoke`, `:ok`, `:fail`, `:info` for unknown, as ZC-E0213 is treated in `test-store-faults`).
4. **Fault surfaces** it can rely on: `SIGSTOP`/`SIGCONT` on any process (documented as safe), `iptables` partitions between any two hosts, clock skew on agents (`faketime` or `date -s`, documented which), killing and promoting Postgres.
5. **Invariants to check, as written properties:** authority.md's I1a–I7 restated for a history (no two live replicas of one slot across fencing, revisions monotonic, no acknowledged write lost under synchronous replication, ZC-E0215 halts on asynchronous loss), the job checks J1–J11 that a history can show, and C4's grant check (no connection without a grant).
6. **Read-only state endpoints** the checker can use after the run: `GET /v1/replicas`, `/v1/jobs`, `/v1/nodes` at a revision.

**What the owner sets up in GCP** (once):

1. A project for Jepsen only, with a billing budget and alert (suggested: 100 USD a month), and the Compute Engine API enabled.
2. A Workload Identity pool and an OIDC provider for `token.actions.githubusercontent.com`, with the attribute condition on the numeric repository id and the branch: `assertion.repository_id == '<id of Zigbox/zigcube-jepsen>' && assertion.ref == 'refs/heads/main'`. The id, not the name, so a renamed or recreated repository does not inherit the access.
3. A service account that the pool can impersonate (`roles/iam.workloadIdentityUser` on it for that principal set), with `roles/compute.instanceAdmin.v1`, `roles/compute.networkAdmin` (networks and addresses) and `roles/compute.securityAdmin` (firewall rules: `networkAdmin` cannot create them). The test VMs run with no service account attached, so `roles/iam.serviceAccountUser` is not needed. No key is created.
4. Quotas in one region for 5 e2-standard-4 VMs (20 vCPUs), and one static external address for the demo job.
5. Repository variables in `Zigbox/zigcube-jepsen` (not secrets): `GCP_PROJECT_ID`, `GCP_WIF_PROVIDER` (the provider's resource name), `GCP_SERVICE_ACCOUNT` (its email), `GCP_REGION`. One repository secret: `CLOUDFLARE_DNS_TOKEN`, for the recorded demo only.

Because the condition names `refs/heads/main`, both the battery and the demo job run only from `main` of that repository (a dispatch from another branch cannot get a token).

The workflow creates a network, the VMs and SSH keys made for the run, runs the battery, uploads the history and the report, and deletes everything it made even on failure. A nightly job deletes any leftovers labelled `jepsen-run`.

**The gate:** the 0.6.0 release PR cites a passing run of the battery on the release commit (the run URL and its result line), next to the fleet tracker line and the two reviews (AGENTS.md "Releases").
