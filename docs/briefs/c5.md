## Goal

One line of config gives a service a public HTTPS address (SPEC):

```zig
.{ .name = "hello", .image = "...", .replicas = 3, .port = 8080, .public = "hello.example.dev" }
```

The demo:

1. Add `public = "hello.<demo-domain>"` to the service and apply it.
2. From a laptop outside the cluster, open the URL. The certificate is valid and the hello page loads.
3. Roll out a new version while a browser refresh loop runs. There are no errors, and the new version appears.
4. Remove the `public` line. The URL stops answering, and the certificate is kept for reuse.

Acceptance (SPEC):

- Certificates renew automatically and are stored encrypted in the control plane.
- The edge can reach only services that declare `public`.

C5 ships in **Zigcube 0.6.0** together with C3 and C4 (`docs/decisions/2026-11-15-0.6.0-bundles-c3-c4-c5.md`). 0.6.0 is the first release gated on the Jepsen battery, a C5 prerequisite (`docs/decisions/2026-11-03-jepsen-before-c5.md`), so this brief also says what Zigcube owes it.

## Non-goals

- HTTP/2, HTTP/3, WebSockets upgrade (the edge offers ALPN `http/1.1` only; a browser falls back), gRPC, TCP or UDP passthrough.
- Wildcard certificates, DNS-01, ACME CAs other than Let's Encrypt (production and staging) and Pebble, EAB, certificate revocation through ACME.
- Paths or several services under one host, rewrites, header policy, rate limiting, WAF, caching, compression.
- Load balancing the edges themselves: DNS points at edge nodes. Anycast, health-checked DNS and a cloud load balancer are out.
- RSA or any key type but P-256 for keys **we** hold: the certificate key and the ACME account key are P-256. The chain above the leaf is the CA's: Let's Encrypt's intermediates (E5–E9) are P-384, Pebble's are RSA. The edge sends them as opaque DER and never parses or verifies them.
- A second server or HA control plane (still the leader-lease prerequisite).
- Client certificates from browsers on the public port.
- External key stores (cloud KMS and the like) for the sealing key: the owner slotted them into **C8** (`docs/decisions/2026-11-15-c5-acme-in-server-sealing-key-file.md`). C5 keeps the key's loading in one shell function.
- Serving while the server is down after an edge restart (see "Accepted limits").

## Design

### The edge role

`zcube node edge node3 on` writes `/edge-roles/node3` through the operator API. The agent on node3 watches that key. When it is on, the agent asks the server for an `/edge/node3` certificate (proving `/node/node3`), reports `edge_addresses` in its node record, and starts `zcube-agent edge` under a supervisor. When it goes off, the server stops issuing and handing over keys at once (both check the role at the current revision on every request), and the agent stops the edge.

The server refuses an `/edge/<node>` certificate or a certificate key to any caller whose node's role is not on, with **ZC-E0716**. A tooth (`edge_role_unchecked`) makes the server skip that check, and a test must fail: a node with the role off asks for an `/edge` certificate and for a host's key, and both must be refused.

The edge process:

- listens on `--edge-listen` (A7): :443 (TLS, public mode) and :80 (plain HTTP). A bind failure is **ZC-E0717** (address, port, the OS error, the fix);
- watches `/edge-routes` (canonical host → service, port, generation) and the clear part of `/edge-certs/<host>`;
- takes each host's key from the server (below) into memory;
- for each request, takes a ready endpoint of the service from the C4 mesh table and dials it over mTLS as `/edge/<node>`. It always goes through the mesh path, even to a replica on its own node: no loopback shortcut, no plain dial.

The destination's supervisor checks the grant. Without `public` there is no grant, so the edge cannot reach the service. That is the second acceptance criterion, enforced by the destination, not by the edge's good behaviour. `sim-c5` checks it (E2), a tooth makes the edge skip its route table (the destination must still refuse), and demo-c5 dials a non-public replica directly with the edge's certificate and asserts the refusal.

### The key handover

`POST /v1/edge/keys` on the server's mTLS listener. The caller must present `/edge/<node>`, the node's role must be on at the current revision, and the host must be in `/edge-routes`. The reply carries the unsealed key and the chain, with no caching; nothing on the path logs it. The edge keeps keys in memory only.

Tests (slice 4a): a `/service/` certificate, a `/node/` certificate, an edge whose role is off and a host not in the routes are each refused; a redaction test (below) covers the reply. Tooth: `edge_key_any_caller`.

**Exposure.** The edge's own `/edge/<node>` key is on its disk. Whoever steals that disk can fetch every public host's certificate key **until the operator revokes the role** (`zcube node edge <node> off`, or removing the node). Keys fetched before then stay usable until their `notAfter`, because ACME revocation is a non-goal; the fix is to reorder (`zcube why` explains this on revocation). A memory dump of a running edge exposes the keys it holds. The store stays sealed: the first acceptance criterion holds for the control plane.

### Host names

Canonicalized at apply, and the same function compares SNI and `Host`: ASCII only, lowercased, one trailing dot removed, at least two labels, each 1–63 letters, digits or hyphens not at either end, 253 bytes at most. Punycode (`xn--`) labels are accepted as given; a Unicode name is refused with the punycode spelling as the fix. IP literals, wildcards (`*`), empty labels and `localhost` are refused. Refusal: **ZC-E0715**. `Host` may carry `:443` (stripped); any other port is refused. Table tests cover each rule.

### Public TLS (the widening)

B7's server grows a third mode, `Public`, next to mTLS and `Browser`:

- No CertificateRequest. The handshake ends at the client's Finished.
- The chain is chosen by canonical SNI from a table of (P-256 leaf key, leaf DER, intermediates as opaque DER). No SNI, or an unknown name, ends with `unrecognized_name`.
- ALPN: if offered, `http/1.1` must be among the protocols, or the handshake ends with `no_application_protocol`.
- Groups: Chromium 153 sends key shares for X25519MLKEM768 and x25519 (b7-slice6). The server takes the x25519 share. A client that offers x25519 without a share would need HelloRetryRequest, which B7 does not have; it is refused, and counted (`edge_handshakes_refused{reason}`). Slice 1 records the three browsers' ClientHellos as fixtures.
- Signature: `ecdsa_secp256r1_sha256` in CertificateVerify, through `x509_p256.sign` (low S), with the leaf key.

The whole mode is in the core (`tls_server.zig`), with the B7 fuzzers extended to it and teeth for each check skipped.

**Risk.** C5 puts the in-house TLS server on the internet for the first time. The owner moved its external review to before 0.6.0, and the adversarial Fable release review of 0.6.0 counts as it (`docs/decisions/2026-11-15-c5-public-tls-mode.md`).

### The proxy

The edge is an HTTP/1.1 reverse proxy facing the internet, so request smuggling is the main risk. In the core (`edge_http.zig`, pure):

- Refused with 400 and the connection closed: `Content-Length` and `Transfer-Encoding` together; several `Content-Length` values; a `Transfer-Encoding` other than exactly `chunked`; a bad chunk size or extension; obs-fold; a bare CR or LF; whitespace before the colon or in a field name; a request target not in origin form; a request line or header block over A9; HTTP versions other than 1.0 and 1.1.
- `Forwarded`, `X-Forwarded-*` and `X-Real-IP` from the client are removed, then `X-Forwarded-For` (the peer address), `X-Forwarded-Proto: https` and `X-Forwarded-Host` are set. Hop-by-hop headers, and those named in `Connection`, are removed.
- The upstream's response is parsed by the same strict rules. A response that breaks them becomes a 502 and both connections close.
- After any framing doubt, the edge closes the client connection rather than reading on.
- :80 answers `/.well-known/acme-challenge/<token>` for any canonical host it routes, redirects other paths of routed hosts to https (308), and answers 404 to an unknown `Host`.

A fuzzer over the parser (`edge_http_fuzz`), and teeth `edge_allow_cl_te`, `edge_keep_forwarded` and `edge_lenient_chunk`, each caught by a test.

### ACME

std has every primitive: the HTTPS client and its root verification, ECDSA P-256, SHA-256, JSON and base64url. What it costs instead:

- About 1,500–2,000 lines to own: JWS, the order machine, ARI, the CSR, error mapping, nonces, rate limits and the in-tree fake.
- No library has met Let's Encrypt's edge cases before us. The fake ACME server must be strict. **CI and demo-c5 use Pebble**; **Let's Encrypt staging runs only in the dispatched demo job**, as a pass before production (below). Neither is in `check`.
- `std.crypto.tls.Client` verifies the directory against the host's system roots. A host without a CA bundle fails with **ZC-E0825** (`--acme-ca-bundle FILE` overrides).
- Port 80 must reach every edge from the internet. The cluster's operator owns that.
- Let's Encrypt's rate limits: 50 certificates per registered domain per week, 5 duplicate certificates per week, 5 failed validations per host per hour.

The machine is in the core (`acme.zig`): given the order record, a response and the server's clock reading, it returns the next request, a record to store, or a time to wake. The shell does HTTP. The order's state is in the store (`/acme-orders/<host>`), so a restart resumes rather than reorders.

**The account.** One per directory URL, created on first use, its P-256 key sealed in `/acme-account/<directory-hash>` with the directory URL and account URL in clear. Switching directories (Pebble, staging, production) uses another record and never another directory's account.

**HTTP-01 across edges.** The server writes `/acme-challenges/<token>` and then, before POSTing the challenge, **self-checks**: it fetches `http://<host>/.well-known/acme-challenge/<token>` from each ready edge's address (connecting to the address, sending the `Host`), in parallel with a short timeout. It POSTs once one edge answers the right key authorization; edges that did not are named in `zcube why` and a warning. If none answers, nothing is POSTed (no validation is spent) and the failure is **ZC-E0829**. An edge asked for a token it has not seen yet asks the server synchronously (`GET /v1/acme/challenges/<token>` over mTLS) before answering 404, so the store's propagation delay to some edges cannot fail a validation. The server never waits for every edge to acknowledge.

**Renewal and retries** (A1–A5, proposed):

- `renew_at` is `notBefore + 2/3 × (notAfter − notBefore)`. When the directory offers `renewalInfo`, the server fetches it (best effort: a failure falls back to 2/3), picks a random time in the window (now, if the window has started), re-polls at the `Retry-After` it gives, and sends `replaces` in the new order.
- A failed step retries with A2's backoff, and never stops while the host is `public`. Any `Retry-After` longer than the backoff wins. A `rateLimited` problem waits for its `Retry-After`, or 1 h without one.
- A3: at most 4 challenges per host may end `invalid` in a rolling hour; the next waits. With the self-check, a closed port 80 that the cluster can see costs nothing; one only the internet sees costs at most 4 an hour.
- A4: ZC-W0806 when less than min(7 days, 1/4 of the lifetime) is left and no renewal has succeeded, repeated each time `zcube why` or the status is read; the edge serves the current certificate until `notAfter`.
- At `notAfter` (server clock), the host's state becomes `expired` and edges stop serving it (E1).

**Errors, one blame per code.** ACME problem documents map to codes by who must act, carrying the problem `type`, `detail` and the fix (DIAGNOSTICS.md):

| Code | Blame | Problem types |
| --- | --- | --- |
| ZC-E0823 | The network in front of the edges: the CA could not fetch the token | `connection`, `unauthorized` on a challenge, `incorrectResponse`, `tls` |
| ZC-E0826 | The domain's DNS or CA policy | `dns`, `caa`, `rejectedIdentifier`, `unsupportedIdentifier` |
| ZC-E0827 | A CA rate limit (wait; the time is given) | `rateLimited` |
| ZC-E0828 | The CA or the path to it (unreachable, 5xx, a malformed reply, an unknown problem type) | `serverInternal`, others |
| ZC-E0829 | The cluster's own edges: the self-check failed | (no CA call made) |

### Clocks

The server's clock is the only one that decides anything about a certificate: `renew_at`, the warning, `expired`, retention and ARI windows. Edges and agents never compare certificate times; an edge stops serving a host because the server's record says `expired`. The server compares its clock with the CA's `Date` header on each ACME reply and warns with **ZC-W0807** when they differ by more than 5 minutes. `sim-c5` adds a `skew` profile (agents and edges skewed by up to an hour, the server not) and its checks are judged on the server's clock. Jepsen's clock faults use `date -s` on the host with NTP stopped (`chronyd` or `systemd-timesyncd`), not libfaketime: Zigcube's binaries are static and libfaketime's `LD_PRELOAD` does not touch them.

### Sealing and the key's lifecycle

`seal.zig` (core): XChaCha20-Poly1305, a random 24-byte nonce, the store key path as associated data, and a key id in the clear envelope header. A record cannot be moved to another path. A record can be replaced by an **older sealed version of the same path**; only a store writer can do that, and store writers are trusted. Accepted, not defended.

The key file is `seal-<hash>.key`, 0600, beside the CA key, loaded by one shell function.

- **No key and no sealed records** (a new cluster, or an upgrade from C3/C4): the server creates the key at start. An upgrade just works.
- **Sealed records and no key, or a key that does not open them:** the server refuses to start with **ZC-E0824**, naming the key file, the key id the records expect and two fixes: restore the key from backup, or start once with `--discard-sealed`.
- **`--discard-sealed`** deletes every sealed record (certificates, accounts, orders), creates a new key, and warns with **ZC-W0808**: every public host is reordered, which counts against Let's Encrypt's limits (50 per registered domain per week, 5 duplicates per week).

Tests (slice 2): round trip; a moved record refused; a tampered byte refused; a C4 store upgraded (key created, nothing refused); sealed records with the key removed (E0824); `--discard-sealed` (records gone, new key, W0808, then a new order on the next start).

### Secrets never leave sealed

An unsealed key (certificate, account or sealing key) never appears in an API reply but the key handover, a log line, a diagnostic, `zcube bundle` (even with `--no-redact`), a failure record or the console. The bundle never includes `seal-*.key` or `ca-*.key`. Each key-bearing field gets a redaction test: plant a known key, run the path (API, logs, bundle, console's API calls), and search the output for the key's bytes, hex and base64. Slices 2, 3b and 4a each add theirs.

### Diagnostics (proposed; each needs the owner's yes, A12)

Checked free against `main` 094c3d7 (08xx up to E0822) and `claude/c4-slice5` 81484b1 (07xx up to E0711 and W0704). **C5 reserves E0712–E0719, W0705–W0709, E0823–E0832 and W0806–W0809**; the supervisor tells the C4 sessions. Each slice re-checks before it registers.

- `ZC-E0712` public host claimed by another service.
- `ZC-E0713` `public` without `port`.
- `ZC-E0714` a grant names `edge` as its source.
- `ZC-E0715` the `public` host name is not a valid DNS name (which rule, and the fix).
- `ZC-E0716` a node without the edge role asked for an `/edge` certificate or a certificate key.
- `ZC-E0717` the edge could not bind its listener.
- `ZC-W0705` no edge node is ready (a `public` service has nowhere to be served).
- `ZC-E0823`, `E0826`–`E0829` ACME failures, one blame each (table above).
- `ZC-E0824` sealed records do not open (key missing or wrong).
- `ZC-E0825` no CA bundle for the ACME directory.
- `ZC-W0806` certificate renewal failing, with time left.
- `ZC-W0807` the server's clock differs from the CA's by more than 5 minutes.
- `ZC-W0808` sealed records discarded; every public host is reordered.

## Accepted limits

- **An edge that restarts while the server is down cannot serve.** Keys are in memory only and come from the server. The other edges keep serving. Not built around in C5.
- Same-path rollback of a sealed record by a store writer (above).
- A stolen edge's keys stay valid until `notAfter` (above).

## How demo-c5 runs

There are two forms, because a real domain cannot run in CI on every pull request.

### `zig build demo-c5 -Dbackend=sqlite|postgres` (CI and the container)

Real processes: `zcube-server`, three agents (node3 with the edge role), Pebble and `pebble-challtestsrv`, and a Playwright Chromium. Not Let's Encrypt, and not the internet.

**Pebble mechanics.**

- Pebble and `pebble-challtestsrv` are pinned release binaries, downloaded once with their SHA-256 checked in `build.zig`, like Zig itself.
- Pebble validates HTTP-01 on port **5002** by default, so the edge's :80 is configurable (A7) and the demo runs it on 5002. Every port the demo uses (Pebble's ACME and management ports, challtestsrv's DNS and management ports, the edge's two ports) is configurable and chosen free per run; a failed bind fails the demo with the edge's ZC-E0717 or a demo error naming the port.
- `pebble-challtestsrv` is Pebble's DNS: the demo adds an A record for `hello.demo.test` pointing at the edge, and Pebble resolves through it (`-dnsserver`).
- Two roots. Pebble serves its ACME directory with a fixed test certificate (`pebble.minica.pem`), which the server takes as `--acme-ca-bundle`. Pebble **issues** from a new root each run: the demo fetches it from Pebble's management endpoint and makes Chromium trust it through an NSS database (`certutil -d sql:$HOME/.pki/nssdb`) in a scratch `HOME`. Chromium reaches the edge with `--host-resolver-rules`.
- Pebble's defaults stay on: it rejects 5% of nonces (`PEBBLE_WFE_NONCEREJECT`), which exercises `badNonce`, and it reuses authorizations, which step 4 must not confuse with our client's own orders. `PEBBLE_VA_NOSLEEP=1`; `PEBBLE_VA_ALWAYS_VALID` is off.
- Pebble's certificate validity is set short (`certificateValidityPeriod`, 90 s) so a renewal happens inside the demo.

**Steps and assertions.**

SPEC's steps 1–4 are steps 1, 2, 3 and 6; steps 4, 5 and 7 assert the two acceptance criteria.

1. Apply `hello` with `public`. Assert: a certificate is issued, `/edge-certs/hello.demo.test` exists, ZC-W0705 is absent, and `zcube why service hello` reports `serving`.
2. Chromium opens `https://hello.demo.test`. Assert: the page loads with the expected body and no certificate error.
3. Roll out a new version while Chromium reloads every 100 ms and a client runs M5's 20 req/s. Assert: zero failed loads and requests, and the new version's body appears.
4. **Renewal.** Keep the refresh loop running past 2/3 of the certificate's lifetime. Assert: the serial (read by a TLS probe) changes, `notAfter` moves later, and zero loads fail across the change.
5. **Only `public` is reachable.** Apply `secret` (no `public`). Assert: a request to the edge with `Host: secret.demo.test` gets no certificate (`unrecognized_name`); and a direct mTLS dial to a `secret` replica's mesh port, made by the demo with the edge's own `/edge/node3` certificate, is refused at the destination with C4's grant code.
6. Remove `public`. Assert, within `mesh_revoke_ms` plus the route propagation bound: https gets `unrecognized_name`, :80 returns 404 for the host, `/edge-certs/hello.demo.test` still exists with the same serial. Re-add `public`. Assert: it serves again with the same serial, and **0 new Pebble orders** (Pebble's order count, read from its log, and the server's `acme_orders_total` both unchanged).
7. **No clear key in the store.** Scan the real store's bytes (the SQLite file and its WAL, or a `pg_dump` of the `zcube` schema) for each leaf key the demo holds (fetched through the handover as `/edge/node3`, before and after renewal) in raw, hex and base64 forms. Assert: none found, and every `/edge-certs/*` and `/acme-account/*` record is a sealed envelope.

### The recorded run (once per release, a dispatched job)

A `workflow_dispatch` job in `Zigbox/zigcube-jepsen` (`docs/decisions/2026-11-15-c5-demo-domain-ci-job.md`) runs the same script against Let's Encrypt on a public address:

1. **Input.** A Zigcube commit that is an ancestor of `main` or the commit of a release tag; the job checks it (`git merge-base --is-ancestor`, or the tag) and refuses anything else.
2. **Build** in a job with no secrets and no `id-token` permission: the `zig build dist` tarball and its SHA-256, passed on as an artifact.
3. **Deploy** in a job bound to the GitHub Environment `demo-dns` (deployments from `main` only, a required reviewer). It takes Google credentials through Workload Identity, creates a VM, and attaches the static IPv4 address the owner reserved beforehand. The job never creates or deletes that address.
4. **DNS.** The DNS method is the owner's open choice (see below). Under option (b), the Cloudflare token is an Environment secret of `demo-dns`, exposed (`env:`) only to the create and delete steps. The create step refuses if the name exists, writes `hello.demo.zigbox.org` (A, DNS-only, TTL 60, comment `zcube-demo run=<run id>`), then waits until Cloudflare's authoritative nameservers answer with the address.
5. **Run.** The demo against **Let's Encrypt staging** first, then production, with headless Chromium on the runner as the outside browser; the transcript and a screenshot are artifacts.
6. **Clean up, even on failure:** delete the record by the id it created, then the VM. The address stays.

A **nightly sweep** deletes any record under `demo.zigbox.org` whose comment starts `zcube-demo` and is over 6 hours old, and any VM labelled for the demo. **Open, the owner's choice; not decided.** Either way, `demo.zigbox.org` is delegated to a zone of its own. (a) *Recommended:* the NS records point at a GCP Cloud DNS zone, and CI writes the record through the existing Workload Identity Federation, so CI holds no Cloudflare token. (b) A zone-wide Cloudflare DNS-edit token, kept in the `demo-dns` Environment (main only, a required reviewer) and exposed only to the DNS steps. A Cloudflare token cannot be scoped below the zone without an Enterprise subdomain zone, so under (b) it can edit every record in that zone, including the apex (a Cloudflare Worker) and the MX records.

**Status.** README and the site mark C5 "demonstrated" when the `demo-c5` CI job is green (AGENTS.md). The site's `recorded` badge cites the dispatched run, whose transcript the supervisor copies into `docs/demos/c5.md`. Pull-request CI never runs it; it is dispatched by hand once per release.

## Jepsen on Google Cloud (0.6.0 ship gate)

This follows `docs/decisions/2026-11-15-jepsen-on-google-cloud.md`: a throwaway cluster of 3–5 VMs per run, GitHub Actions with Workload Identity Federation and no key files, and the harness in `Zigbox/zigcube-jepsen` (Clojure).

**What Zigcube provides** (one slice-sized PR, `J`, not a C5 slice):

1. **A release tarball** for a pinned commit, `zig build dist`: `zcube`, `zcube-server`, `zcube-agent` and `zcube-jepsen-client`, linux x86_64, ReleaseSafe, with a SHA-256.
2. **A deployment recipe** in `ops/jepsen/`: systemd units, a script for a Postgres 16 primary and a synchronous standby (from `pg_dev pair-up`), and the config files. Idempotent and non-interactive.
3. **A workload client**, a separate test-only binary so the shipped CLI does not grow: `zcube-jepsen-client --op apply|get|delete|watch --history FILE`, a JSON line per invocation and completion (`:invoke`, `:ok`, `:fail`, `:info` for unknown, as ZC-E0213 is treated in `test-store-faults`).
4. **Fault surfaces:** `SIGSTOP`/`SIGCONT` on any process (documented as safe), `iptables` partitions between any two hosts, clock faults with `date -s` and NTP stopped (not libfaketime, above), killing and promoting Postgres.
5. **Invariants, as written properties:** authority.md's I1a–I7 restated for a history, the job checks J1–J11 that a history can show, and C4's grant check.
6. **Read-only state at a revision:** `GET /v1/replicas`, `/v1/jobs`, `/v1/nodes` with `?revision=N`. This is **new API surface**; PR `J` proposes it in `docs/api.md` first.
7. *Mechanical (Haiku):* the client's unit-test boilerplate and the history encoder's golden files.

**What the owner sets up in GCP** (once):

1. A project for Jepsen only, with a billing budget and alert (suggested: 100 USD a month), and the Compute Engine API enabled.
2. A Workload Identity pool and an OIDC provider for `token.actions.githubusercontent.com`, with the attribute condition `assertion.repository_id == '<id of Zigbox/zigcube-jepsen>' && assertion.ref == 'refs/heads/main'`.
3. A service account the pool can impersonate, with `roles/compute.instanceAdmin.v1`, `roles/compute.networkAdmin` and `roles/compute.securityAdmin`. The test VMs have no service account. No key is created.
4. Quotas in one region for 5 e2-standard-4 VMs (20 vCPUs), and **one static external address the owner reserves** for the demo job, which only attaches it.
5. Repository variables in `Zigbox/zigcube-jepsen`: `GCP_PROJECT_ID`, `GCP_WIF_PROVIDER`, `GCP_SERVICE_ACCOUNT`, `GCP_REGION`, `DEMO_ADDRESS_NAME`. Under option (b) only, the GitHub Environment `demo-dns` (main only, required reviewer) holds the secret `CLOUDFLARE_DNS_TOKEN`.

Because the condition names `refs/heads/main`, both the battery and the demo job run only from `main` of that repository.

The workflow creates a network, the VMs and SSH keys made for the run, runs the battery, uploads the history and the report, and deletes everything it made even on failure. A nightly job deletes leftovers labelled `jepsen-run`.
