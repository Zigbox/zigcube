# C1 slice 10 · The store under faults

*Written 2026-10-31 by the supervisor, on the owner's call (2026-10-30) that Zigcube keeps Postgres as its store, with rules, and tests it the way Jepsen would. Read this first, then `docs/briefs/c1.md` (the two store rows of "Settled here", slice 10, "Gate for shipping C1"), `docs/store-design.md`, `src/store.zig`, and `docs/authority.md` where it touches the store. Where they disagree, stop and report.*

## Why

The orchestrator's safety rests on its decisions persisting: a placement, a lease, a fence that the store acknowledged must stay acknowledged. Jepsen's findings on Postgres sit in replication and failover (a promoted asynchronous standby forgets acknowledged commits; reads from replicas break snapshot isolation), not in a single primary, and the store already serialises writers on one row lock under `READ COMMITTED` (`store_postgres.zig`, "Revisions"). So the work is: make a store that went backwards impossible to act on, and prove the store contract under a hostile network and a failover with a recorded history, not a hope.

## Slices

Four small slices, each its own session, in order. 10a and 10c do not depend on each other and may run side by side on separate branches.

### 10a · The chain hash

- Every committed write (a `txn` that changes a key, and every write the store makes itself: lease expiry, revocation) records `h(n) = SHA-256(h(n-1) ‖ revision ‖ the revision's events in a canonical encoding)`, `h(0)` = 32 zero bytes. The encoding and the hash are computed in Zig, in one function in `store.zig` (core), never in SQL, so the memory, SQLite and Postgres backends give byte-identical hashes for the same history. Write the encoding down in `docs/store-design.md`: field order, lengths, kind, lease; nothing that depends on the backend.
- `Store.status` returns the hash of the current revision. A new call, `hash_at(revision)`, returns the hash of any revision since 1. Compaction never drops a hash: one 32-byte row per revision is kept (a million revisions is 32 MB; revisit in C3 if it matters). Say how each backend stores it and that it is written in the same transaction as the revision.
- The schema version goes up (`schema_version`), with the migration of an existing C0/C1 store: the hashes of revisions already compacted cannot be recomputed, so an upgraded store starts its chain at its current revision from a recorded seed, and `hash_at` below that point fails with a `ZC-` diagnostic that says why. Test the upgrade from a store written by the previous schema.
- Conformance (`store_conformance.zig`, every backend): the same scripted history gives the same hashes on all three; a concurrent-writers test checks that `hash_at` over the whole run recomputes from the log; a transaction that commits nothing changes no hash.
- Not in 10a: who checks the hash.

### 10b · Nothing acts on a store that went backwards

- A core wrapper (`VerifiedStore`, or a check inside the existing server driver if that is simpler; say which) remembers the highest `(revision, hash)` it has seen and, on every `status` and after every reconnect, checks the store: a revision lower than the remembered one, or a different `hash_at(remembered revision)`, is refused with one `ZC-` diagnostic naming both revisions and both hashes (shortened), and the server stops acting (the controllers do not step, writes are refused) until an operator intervenes. No automatic recovery.
- The server persists its remembered pair, so a server restarted after a lossy failover still notices: a small file next to the server's config or under a `--state-dir` (decide; say why), written crash-safe like the agent's files (fsync, rename, fsync the directory).
- Agents: the server's agent endpoints carry the revision and hash they answered at; the agent remembers the highest in `AgentState` and refuses an answer from behind it with the same diagnostic. Coordinate with `agent_client.zig` (core) on branch `claude/c1-2b-cluster-sim`: if 2b has not merged, build on `main` and note the merge points for whoever merges second.
- The operator's way out: `zcube store accept-rollback --confirm` (a decision with the old and new pair as evidence) after they have looked. Name it in the diagnostic's fix line.
- Tests: memory store with a hand-made rollback and fork; a server restart across a rollback; an agent that sees an answer from behind.

### 10c · The fault proxy and the history checker

- `src/testing/fault_proxy.zig` (shell): a TCP proxy in Zig, standard library only, scripted per test: latency, bandwidth limits, cut every connection now, cut a connection after N bytes in a direction (so mid-transaction and mid-`COMMIT` both happen), half-open (one direction stops), black hole (accept and say nothing), heal. `demo-c1`'s partition test (slice 8) will use the same proxy: give it the interface that test needs (both directions dropped, then healed) and say so in its doc comment.
- A history recorder and checker (core, `src/testing/history.zig`): every `Store` call's invocation and completion with its result, from several client threads, through the proxy. The checker verifies:
  - compare-and-set linearizable (a Wing–Gong / Knossos-style search over a single key's register history is enough at these sizes; bound it and say the bound);
  - revisions gap-free and in commit order, and each revision's events match what its writer sent;
  - every write reported as unknown (`ZC-E0213`'s "outcome unknown", or the store's lost acknowledgement) is either wholly in the log or wholly absent;
  - a watch from N + 1 delivers exactly the log after N.
- The checker has teeth: a test feeds it a hand-made history with a lost write, one with a duplicated revision and one that is not linearizable, and each is caught.
- `zig build test-store-faults -Dbackend=postgres [-Dseed=N]` runs the conformance suite's concurrent tests and a fault schedule chosen by the seed through the proxy, records, checks, and prints the seed first. SQLite runs it too where a proxy applies (it does not: say so, and run SQLite with the history checker only).

### 10d · Failover

- `pg_dev` learns to start a primary and a streaming standby on one machine (two data directories, two ports), synchronous or asynchronous by flag, and to promote the standby.
- The test: load through the proxy with the history recorder; mid-load, stop the primary hard and promote the standby; the clients reconnect to the standby (a libpq multi-host connection string or the proxy repointed; decide). Then:
  - synchronous standby: no acknowledged write is missing, and the checker passes across the failover;
  - asynchronous standby with the primary killed before the standby caught up (hold the standby back with the proxy so the loss is certain, not lucky): 10b's check refuses the promoted store, the server stops acting, and the diagnostic is the one 10b wrote. This is the teeth test.
- `test-store-faults` gains the failover run; CI runs it on Postgres; `docs/demos/c1.md` and the operator docs state the supported setup (`c1.md`, "Supported Postgres setup").
- The simulation fleet (slice 9) runs `test-store-faults` once a day with a fresh seed.

## Not in this slice

A different store; Postgres logical replication; any read from a replica; OrioleDB-specific behaviour (the plain-heap path is what runs); a Jepsen (Clojure) harness: we write our own, in Zig; reading through a connection pooler.
