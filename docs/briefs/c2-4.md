# C2 slice 4 · Summary and fetch plan as pure core modules

*Derived from `docs/briefs/c2.md`, slice 4, on 2026-11-03. It adds nothing that c2.md does not name;
what the implementer had to decide is listed at the end.*

## Goal

The algorithms of C2, proven by table tests and a simulation before any key, process or network
exists: the store summary (a Bloom filter plus per-tree bottom-K sketches and the locality
estimate), and the fetch plan (peer choice, per-chunk verification, skipping a bad peer, registry
fallback, bandwidth caps).

## Changes

- `src/chunk_summary.zig` (core): `Filter` (Bloom filter over chunk hashes; the k indices come
  from the BLAKE3 hash itself; add, query, merge), `Sketch` and `SketchBuilder` (bottom-K of a
  tree's distinct chunks, weighted by bytes), `locality_bytes(target, held)`.
- `src/fetch_plan.zig` (core): `Plan`, the state machine. Input: the tree's chunk list, peer
  filters, caps, the time. Output: the next request, or a wait, or done. Fed back: `verified`,
  `bad_hash` (the plan hashes the bytes itself), `refused`, `timeout`. A `bad_hash` peer is struck
  for this fetch and reported with the new code ZC-W0601. After `fetch_peer_wait_ms` with no peer
  holding a chunk it falls back to the registry; per-peer and per-node byte-rate caps.
- `src/sim_images.zig` (core): a model of N node stores, tree versions that share most chunks, and
  peers that lie, stay silent or refuse.
- `src/sim_swarm.zig` (core) and `src/sim_swarm_main.zig`, `src/sim_swarm_teeth_main.zig` (shell
  roots): `sim-swarm`, native and WASM reports compared, and its teeth fault.
- `src/constants.zig`: the constants, with derivations. `src/diag/codes.zig`: ZC-W0601 (plus its
  golden, error page). `src/core.zig`, `src/wasm_core.zig`, `tools/wasm_check.mjs`, `build.zig`,
  `src/testing/check.zig`, CI: wiring. `docs/swarm.md`: the format, the estimate, the fetch protocol
  as a state diagram, the constants.

## Tests

- Bloom: no false negatives; false-positive rate within bound at capacity (seeded); merge.
- Sketch estimate within bound for overlaps of 0, 50, 99 and 100 %.
- Fetch plan: a corrupt peer is struck and the chunk fetched elsewhere; all peers corrupt means the
  registry; no peer means the registry after the wait; caps hold; an unverified chunk is never
  accepted; a refused or silent peer.
- `sim-swarm` over seeds, native equals WASM; the teeth fault ("accept a chunk without checking
  it") must fail a seed.

## Gates

`zig build check` PASS on the reported commit, with `sim-swarm` and `sim-swarm-teeth` in it and in
CI wherever `sim-cluster` is; a seed sweep 1..200 and the teeth run reported.

## Non-goals

No key, record, API, `Runtime` or `Store` change; no wire encoding of the summary (slice 5 writes
`/node-store`); no process, socket or file; no real chunk store. Not touched: `records.zig`,
`apply.zig`, `api.zig`, `runtime.zig`, `agent.zig` (slice 2 is working there).

## Decided by the implementer (c2.md left it open)

1. Entries of a sketch carry a 4-byte size beside the 8-byte key (12 bytes, not 8), so the estimate
   is weighted by bytes.
2. The estimate compares the target's sample with the union of the held sketches over the key
   range both cover exactly, so a held tree that is not the target but shares chunks counts.
   Where the target's sketch comes from is slice 5's question; the function takes it as input.
3. The plan verifies by hashing the bytes it is handed (BLAKE3), so "never accepts an unverified
   chunk" is a property of the plan, not of its caller.
4. The code for a bad peer is ZC-W0601 (warning, blame external): the fetch goes on.
5. Chunk state lives in a slice the caller provides, so a 64 Ki-chunk tree is not on the stack.
