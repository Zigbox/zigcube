## Goal

A job starts only from an image that a trusted key has signed. The check runs twice:

- **At admission.** `zcube-server` checks the job against the keys in its own configuration.
- **Before exec.** `zcube-agent` checks it again against a policy file local to the node. No
  API call can change that file.

Both checks call Zigbox's verdict function, so the two ask the same question in the same way.
A refusal happens before any process starts, and it never stops anything that is already
running.

## Fixed decisions

- **O3 is assumed, not answered: Botpike runs `zbx pull` and `zbx sign` itself.**
  - Zigcube adds no resolve call.
  - The owner's recommendation is recorded in `botpike-first-customer.md`.
  - If the owner chooses the resolve call instead, it becomes a slice of its own. Nothing here
    changes.
  - The assumption is recorded in `docs/decisions/2026-11-12-o3-assumed-botpike-runs-zbx-pull.md`.
- **Signatures travel in the job.**
  - The job body gains `signatures`, an array of DSSE envelopes.
  - Each envelope is the text of one line of `zbx trust export <tree>`.
  - Bounds: at most `job_signatures_max = 4` envelopes, each at most
    `job_signature_bytes_max = 2048` bytes.
  - The envelopes count toward `job_run_bytes_max`. If 16 KiB is too small for them, ask first.
  - No registry lookup is made. M8 keeps signatures out of registries.
- **The subject.**
  - The tree is the job's `image` (`b3:<hex>`).
  - When the job has a `source`, the binding is that `source`'s manifest digest.
  - So a tree-only signature counts for any job of that tree, and a signature bound to a
    manifest counts only for a job pulled from that manifest. This is M8's rule, applied
    unchanged.
- **Server policy.**
  - `zcube-server`'s config gains `trust = .{ .policy = "<path>" }`.
  - The path names a Zigbox policy file, in the same format as `/etc/zbx/policy.zon`.
  - The server reads it once, at start. A file that cannot be read stops the server with
    ZC-E0106.
  - With no `trust` entry, nothing is checked, as today.
  - With a policy that has `require_signature = true`, `POST /v1/jobs` refuses a job that no
    trusted line covers. The refusal is `403`, carrying the Zigbox code `ZBX-E0905`, with
    Zigbox's cause listing each line and why it does not count.
  - No job is created.
  - **Cut from the input:** the input asks for a job state `refused` at admission. Refusing the
    request is simpler and just as safe, because nothing exists to start.
- **Node policy.**
  - `zcube-agent --trust-policy FILE` (also a key in its ZON config) names the node's own policy
    file. The API cannot name, change or switch off that file.
  - Before it starts a run, the agent calls `verdict.judge` with that policy and the job's
    envelopes.
  - A refused run ends with the new ending reason `refused`, carrying ZBX-E0905 and its cause.
    The run is never retried, never started elsewhere, and counts as an ending under J1 to J11.
  - With the real runtime, the agent also imports the envelopes into the node's store
    (`store.import_trust`). Zigbox's own run gate then judges the run a third time, if the
    node's `/etc/zbx/policy.zon` asks it to.
  - An agent with no `--trust-policy` checks nothing. `zcube why node` says that.
- **Keys are named in policy files only.** No API field names a key, and no API field changes
  trust.
- **Order.** B5 does not depend on B4. It may run beside B4, and merges after the `b3` tag.

## Diagnostics

- Zigbox's `ZBX-E0905` (no trusted signature covers the run) and `ZBX-E0904` (a policy file
  cannot be used) reach the user as Zigbox writes them, the same way `ZBX-E0410` does today.
- New ZC codes:
  - Malformed `signatures` is ZC-E0130, naming the field and the bound.
  - A bad `trust` config is ZC-E0106.
  - No other new ZC code is expected. Ask before adding one.

## Slices

1. **The job field and the server check.**
   - `signatures` in the body, the store and `docs/keys.md`, with its bounds.
   - The `trust` config entry and the call to `verdict.judge` at admission.
   - The `403` response.
   - Tests:
     - an unsigned image is refused;
     - an image signed by an untrusted key is refused;
     - a signature over another tree is refused;
     - a manifest-bound signature with a different `source` is refused;
     - a good signature is accepted;
     - with no `trust` entry, everything is accepted as before.
   - Each check has a teeth test.
   - The server's admission check is core code (WASM-clean), so `wasm-check` covers it.
2. **The agent check.**
   - `--trust-policy`, the check before exec, and the `refused` ending in `docs/api.md`, the
     watch, `zcube why job` and the console.
   - Both runtimes.
   - A test writes an assignment straight into the store, so the server's check is bypassed,
     and the agent must refuse it before any process starts. Over the fake runtime, no
     supervisor is spawned.
   - `agent-smoke` gains one refused job and one signed job.
3. **Simulation.**
   - The cluster simulation's jobs carry signatures from a seeded set of keys. Nodes trust a
     subset.
   - J12, a new check: no run of a job that its node's policy refuses ever starts, and every
     refused run ends `refused` exactly once.
   - A tooth skips the agent's check.
   - `sim-c1` runs it, and the fleet picks it up.
4. **The demo.**
   - `demo-b5` runs on B3's VM rig with `--runtime zigbox`. A job is signed with `zbx sign` and
     `zbx trust export` in the guest and submitted, and it runs.
   - Each of these is refused at the server: an unsigned job, a job signed by an untrusted key,
     and a job whose signature names another tree.
   - The same three are refused again at the agent, through an assignment written straight into
     the store.
   - `demo-b5` skips without `ZCUBE_REAL_HOST=1`, and CI runs it.

## Non-goals

- A resolve call (O3).
- Signatures in registries.
- Provenance requirements (`require_provenance`): the server passes them through if the policy
  sets them, but nothing tests them.
- Key rotation tooling.
- Per-tenant keys. The cluster trusts Botpike's admission key, which signs for every tenant.
- Services. Jobs only; signed services are C6.
- The external TLS review (a C6 prerequisite, not B5's).
