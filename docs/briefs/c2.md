## Goal

SPEC Part II, "C2 · Swarm: store-aware distribution": images reach nodes fast because nodes share
chunks, and the scheduler prefers nodes that already have them. Each agent advertises a compact
summary of its local store. The scheduler adds a locality score. Agents fetch chunks from peers
before going to the registry, and verify every chunk by its hash. `zcube stats pull` reports bytes
by source.

The demo (SPEC, verbatim in substance):

1. Deploy `python-app v1` to three nodes. `zcube stats pull` shows registry bytes once, then peer
   bytes for the other two nodes.
2. Deploy `v2`, which changes one source file. Each node transfers only that file's chunks; the
   stats show kilobytes, not hundreds of megabytes.
3. Block registry access from VM3 with a host firewall rule and add a replica there. It starts
   anyway, entirely from peers.
4. Add a fourth, empty node and a new replica. The scheduler picks a warm node, and `zcube why`
   names locality as the reason.

Acceptance: a peer that serves a corrupted chunk is detected by hash, skipped and reported.
Locality never overrides resource fit or spread.

## What exists, and what is missing (gap analysis)

### Zigbox's store, as the code has it

- **Objects are whole files.** `store/objects.zig` stores each regular file once, under
  `objects/ab/<62 hex>`. The object id is the BLAKE3 hash of a header, the content hash and the
  metadata, so an id tells you nothing about the bytes or the chunks.
- **Chunks are fixed-size.** `store_chunk_bytes` is 1 MiB (`constants.zig:522`), with at most 4096
  chunks per file. A `.chunks` list is written only for an object longer than one chunk. A
  one-chunk file's single chunk hash is its content hash. Digest text is `b3:` followed by 64 hex
  digits.
- **Dedup works per file, not per chunk.** No index maps a chunk hash to an object, and two files
  that share a megabyte share nothing in the store. This matters for demo step 2: in a Python
  image, "one source file changed" means one new object of a few kilobytes and a new tree record.
  Everything else is already on the node under the same object ids, so the step holds with
  whole-file objects. Nothing in C2 needs cross-file chunk dedup.
- **What the library already offers:**
  - `store.chunks` (`object.chunk_hashes(store, id, io, out)`) lists an object's chunk hashes.
  - `store.put_chunk(store, io, wanted, index, bytes, failure)` (`chunks.zig:148`) checks each
    chunk's length and BLAKE3 hash, accepts chunks in any order, resumes after a restart, and
    checks the whole content hash on the last chunk. `Wanted` is `{id, attrs, size, content,
    hashes}`. This is the receiving half of a peer fetch, already written and tested.
  - `store.get_tree` (`trees.load`, a verified read), `store.walk.walk`, `store.shards.read`,
    `roots.list` and `usage`.
  - A test at `store.zig:134` already checks "the library surface Zigcube's C2 uses".
- **What is missing (the Zigbox changes, Z1–Z8, are listed below):**
  - There is no verified read of one chunk or one object. A peer server must not send bytes it
    has not checked.
  - There is no public enumeration of the objects in a tree with their chunk lists, and no cheap
    "do I have this object" check.
  - `trees.put` asserts its hash, so a wrong hash crashes the process. A tree that arrives from a
    peer is untrusted input and needs a put that returns an error instead.
  - There is no way to export or import an image record (`images.save`): the settings and GC root
    that a pull writes. A tree fetched from a peer would otherwise have no entrypoint, environment
    or user, and could be collected.
  - There are no pull stats by source. `pull` reports `BlobOutcome {cached, downloaded, resumed}`
    for each blob; `import.Result` has `objects_new`, `objects_reused` and `bytes_new`. The number
    of bytes per blob is not in the result.
  - There is no fetch seam keyed by a blob or chunk digest. `Request.mirrors` works for docker.io
    only, and the `Net` vtable is an HTTP-level GET. A peer cannot stand in as a registry mirror.
  - Store work must run in the single-threaded namespace child (`store.namespace`). That process
    has no entry point the agent can call to read or write chunks.

### The pieces SPEC names

| SPEC piece | Today | What C2 builds |
|---|---|---|
| Store summary (Bloom filter of chunk hashes per tree) | nothing | A pure `chunk_summary` module in the core. A Bloom filter over the hashes of the chunks the node holds, plus a list of held trees, each with a bottom-K sketch of its chunk hashes weighted by bytes. Written by the agent to a new lease-bound key, `/node-store/<node>` (O1). It cannot live on `/nodes/<node>`: tenure is that key's `mod_revision`, so rewriting it would reset tenure. |
| Locality score in the scheduler | `precedes`: fit, then spread, then least allocated, then name | A fourth comparison inserted between spread and least allocated: estimated bytes the node already holds of the replica's tree, read from `/node-store` (O2). It is advisory. It cannot make a node fit, and it cannot beat spread. |
| Peer fetch, verified per chunk | `zigbox_image.start_with_image` pulls from the registry only | A pure `fetch_plan` state machine (choose peers, verify each chunk, skip and report a bad peer, fall back to the registry after a timeout, cap bandwidth). It is driven by an agent-side `zcube-agent fetch` worker, and peers are served by a chunk server on the agent's `/nodes` address (O3). |
| `zcube stats pull` | nothing | `/pulls/<node>/<tree>` records of bytes by source (registry, peer, cached), plus a CLI, `docs/api.md` and the console (O6). |
| `zcube why` names locality | `why` renders the decision's ranking members | The decision records the locality bytes and the `/node-store` revision it read. `why` says "picked node2: it already holds 312 MiB of this image". |

### Why the summary is per node, and the score is an estimate

A Bloom filter of every chunk hash on the node answers "does node N have chunk c" with false
positives and no false negatives. It does not answer "how much of tree T does N have" without the
tree's chunk list, and the server has no chunk lists: it holds no images. So the summary has two
parts:

- **The Bloom filter** is for the fetching agent. It already has the tree's chunk list, and asks
  each candidate peer's filter which chunks it probably holds. A false positive costs one refused
  request, nothing more, because every chunk is verified.
- **The held-tree list** is for the scheduler. It lists each complete tree the node holds, plus a
  bottom-K sketch of its chunk hashes weighted by size. A replica's tree is either held (score =
  its size) or estimated from the sketch overlap with held trees, which is how a node with v1
  ranks warm for v2. The sketch is computed by the agent, which has the chunk lists. The server
  compares sketches only, and that comparison is pure and cheap.

Sizes, under `store_value_bytes_max` (256 KiB): a filter for 64 Ki chunks (64 GiB of distinct
1 MiB chunks) at a 1 % false-positive rate is about 77 KiB. A sketch of K = 64 hashes of 8 bytes,
for each of at most 32 held trees, is 16 KiB. Constants go in `constants.zig` with these
derivations, and the agent refuses to grow beyond them (it advertises the most recently used trees
first and says so in its log).

## How demo-c2 runs

- **Machines.** 3 QEMU guests at start and a fourth added in step 4, each a `zigbox_vm.Session`
  (`start`, `provision`, `run`, `copy_in`, `put_file`, `shutdown`, over the serial console), as
  ops/zigbox-smoke does today. `zcube-server` runs on the host, with a SQLite store (a Postgres
  run is a later option, not the demo). Each guest runs one `zcube-agent --runtime zigbox
  --server 10.0.2.2:<P>`, since user-mode networking puts the host at 10.0.2.2.
- **Peer traffic.** `zigbox_vm` gives each guest one `-netdev user` with no forwards, so guests
  cannot reach each other. Z7 adds `hostfwd` forwards to `zigbox_vm`. Guest *i*'s peer server is
  forwarded from host port H_i, and the agent advertises `10.0.2.2:H_i` as its `/nodes` address, so
  peer traffic goes guest → host → guest. This is honest about the bytes but not about latency.
  `docs/demos/c2.md` must say so, and the stats must count bytes, not time (O4).
- **"Block registry access from VM3 with a host firewall rule."** With user-mode networking, the
  QEMU process makes the guest's outbound connections, so a host rule would have to match that one
  process. The faithful equivalent is a rule inside guest 3 (`nft` drop to the registry's
  addresses, peer port to 10.0.2.2 left open), plus a recorded `curl` to the registry from the
  guest that fails. Whether that counts as the SPEC's "host firewall rule" is O4.
- **Images (O8).** `python-app v1` and `v2` must differ in one source file, and that file must sit
  in its own layer, or step 2 transfers a whole layer from the registry on the first node. Either
  the owner pushes both images to GHCR (public, digest-pinned in the demo's service files), or the
  demo runs a local test registry on the host (Z8, if Zigbox's test registry is exported) and the
  registry bytes are counted against it.
- **Assertions.** Every step is asserted from `zcube stats pull --json` and `zcube why --json`, not
  from transcript text:
  - Step 1: registry bytes on one node only, peer bytes on the other two (requires O5's
    "registry once" rule).
  - Step 2: peer and registry bytes per node under 1 MiB.
  - Step 3: zero registry bytes on node 3, and the replica `running`.
  - Step 4: the chosen node is warm, and the decision names locality.
  - The corrupted-chunk criterion: a test-only fault on one agent (written into its state
    directory, as with today's faults), and the fetching node reports that peer with its code.
- **Step 4, read with the scheduler order (O2).** Locality ranks after spread. A new replica of an
  existing service would go to the empty fourth node, because that node has the fewest replicas of
  the service. That is correct, and SPEC's second criterion requires it. So step 4 must add a
  replica of a **new service on the same image** (or of a service whose spread is equal across
  nodes), so that spread ties and locality decides. The demo document says so.
- **Gate for shipping C2.** As for C1: `demo-c2` green in CI, and the simulation fleet run for 24 h
  on the shipping commit, now with `sim-swarm` seeds.

## Owner questions

- **O1. `/node-store/<node>`, and locality as advisory.**
  - The key: lease-bound, agent writer, at most 256 KiB.
  - The authority.md amendment: the scheduler reads it as evidence, records its revision in the
    decision, and does **not** put it in the placement compare set. A stale summary can make a
    placement slower, never wrong.
  - This adds a key and amends authority (Ask-first).
- **O2. The order: fit → spread → locality → least allocated → name.** Spread before locality is
  what SPEC's criterion says. It also means demo step 4 needs a new service on a shared image (see
  above). Confirm both the order and that reading of step 4.
- **O3. The peer protocol and an unauthenticated chunk server on the node address.**
  - Integrity rests on hashes alone.
  - Confidentiality is not protected. That is acceptable only because images in scope are public.
  - Bandwidth caps per peer and per node are constants.
  - A new listener on every node is an exposure the owner must accept, or require a shared token
    (not in scope here).
- **O4. The demo network.**
  - `hostfwd` in `zigbox_vm` (Z7), and peer traffic through the host.
  - A guest-side `nft` rule accepted as the SPEC's "host firewall rule".
- **O5. "Registry bytes once" with simultaneous starts.**
  - Step 1 places three replicas at once. Without coordination all three pull from the registry.
  - Proposal: among the nodes fetching a tree, the one whose `hash(node name, tree)` is lowest
    pulls from the registry at once. The others wait up to `fetch_peer_wait_ms` (proposed 30 s)
    for a peer's Bloom filter to show the chunks, then fetch from it or fall back.
  - It needs no new key: the agents read each other's `/node-store`, which now changes while a
    fetch is under way. Its write rate is bounded by a constant.
- **O6. Where pull stats live.** `/pulls/<node>/<tree>` (proposed: its own retention, and a stats
  view that needs no join), or a member on `/observed/<node>/<replica>` (no new key, but a
  replica-scoped record for a node-scoped fact).
- **O7. Peers do not travel on `Runtime.Spec`.** The fetch worker reads `/node-store` itself
  through the agent's API, so the `Runtime` contract does not grow for C2 beyond P1 and P2.
  Confirm.
- **O8. The demo images.** GHCR images pushed by the owner (public, digest-pinned), or a local
  test registry (Z8). Either way, the changed source file must be in its own layer.
- **To confirm after slice 2 starts (does not block it).**

## Non-goals

- Private registries, credentials, and image signing beyond digest pinning.
- Chunk dedup across files, content-defined chunking, or any change to Zigbox's store layout.
- A peer protocol for anything but the store: no logs, no exec, no registry-mirror emulation.
- Garbage collection policy for images on nodes beyond what Zigbox's roots already do. Eviction
  that is aware of the summary is C4's or later.
- Rollout and health (C3). A changed image is rolled out exactly as today: replace on a generation
  bump.
- Latency claims. The demo's network goes through the host, so C2 claims bytes, not seconds.
