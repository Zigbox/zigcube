# C2 slice 1 · The real Zigbox runtime

*Owner decision (2026-11-02): the real runtime is C2's first slice and runs in parallel with the rest of C1 (slices 3-8 on other branches). This is an explicit exception to "one milestone at a time"; it is recorded in `docs/DECISIONS.md`. Read `AGENTS.md`, `HANDOFF.md` (Ask-first binds), `DIAGNOSTICS.md`, `docs/STYLE.md`, `REVIEW.md` and `docs/agent.md` first. Written from the code of Zigcube `main` (81314db) and Zigbox `main` (600939c, 0.2.0); nothing here was run on a real Zigbox host (this container is cgroup v1 and root).*

## Goal

`ZigboxRuntime`: a `Runtime` (the existing contract, unchanged) over the linked `zigbox` module, selected by `zcube-agent --runtime zigbox|fake`. `fake` stays the default; every test and demo keeps using it. The runtime starts containers with CPU, memory and pid limits and no network (Zigbox's default, `Network.none`), stops them, lists them, reports why they ended (exited, signaled, `oom`, `pid_limit`, `start_failed`, `lost`), re-adopts running containers after an agent restart without duplicates, and gets the image onto the node.

## (a) Digests, references, and getting the image onto a node

- A Zigcube `image` (`b3:…`) is a Zigbox **store tree digest**: the BLAKE3 digest of the flattened layer tree. `zigbox.Spec.image` takes exactly that (full digest, or a unique prefix of 12 or more hex digits, with or without `b3:`) and runs it on an overlay. `Spec.image` also needs `StartOptions.image_workspace` (about 17 MiB, caller's static or heap storage).
- A tree digest is the **output** of a pull, not something derivable from an OCI reference. `zigbox.pull.pull(host, facts, &request, progress, ws, import_ws, &result, diag)` takes a reference (`ghcr.io/o/r@sha256:…`, or a tag), resolves it for a platform, verifies every blob, unpacks to a tree in the store, writes the image record, and returns `Result{manifest_digest, config_digest, tree, settings}`. `images.load(store, manifest)` finds the record of an already pulled manifest (and so its tree). Zigbox's own docs call "`ensure_image`" this: look in the store, else pull. It is the agent's to write.
- So the service needs both: **an OCI reference pinned by manifest digest** (what to fetch) and the **locked tree digest** (what must come out). The agent pulls, then checks `result.tree == locked`; a mismatch is a refusal (a new `ZC-` code, blamed on the user: the reference no longer yields the locked tree, or the lock was made for another platform). Locking is done once by whoever writes the service (a later `zcube` command or a `zbx pull`; out of scope here).
- **Where the reference lives (decision for the supervisor).** The service record carries only `image`. Putting a reference on it changes `Service`, `Replica`, `Runtime.Spec` and `docs/api.md` (the first three are stored values or the approved contract: Ask-first, see P1). To keep this slice off the contracts, **slice 1 reads the reference from a node-local images file**, the real-runtime counterpart of `fixtures/images.zon`: `--images FILE` (ZON, `.{ .images = .{ .{ .digest = "b3:…", .reference = "ghcr.io/…@sha256:…" } } }`, the old digest-only form still read by `fake`). A digest not in the file and not in the store is `start_failed` with the "image not found" diagnostic, as with `fake`. The file is the operator's, on each node; it holds no intent (REVIEW.md: intent never lives on a node), only a lookup. P1 replaces it.
- **Public registries only.** GHCR is proven in Zigbox M4; ECR Public is **unverified** (not run here, not claimed). Anonymous pulls only; private registries and credentials are out of scope. Registry mirrors/proxy: `Request.mirrors` and the real host read `HTTPS_PROXY`, `NO_PROXY` and `SSL_CERT_FILE` from the environment the agent gives `host`.
- **Pull must not block the agent's lease.** `pull` and `start` both need the calling thread to be the only one in the process (they make namespaces), and a pull of a large image takes minutes while the agent renews its lease in the same thread. Zigcube already puts each container under a `zcube-agent supervise` process (a recorded owner exception). The same process does the work: the supervisor runs `ensure_image` then `zigbox.start`, then `zigbox.wait`, and the agent sees `Status.starting` from `inspect`/`list` until the run record says `running`. `start` returns `.started` as soon as the supervisor is up (a `starting` container is within the contract's `Status`); the failure arrives as `StartOutcome.failed` if it comes within a bounded wait (as `FakeRuntime` waits for `ZC-E0508`), else as `stopped: start_failed` on a later `list`. **To verify in the first step:** that the agent core treats `starting` as "not yet running, not missing" (`agent.zig` `is_running`/`report`); if it does not, a pull-time wait with a bound is the fallback and the lease risk is documented.

## (b) Zigbox version and the pin

- The pin (`90b6f1c`, 2026-10-26, Zigbox 0.0.0) predates everything this slice needs: `zigbox.lifecycle` (`list`, `adopt`, `stop`, `Watcher`), `Spec.image`, `pull`, logs, `Network`, and `ExitReason.oom`/`pid_limit` with their data. **The pin must move.** Proposal: Zigbox `main` at **600939c** (2026-10-30, 0.2.0, `minimum_zig_version` 0.17.0 like ours), the first commit with `pull` in the library (M6b slice 4) and everything before it. Moving it is part of slice 1, as step 1 of the work.
- How: `git archive 600939c | tar` into a clean directory, `tar czf`, `zig fetch <local tarball>` to compute the `.hash` (package fetch over the network does not work here; a local file does), then update `build.zig.zon`, and unpack into `zig-pkg/<hash>` as AGENTS.md says. The `.url` stays the GitHub archive URL of that commit.
- **Expected breakage, found by reading the diff:** `diag/codes.zig` grew by 2,473 lines, `diag.zig`, `diagnostic.zig` and `explain.zig` changed. Zigcube's `src/diag.zig`, its golden files and `errors-site` may need regenerating; the first step is to move the pin on its own and get `zig build check` green, with no other change.
- **A collision:** Zigcube's placeholder `ZBX-E0501` (image not found, `src/runtime_codes.zig`, `docs/runtime-codes.md`) is now a real Zigbox code, with another meaning (an empty or over-long reference to `pull`, `pull.zig`). The placeholder must be renamed or removed in the same step, and the "image not in this node's store" case given the code Zigbox actually raises (the store's "no such tree" diagnostic, `store/diagnose.zig`; its number is to be read from the pinned source, not guessed). This changes a code that appears in `demo-c0` output and goldens, so it is its own commit.

## (c) Gaps between `Runtime` and the `zigbox` module

Every difference, ranked by how much it costs. Items 1-6 need no contract change. P1-P2 are proposals for the owner (Ask-first); I make none of them.

1. **Handle.** Zigbox's `Handle` (about 480 KiB, pinned in place, holds pointers into the `Spec`) cannot be a `Runtime` handle. In the supervisor model it lives in the supervisor process only, which owns the one container; the agent talks to the container by name through `lifecycle.list`/`adopt`/`Ref`, which work from the run records and the kernel in any process. No pool.
2. **Labels and environment are narrower.** Zigbox: at most 8 labels, keys at most 32 bytes, values at most 128; at most 16 `-e` variables (`run_env_count_max`; the image's own variables add to these). Zigcube accepts 16 labels (key 63, value 253) and 64 variables. The adapter refuses a spec that does not fit with a coded `start_failed` (user blame: "the service sets more than 16 variables"), rather than truncating. `apply` is not changed here; narrowing its limits is a decision for the owner (P3: lower `runtime_env_count_max`, `runtime_labels_max`, label sizes to Zigbox's, a breaking tightening of `docs/api.md`).
3. **Exit reasons.** `oom` and `pid_limit` carry data in Zigbox (limit, what PID 1 did); the contract's carry none. Mapped with the data dropped into the diagnostic text. `start_failed: Diag` maps through `zigbox.diagnostic.from_diag`. `lost`: Zigbox's `lost_diag` exists only in the supervising process's `Handle`; a `lifecycle.Entry` of an adopted container says `lost` with no diagnostic, so the agent reports `lost: null` unless the supervisor wrote its reason. OOM/pid-limit attribution depends on the cgroup scope, which needs a user systemd bus (see (d)); without it Zigbox refuses limits.
4. **`stop` and the fence (the C1 slice 6 gap).** `lifecycle.stop(ref, grace_ms, kill_wait_ms)` blocks: SIGTERM, poll every 20 ms up to `grace_ms`, then SIGKILL and up to `kill_wait_ms` (5 s) more. The contract allows `stop` to return early (docs/agent.md, gap 1; the caller checks `inspect`), and `lifecycle.signal(ref, n)` is non-blocking. `ZigboxRuntime.stop` therefore follows `FakeRuntime`: with `grace_ms > 0` send SIGTERM through `signal` and wait at most a short `stop_wait_ms`; with `grace_ms == 0` send SIGKILL through `signal` and wait at most the same short bound; neither waits out a grace. A fence that must stop every container within `fence_stop_ms` (2 s) can then call `stop(handle, 0)` on all containers in turn and each call costs at most `stop_wait_ms`, not `kill_wait_ms`. The bound must be chosen so that N containers still fit: **for N containers the total is N times `stop_wait_ms`**, so the real fix is P2.
   - **P2 (Ask-first, proposal):** add a non-blocking `Runtime.signal(handle, number)` (or `stop_begin`) to the vtable, so the fence signals everything first and then polls `inspect` against one deadline. Cost: a new vtable entry in `Runtime`, `FakeRuntime`, `SimRuntime` and the agent core. Until approved, the adapter uses the bounded-wait behaviour above and the gap stays documented, not hidden.
5. **Events.** `Watcher.poll(host, watcher, scratch, out)` reports started/stopped/lost between looks and does not wait: the adapter sleeps and polls up to `timeout_ms`, bounded by `constants.events_poll_ms_max`. Events stay a hint; `list` is the truth.
6. **Listing has no start time** (docs/agent.md, gap 2). The run record has `started`; unchanged (no contract change).
7. **Image defaults.** `Result.settings` and `run_image.zig` compose the image's entrypoint, cmd, environment, working directory and user the way `zbx run` does. Zigcube's `Spec.command` is mandatory and replaces the image's; the adapter must still take the image's working directory, user and environment (service `env` wins). Not in the contract; to be verified against `run_image.zig` in the first step and tested.
8. **P1 (Ask-first, proposal): the reference travels with the service.** Add `source` (an OCI reference) beside `image` in `Service`, `Replica` and `Runtime.Spec`, and `docs/api.md`/`docs/keys.md`; additive JSON, value versions bumped (REVIEW.md), `apply` validates both and that the reference is digest-pinned. Removes the node-local images file. Needed before C2's peer fetch in any case.

## (d) Host requirements and real validation

Zigbox runs rootless. A host needs (from Zigbox's `doctor.zig` and `docs/demos/m0.md`/`m1.md`/`m2.md`):

- Linux 5.15 or newer (overlayfs in user namespaces).
- cgroup v2 with the `cpu`, `memory` and `pids` controllers delegated to the user, and **a systemd user manager with a session bus**: Zigbox asks it for a scope per container. A user manager needs a login session or **lingering** (`loginctl enable-linger <user>`). Without a bus, a run with limit flags is refused (m2.md); this container (cgroup v1, root, no user bus) can run none of this.
- `uidmap` (setuid `newuidmap`/`newgidmap`) and a `/etc/subuid` and `/etc/subgid` range for the user (e.g. `100000:65536`).
- **Ubuntu 24.04:** `kernel.apparmor_restrict_unprivileged_userns=1` is the default and fails Zigbox's doctor (`ZBX-E0101`); set it to 0 (`/etc/sysctl.d/60-zigbox-userns.conf`). Zigbox ships no AppArmor profile.
- `passt` (`pasta`) only for `--net user`/`--publish`; this slice uses `Network.none`, so it is not needed.
- `zcube-agent` must not be setuid and must run as that user, not root.

**Validation (the cheapest real one).** Zigbox's own CI never runs containers on the GitHub runner: each demo job boots a pinned Ubuntu 24.04 cloud image under QEMU/KVM (`zig build demo-mN -Daccel=kvm`, harness in `src/testing/vm/*`, guest provisioned by cloud-init with user `demo` (no sudo), subuid, `uidmap`, the AppArmor sysctl, lingering). The runner needs `qemu-system-x86 qemu-utils` and a udev rule for `/dev/kvm`, installed with `sudo` **on the CI runner only**.

Proposal, in two parts, cheapest first:

1. **Reuse Zigbox's harness (recommended).** Build the guest as Zigbox does and run, inside the VM as `demo`, a Zigcube smoke: `zcube-server` (SQLite) + `zcube-agent --runtime zigbox` + the `zcube` CLI, against a public image (an Alpine tag pinned by digest, pulled from GHCR or through `mirror.gcr.io` as Zigbox's m4-m6 jobs do). The harness code is Zigbox's; Zigcube would need either a dependency on it (not today: `zigbox` is imported as a module only, and `src/testing/vm` is not exported) or a copy. **Open question for the supervisor:** may Zigcube vendor a trimmed copy of Zigbox's `vm/cloud_init.zig` and `harness.zig` (Apache 2.0, same owner), or should Zigbox export the harness as a module? Either is a cross-repo decision; I start with the first.
2. **Direct on the runner.** `ubuntu-24.04` GitHub runners have systemd, cgroup v2 and a user, but not lingering, not the sysctl, and no subuid range for `runner`; making them so needs `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, `sudo loginctl enable-linger runner`, an `/etc/subuid` line and a Delegate drop-in with a manager restart. It is cheaper to write and it may work, but it is the less certain path (Zigbox chose the VM, and its m2 notes say the user manager and delegation are the fragile parts). I would try it **once, in a throwaway CI job on a branch**, before committing to the VM, and keep it only if it is stable over several runs.

Either way: a new CI job `zigbox-smoke` (not in `zig build check`; like `agent-smoke` and `demo-c0` it is CI-only), a `zig build zigbox-smoke` step that **skips with a printed reason** unless `ZCUBE_REAL_HOST=1` (so `zig build test` stays hermetic), and nothing that needs sudo on a developer host. Per AGENTS.md, a pass of this smoke is a check, not `demo-c2`, and is never reported as a demo.

## (e) Steps, tests, smoke, non-goals, mechanical parts

**Steps (one commit each, each ends with `zig build check` green):**

1. **Move the pin** to Zigbox 600939c; fix only what the move breaks (diag registry, goldens, errors pages). Rename the `ZBX-E0501` placeholder and give "image not found" the code Zigbox raises (own commit).
2. **Pure mapping** in new `src/zigbox_map.zig`: `Spec` to `zigbox.Spec`, `ExitReason`/`Status`/`Entry` to ours, `Diag` to `Diagnostic`, the narrower-limits refusal, label/env bounds. Table tests for every `ExitReason` variant and bound.
3. **`ZigboxRuntime`** in new `src/zigbox_runtime.zig` (`list`/`inspect`/`events` over `lifecycle`, `stop` as in (c).4). Tests over `zigbox.host_sim` (Zigbox's simulated kernel, the same seam its own tests use) wherever it supports the call; a runtime that cannot be simulated is covered only by step 6, and the brief says which.
4. **Supervisor mode for Zigbox** in new `src/zigbox_supervisor.zig`: `zcube-agent supervise-zigbox`: `ensure_image` (store look-up, else `pull`, tree check against the locked digest), `zigbox.start` with `detached`, `wait`. `ensure_image` also in a separate file with its table tests (pull reports through a fake `Progress`).
5. **Wiring:** `--runtime zigbox|fake`, `--images` accepting the reference form, `docs/agent.md` section, `--help`, goldens, new `ZC-` codes registered with error pages (tree mismatch, no user bus for limits, unsupported host). The only edits to files C1 is changing are in `zcube_agent.zig`/`agent_config.zig` (flag and config) and `agent_run.zig` (select the runtime): a few lines each. No change to `agent.zig`, `agent_api.zig`, `sim_*.zig` or `server_drive.zig` unless (c).2's `starting` check shows a bug (then reported, not fixed here, unless trivial).
6. **Real smoke** `zigbox-smoke` on the host chosen in (d): start a service of 2 replicas on an Alpine image with `memory_bytes` and `pids` set, assert limits in the container's cgroup, `kill -9` of one container's PID 1 is replaced, an agent restart re-adopts both (no duplicates, by name and pid), a container that allocates past its limit ends as `oom`, one that forks past `pids` as `pid_limit`, `stop` with a 5 s grace on a process that ignores SIGTERM ends within the bounds of (c).4, an image missing from the file is held with the "image not found" diagnostic, network is `none` (`ip link` shows only `lo`).

**Tests (also in `zig build test`, hermetic):** mapping tables; `ensure_image` decisions (in store, pull, tree mismatch, bad reference, no file entry); the images file parser (both forms, bad text, bounds); `stop` bounds; config/`--runtime` parsing and refusal of `zigbox` on a platform without the module's host; the default stays `fake` (a test asserts it). `zig build agent-smoke` and every `demo-cN` keep running on `fake` unchanged.

**Non-goals:** scheduler changes; networking (`Network.none` only; no `user`/`host`, no `--publish`); registry credentials or private registries; C2 peer fetch, locality, `zcube stats pull`; the reference on the service (P1); a `Runtime` or `Store` change of any kind; macOS; exec/logs endpoints (the run record keeps logs; nothing reads them yet); stateful volumes; marking anything "demonstrated".

**Mechanical parts for Haiku** (exact pattern, diff checked by me): updating `build.zig.zon` after the hash is computed; regenerating goldens and error pages after the pin move; adding the new `ZC-` codes' error-page text from a template once the codes are named; the `docs/agent.md` flag table and `--help` text; the CI job skeleton copied from Zigbox's `demo-m2`.

**Gates for the report:** `zig build check` PASS on the reported commit (no `+dirty`), `zig build agent-smoke`, and the `zigbox-smoke` result from the chosen real host, or an explicit statement that it was not run and why.

## Risks I could not settle from here

- The pinned-source numbers: whether Zigbox's `Handle` plus pull and image workspaces fit in a supervisor's memory budget (about 480 KiB + 15 MiB + 17 MiB + the doctor's facts: fine for one container per process, to measure).
- Whether `host_sim` simulates enough of `lifecycle` and `start` for step 3's tests.
- Whether limits work on the chosen validation host (delegation), which decides whether (d).2 is viable.
- Zigbox's `README` lists six doctor checks and the source seven; the source was followed.
