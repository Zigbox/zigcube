# C1 slice 1 · `zig build check`

*Brief written 2026-10-30 by the supervisor. One implementer session. It does not depend on the rest of C1's brief (`docs/briefs/c1.md`), which the owner is still settling.*

## Goal

One command runs every gate a slice must pass and ends in one line a report can quote:

```
check: PASS 1a2b3c4d5e6f (build test tidy errors-site wasm-check wasm-test console-wasm store:memory,sqlite sim-c0, test as tester)
check: FAIL 1a2b3c4d5e6f (zig build test as tester)
```

From the next slice on, `AGENTS.md`'s gate list is this one command.

## Port, don't invent

Zigbox has this already: `src/testing/check.zig` and `add_check_step` in its `build.zig` (repo `Zigbox/zigbox`, branch `main`; read them with the GitHub tools or a shallow clone). Port it and keep its shape: the cheap gates as build-step dependencies of a host tool that runs last, then the gates a dependency cannot express, then the one line. Same `+dirty` rule, same cache note, same `-Dcheck-user=<user>|-` option with `tester` as default, same scratch-worktree run as an ordinary user. Put it at `src/testing/check.zig` here too (create `src/testing/`), and register the new file with `tidy`'s scope as the other build-host tools are.

## What it runs

As build-step dependencies (any failure stops before the tool runs):

- `install` (the three executables), `test`, `tidy`, `errors-site-check`;
- `wasm-check`, `wasm-test`, `console-wasm`;
- `test-store` on `memory` and `sqlite`. `test-store` takes `-Dbackend` as one option today; give `check` its own run of the conformance suite per backend rather than a second `zig build` invocation, if the build graph allows. If it does not, run them from the tool and say why in the handoff note.

From the tool, in order:

1. `test-store -Dbackend=postgres` only when `ZCUBE_TEST_POSTGRES` is set; the PASS line names the backends that ran (`store:memory,sqlite,postgres`). Unset is not a failure.
2. `sim-c0` with a fresh seed (native against WASM, as CI's second sim step does, `-Dops=200 -Doptimize=ReleaseSafe`). Print `sim-c0: seed N` before it, so a FAIL's seed is the last such line, as Zigbox does for its fuzzers.
3. As root, unless `-Dcheck-user=-`: `zig build test` as that user in a scratch worktree of HEAD under `.zig-cache/`, with its own `ZIG_GLOBAL_CACHE_DIR` and `HOME`. `zig build test` installs `zcube-agent` first and the `FakeRuntime` tests start real processes, so check that the run as the user really starts them (not skips them) and that nothing is left running afterwards (`pkill -9 -f '[z]cube-agent supervise'` is the fallback, never the plan).

If the user does not exist, fail with one line that says so and how to fix it (`useradd -m tester`, or `-Dcheck-user=-`), not a `runuser` message. This container has no `tester`: create one to test the real path.

Not in `check`: `agent-smoke` and `demo-c0` (CI runs them; they are slow and start servers). Say so in `check`'s doc comment.

## Done when

- `zig build check` prints `check: PASS <commit>` on the reported commit, as root with `tester`, and once with `ZCUBE_TEST_POSTGRES` set against `zig build pg-up` (then `pg-down`).
- Each failure path seen once and its line pasted in the report: a broken test, a tidy violation, a failing sim seed (force one locally, do not commit it), a missing user. Each says what failed in one line.
- `AGENTS.md`: the **Commands** list gains `zig build check`, and the implementer section's gate list becomes "`zig build check` on the commit you report; paste its last line". `REVIEW.md`'s "gates run on the exact commit" item points at it. `docs/DECISIONS.md` gets a line.
- CI is **not** changed in this slice: CI keeps its separate jobs.
