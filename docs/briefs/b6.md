## Goal

A job can say which nodes it may run on, and a node can be reserved for one tenant:

- `placement = { "require": { "tenant": "acme" } }` makes only the nodes that carry every listed
  label candidates.
- A node labelled `exclusive = "tenant"` takes only jobs whose `require` names that node's own
  `tenant` value.
- When nothing matches, the job stays `pending` with the reason. It never starts somewhere else.

## Fixed decisions

- **Where labels come from.** Node labels come from the agent's own configuration, at
  registration (at most 8, as today). No API call sets or changes them. A node's label change
  is a re-registration, and that is a new tenure.
- **The job field.**
  - `placement.require` is an object of label key to value: at most `job_require_max = 4`
    entries, under the label key and value bounds.
  - B6 adds nothing else to `placement`. Any other member is ZC-E0130.
  - `placement` stays refused for services, with ZC-E0130 naming it. (Slice 1 review: on `main`
    `POST /v1/apply` never parsed `placement`, so a service with it is refused with ZC-E0104,
    the current behaviour; no new E0130 path was built.) Services gain
    `placement` in C-milestone work, not here.
- **The filter.** It runs before fit. The order becomes require/exclusive → fit → spread →
  locality → least allocated → name. A node is a candidate for a job only when both hold:
  - it carries every `require` pair;
  - if it has an `exclusive = K` label, the job's `require` names `K` with the node's own value
    of `K`.

  A node whose `exclusive` names a key it does not itself carry is refused at registration
  (ZC-E0130 is the API code; use the registration refusal the agent API already has).
- **Services and exclusive nodes.** A replica of a service has no `require`, so it never lands
  on an exclusive node. Today no node is exclusive, so nothing that runs now changes.
- **Pending with a reason.** The scheduler's decision for an unplaceable job names the
  constraint, for example: `no ready node has tenant=acme`, or `node3 is exclusive to
  tenant=beta`. `zcube why job` shows it.
- **Authority.** The placement compare set already covers `/nodes/<n>`, so a relabel that races
  a placement makes the placement fail and be planned again.

## Slices

1. **The field and the filter, as core code.**
   - `placement.require` parsed and stored.
   - The `exclusive` check at registration.
   - The filter in the scheduler, and the reason text.
   - Tests:
     - `require` matches a node;
     - `require` matches no node, so the job stays pending with the reason;
     - an exclusive node takes a job of its own tenant;
     - an exclusive node refuses a job with no `require`;
     - an exclusive node refuses a job of another tenant;
     - a service never lands on an exclusive node.
   - Each rule has a teeth test.
   - Update `docs/api.md`, `docs/keys.md` and `docs/scheduler.md`, or wherever the order is
     documented.
2. **Simulation.**
   - The cluster simulation gives nodes seeded tenant labels, some of them exclusive.
   - Jobs carry seeded `require`.
   - New check P1, at every revision: no assignment puts a job on a node that fails its
     `require`, and no exclusive node holds a job of another tenant or a service. This must
     hold across node loss, re-registration with other labels, and partitions.
   - A tooth skips the exclusive check.
   - `sim-c1` runs it, and the fleet picks it up.
3. **The demo.**
   - Carried from slice 1's review: `zcube-agent` has no flag or config field to send node
     labels, so the `exclusive` check is reachable only through a raw
     `PUT /v1/agent/nodes/<n>`. The demo's labelled agents need one (a user-visible addition the
     brief does not list): the supervisor decides whether it lands in slice 2 or 3.
   - `demo-b6` runs over the fake runtime, like `demo-c1`, with three agents: two labelled
     `tenant=a` (one of them exclusive) and one labelled `tenant=b`.
   - Jobs for `a` land only on `a` nodes.
   - A job with no `require` never lands on the exclusive node.
   - A job for tenant `c` stays pending, and `zcube why job` says why.
   - Power off an `a` node. Its job ends `node_lost`, and no `a` job ever lands on the `b` node.
   - It needs no KVM.

## Non-goals

- `placement` on services.
- Anti-affinity.
- Preferences: weights, or "prefer" instead of "require".
- Taints and tolerations beyond `exclusive`.
- Labels set through the API.
- Tenant quotas.
- Tenant isolation on shared nodes (CS3, after Zigbox's microVM work).
