# B1 slice 1: what the later slices need to know

*Written with the review fixes of PR #98. The design is `docs/briefs/b1.md`; this is the part of
slice 1 that the brief's slice table asks for (the readers of `Assigned.service`) and the notes
that slices 2 to 4 start from.*

## Readers of `Assigned.service`

A run's assignment (`Assigned` version 2) has an empty `service` and a `job`. The scheduler writes
runs only in slice 3, so today nothing reads one; every reader below is checked now, because
slice 3 puts runs under `/assigned/` beside the replicas. Replica assignments are written by
`records.assigned_replica` at version 1; a run by `records.assigned_run` at version 2; `read`
refuses a record that has a `job` and a `service`, neither, a `job` below version 2, or a replica
that is not `<job>-job`.

| Where | What it does with the record | Verdict for a run |
|---|---|---|
| `scheduler.zig:351` (`world` from `/assigned/`) | copies `service` into `Assign` | **Safe.** `service` is `""`; no service has an empty name (`name_problem`). Slice 3 must give the `Assign` its `job` so the per-node job count (`jobs_per_node_max`) can use it. |
| `scheduler.zig:399` (spread count) | counts assignments whose `service` equals the replica's service | **Safe.** `""` never equals a service name, so a run is never counted toward a service's spread. |
| `agent.zig:681` (wanted set) | keeps `replica` ids of the node's assignments | **Needs slice 4.** The ids of runs enter the wanted set (gap 8 of the brief) so that `orphan_containers` leaves them alone. Reads no `service`. |
| `agent_api.zig:355` (`GET …/replicas`) | serves the replicas whose id is in the assignments | **Safe.** A run id matches no `/replicas/` record, so it is not served there; runs have their own route (slice 4). |
| `agent_api.zig:385` (`GET …/assignments`) | serves every assignment of the node as stored | **Safe, and slice 4 must check.** An agent of the previous release reads a version 2 record as too new (ZC-E0303) and so stops reading that node's assignments (the mixed-version test in `records.zig` pins this). The brief does not say how a rolling upgrade avoids it; slice 3 must, or state that B1 needs every agent upgraded before the first job. |
| `allocations.zig:65` (rebuild tallies) | sums `requests` per node | **Safe.** Runs count in the allocation like replicas (brief, "Settled here"). |
| `controller.zig:296` (`assigned_of`) | the assignment of a replica id, by key | **Safe.** Looked up by replica id; a run id is never asked for. |
| `controller.zig:389` (snapshot) | `replica → node` map | **Safe.** A run id is an unused key in it. |
| `sim_c0.zig:956` | moves the first assignment to another node | **Safe for C0** (no jobs there); a test that moves a run must move the whole record. |
| `sim_c1.zig:53` (I1a) | each replica id has at most one assignment | **Safe, extends to runs unchanged** (authority.md §7: I1a holds for runs). |
| `sim_checks.zig:105` | placements since a revision | **Safe.** Reads revisions and keys, not `service`. |
| `sim_cluster.zig:1779` (`read_homes`) | replica → node | **Safe.** Same as the snapshot. |

**A bound to fix in slice 3.** Every one of these lists `/assigned/` with `constants.replicas_max`
(512) as the limit, and `list_all` fails (ZC-E0302) over it. With runs under the same prefix the
count is replicas plus runs, so slice 3 must list with `replicas_max + jobs_max` and assert it
against the store's limits, or the first cluster with 300 replicas and 300 jobs cannot reconcile.
`agent_api.zig`'s per-node list uses `agent_node_replicas_max` and has the same problem for
`jobs_per_node_max` runs.

## For slice 2 (API)

- **Run record size.** `records.encode` refuses a `JobRun` over `job_run_bytes_max` (16 KiB) as
  ZC-B0005 (our defect: it got past the API) and `read` calls one malformed, after the version
  check (a newer, larger record is ZC-E0303). The API must still refuse a job whose run would not
  encode as ZC-E0130 naming the field, so B0005 is never reached. Measure the escaped size of
  `command` and `env`, not their raw size.
- **Input wire size** is an open owner question:
  `docs/decisions/2026-11-05-b1-job-input-wire-size.md`. The route's body limit waits for it.
- `Job.grace_ms` and `JobRun.grace_ms` are `u32`, as `job_grace_ms_max` and `Runtime.stop`.

## For slice 3 (controller and scheduler)

- **Never create a second run of a job that had one.** Step 1 ("create the run and status when a
  job has none") means *never had*. An operator who deletes `/job-runs/<name>` and
  `/job-status/<name>` to "fix" a contradiction (as ZC-E0307 used to say) would otherwise run the
  job again and break I8a. Such a job is ZC-E0307 and nothing changes. The controller knows the job
  had a run by its `job-created` decision (the owner chose option A), with the conditions and
  negative tests in `docs/decisions/2026-11-05-b1-controller-never-recreates-a-run.md`. The E0307 text,
  authority.md §7 and the brief's step 1 already say it.
- Place runs with `records.assigned_run`; every replica placement already goes through
  `records.assigned_replica`.
- The `/assigned/` listing bound, above.
- `JobObserved` and `JobStatus` have `valid()` checks that `read` enforces; the controller can
  rely on them and must not repeat them.
- Retention deletes a job's five records in one transaction that `writers.retention_only` allows
  (one job, at most one node, no pull records), and the transaction must compare the terminal
  `/job-status/` and delete `/jobs/<name>` with it (authority.md §7). `writers` refuses a
  retention transaction that deletes a run or status without the spec.
