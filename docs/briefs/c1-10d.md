# C1 slice 10d · Failover (implementer's plan)

*Written 2026-11-02 by the 10d implementer, from `docs/briefs/c1-10.md` (10d) and `c1.md`'s rows
"Supported Postgres setup" and "The store never goes backwards". Where this and those disagree,
those win.*

## What

- **`pg_dev` makes a pair.** `pg_dev pair-up sync|async` starts a primary and a streaming standby
  on one machine (two data directories under `ZCUBE_PG_PAIR_DIR`, default `/tmp/zcube-pg-pair`;
  ports `ZCUBE_PG_PAIR_PORT`, default 55433, and the next one), the standby made with
  `pg_basebackup -R` and `application_name=zcube_standby`. `sync` starts the primary with
  `synchronous_commit = remote_apply` and `synchronous_standby_names = zcube_standby`; `async`
  with neither. `pair-crash` stops the primary with `pg_ctl -m immediate` (no shutdown
  checkpoint, no WAL flushed to anyone: a crash); `pair-promote` promotes the standby
  (`pg_ctl promote -w`); `pair-down` stops both and deletes the directory. A pair-up first removes
  any pair left by an earlier run. `zig build pg-pair-down` cleans up after a killed run.
- **The failover runs** (`src/store_failover.zig`, shell), two per `test-store-faults
  -Dbackend=postgres`, one `sync`, one `async`, with the run's seed. Each:
  1. makes a fresh pair, and routes the standby's replication through a fault proxy `R` of its
     own (`ALTER SYSTEM SET primary_conninfo` on the standby, reload; it waits until
     `pg_stat_wal_receiver.sender_port` is `R`'s port and, for `sync`, the primary reports the
     standby `sync`);
  2. creates the store (schema `zcube`) on the primary, waits until the standby replayed it, and
     starts a real `zcube-server` on it with a `--state-dir`, its store reached through the client
     proxy `C`;
  3. runs 10c's clients and watcher through `C`, with the history recorder, paced so the load
     lasts a few seconds;
  4. at a quarter of the load: `async` partitions `R` (the standby stops hearing the primary) and
     reads the primary's revision; both then wait until the server remembers a revision past that
     point (polling `GET /v1/status`, `store.remembered`) and its file is saved;
  5. fails over mid-load: `C` goes black-hole (new connections hang, as when the address of a dead
     primary answers nothing), `pair-crash`, `pair-promote`, `C` repointed at the standby, `heal`
     (which resets the swallowed connections, so clients reconnect at once). Clients and server
     reconnect through `C` without being told: a libpq multi-host string was the alternative, but
     the repointed proxy makes the moment of switch the test's, not libpq's.
- **Sync verdict:** the clients finish on the promoted standby; the history checker passes over the
  whole run (every acknowledged write is in the new primary's log, every unknown wholly in or
  absent, compare-and-set linearizable across the switch); the server answers `GET /v1/status`
  with `store.ok` true and a remembered revision at least the pre-failover one: the positive
  control for the teeth test.
- **Async verdict (the teeth test):** the clients stop at the failover. The new primary's revision
  is below the one the server remembered (asserted: this is what makes the loss certain, not
  lucky); the server's `GET /v1/status` answers `store.ok` false with `ZC-E0215` naming both
  revisions; `POST /v1/apply` is refused with `ZC-E0215`; a restarted server starts halted with
  the same diagnostic; and the history checker, run over the promoted store's log, reports the
  lost acknowledged writes.

## How the async loss is made certain

`R` is partitioned before the failover, so no WAL after that point reaches the standby, whatever
the timing. The test then waits until the server has *seen* a revision at least 20 past the
primary's revision at the partition, so writes the standby cannot have were acknowledged and
observed. After promotion the test reads the promoted store's revision and fails the run as
"not certain" if it is not below the server's remembered one. No timing luck is involved.

## CI cost

The `store-faults` job already builds the store; the failover runs add `zcube-server` to its build
and two runs of about 10 s each (pair-up about 2 s, load about 3 s, server start and checks). The
standby pair is two local Postgres 16 processes run by `pg_dev` with the runner's preinstalled
`/usr/lib/postgresql/16/bin` (installed with apt if absent); the service container stays for
10c's run, since a container cannot easily be one half of a streaming pair with a proxy between.

## Non-goals

The daily run in the simulation fleet (slice 9's branch: follow-up). Reads from the standby,
logical replication, poolers, OrioleDB. Automatic failover or a multi-host connection string in
the server. The random fault schedule of 10c during the failover runs (the failover is the fault;
10c's run keeps the schedule). Recovery after the halt (`accept-rollback` is 10b's, tested there).
No `Store` or `Runtime` contract change.
