## Goal

A `job` object beside `service`: run one task to completion on one node, report how it ended,
and never start it twice. The cluster guarantees that a job's run is started at most once, ever,
and that an ended job never starts again. Botpike's use: one job per agent run, `retries` 0, the
ending read through a watch that is gap-free within the store's history and backed by a list.

## Non-goals

- Retries above 0 (the field exists, a value above 0 is refused: ZC-E0130; C8 builds retry with
  its own idempotency story). Botpike sends 0.
- Gang scheduling, builds (M7), the shared build cache (C8).
- `relay`, `placement`, identity and signed images (B2 to B6). B1 stores the `relay` and
  `placement` fields as absent and refuses them if sent (ZC-E0130, "not built yet"): a field
  that is accepted and ignored is a lie about isolation.
- Cron and recurring jobs. Job dependencies. Streaming logs.
- Authentication of the API (docs/api.md:232: writes are unauthenticated until auth exists). Jobs
  are no different; listen on a private address. **A job's `env` and input are readable by
  anyone who can reach the server** (the agent endpoints that serve them are unauthenticated too)
  until mTLS (`mtls-client.md`) and B3 bring identity. Question 12.

   expects a workload job (`src/constants.zig:591`, the leaf's life is "the job's deadline bound";
   `:595`, a commonName "a job name": good for B3). None is a workload job.
2. **The replica controller does the wrong thing for a job.** It replaces an exited replica,
   replaces a replica on a lost node under a new id, and holds a user-blame start failure
   (`src/replica_controller.zig:13-26`). A job must do none of the first two. So a job cannot be a
   replica of a one-replica service. It needs its own desired and status records and its own
   controller. It reuses the scheduler's `/assigned` + `/allocations` path unchanged in ownership:
   the scheduler places a run and releases it, so I6/I7 apply to runs as they are.
3. **`deadline` is not a runtime concept.** `ExitReason` has no deadline. The agent must enforce it.
4. **`pids` is in `Runtime.Limits` but not in `records.Limits`** (`src/records.zig`, `Limits`). The
   input's `pid_limit` cause cannot be configured until the record gains it. Jobs' own record has it;
   services stay as they are.
5. **There is no log facility.** `Runtime` has no way to read output. Under `FakeRuntime` the
   container's own stdout and stderr go to `.ignore` (`src/fake_supervisor.zig:216`); the

   stdio, not the job's. Under the Zigbox runtime the container is started through the `zigbox`
   module from `src/zigbox_supervisor.zig`, and where its output goes is Zigbox's; the only log
   file Zigcube writes is a fetch's `fetch.log` (`src/agent_records.zig:54`). Zigbox's `zbx logs`
   (5 MiB per container, per the input) is not reachable through the `zigbox` module as
   `src/zigbox_runtime.zig` uses it. Reading output through `Runtime` is a change to the
   interface: **Ask-first** (HANDOFF; AGENTS.md says the agent's `Runtime` follows what `zigbox`
   exposes). See question 4.
6. **The API has no typed view of jobs and `/v1/why` has no `job` subject.** Both are added.
7. **Names.** Replica ids are `<service>-<n>`, `n` decimal (`src/replica_controller.zig:645`;
   keys.md:117). Container names follow Zigbox's rule, a hostname label of at most 63 bytes
   (`src/runtime.zig:40-43`, `name_problem` at `:266`), and the agent names a container by its id
   and labels it `zcube.replica` with it (`src/agent.zig:907`). So a run id must be a valid
   container name (`job.<name>`, revision 1's choice, is not: `.` is refused) and must never equal
   a replica id. B1's run id is **`<name>-job`**: the last segment is not decimal, so it is never

8. **The agent stops what it does not want.** `orphan_containers` stops every running container

9. **`Assigned` names a `service`** (`src/records.zig:429-435`, v1) and its readers use it: the

10. **The agent endpoints do not page** (`src/constants.zig:268-270`, asserted at `:743`): a list

11. **The HTTP body limit is 64 KiB** (`http_body_bytes_max` = `api_request_bytes_max`,

Where the input and the code disagree (all followed as the code says):

- **"`node_lost` once the node's lease expires."** The server learns of loss at expiry, plus
  `lost_grace_ms` (`constants.zig:139`), and only if the node does not register again first: a
  fenced agent registers again at once under a new tenure, and the node controller then records the
  old tenure `lost` only if its lease had ended (`src/node_controller.zig:9-14`). B1 therefore
  judges loss by the **run's tenure** (Design, "Node loss"), not by a `lost` status. An ending
  written then is safe only because the agent fenced itself first, the same bound as I1b; a *wedged*
  node breaks it, as for services. The two are separate endings (question 6, answered): `failed
  fenced` when the agent comes back and reports it stopped the run, `failed unreachable` when it
  only stopped being heard (never "has stopped").
- **A partition kills jobs.** The agent fences at `s + ttl - fence_margin` (7 s at the defaults,
  5 s with demo-c1's `--lease-ttl-ms 8000`): a network partition that long stops every job on the
  node, and the job ends `failed fenced` (`failed unreachable` if the agent does not come back
  before lease expiry and grace). The input does not say this. Question 10.
- **`exited` carries "the exit code".** A process killed by a signal has no code. `exited` carries
  `code` or `signal`, exactly one.
- **`limits` "as `Runtime.Spec`".** The record's `Limits` has no `pids` (gap 4).
- **`labels`.** `Runtime.Spec.labels` is `runtime_labels_max` (8) pairs, key 32 B, value 128 B
  (`constants.zig:96,99-100`); input's `run`, `org` fit, with one pair taken by `zcube.replica`
  and one by `zcube.job`, so a job may set 6. The input cites `src/agent_api.zig:680` for node
  labels; the constant is at `:683`. The input cites `docs/api.md:231` for unauthenticated
  writes; it is `:232`. Both are off by a few lines, not in substance.
- **`env`, up to 64 KiB in Botpike's RT-Z1 (`BOTPIKE_INPUT`).** Three limits refuse it: a 64 KiB
  value cannot be POSTed beside the rest of the spec (gap 11); a value in the spec is stored twice
  (in `/jobs` and in the run the agent reads); and the agent's list of a node's runs is one
  unpaged page (gap 10), so 64 runs of 64 KiB each is already 4 MiB, the whole page, before any
  other field. B1 moves the input to its own record, `/job-input/<name>`, written once by the API
  and read only by the agent, one run at a time (Design, "Input"); `env` proper is capped at
  `job_env_bytes_max` 8 KiB. Question 5.
- **"Placed → running" as states.** Placement is the scheduler's `/assigned`, not a job state the
  job controller decides, but `zcube why` reads it as the `placed` step. The states below are
  derived, and the stored status has fewer values.
- **"Exactly once" through the watch.** The watch is gap-free only within the store's retained
  history: `server_compact_keep_revisions` (1000 revisions, `constants.zig:239`). A job costs
  about ten revisions (job, run and status, placement, `placed`, claim, `running`, exit,
  ending, release), so the horizon is about 100 jobs' worth of cluster activity, minutes at
  Botpike's rate, not job retention's 24 h. B1 states the contract as watch, then on 410 list and
  deduplicate (Design, "The watch").
- **O3 to O5** are listed open in the input's questions; the owner has answered O1 and O2 only.
  Nothing in B1 reads them.

## Design

### Keys (additions to keys.md)

| Prefix | Writer | Content |
|---|---|---|
| `/jobs/<name>` | API | Desired: the immutable spec (v1): `image`, `source`, `command`, `env` (≤ 8 KiB), `limits` (cpu, memory, pids), `deadline_ms`, `retries` (0), `labels`, `grace_ms`, `input_env` (the variable the input is given in, or absent), `input_digest` and `input_bytes` (or absent), `submit_by_ms`, `created_at_ms`, `applied_by`; and mutable `cancel_requested` (null or `{at_ms, by}`). |
| `/job-input/<name>` | API | The input, at most `job_input_bytes_max` (64 KiB), written in the same transaction as `/jobs/<name>` and never changed. Read only through the agent endpoint for the node the run is assigned to. Deleted by retention once the job has ended. |
| `/job-admission` | API | Aggregate: `admitted` (jobs ever created) and hourly counts of creations over `job_admission_window_h` hours. Rewritten by every create, which compares it. |
| `/job-runs/<name>` | job controller | The run: id `<name>-job`, a copy of the spec the agent needs (without the input), `start_by_ms`, and `stop` (null or `{cause: cancel|unreachable|not_started, at_ms}`). Created once; `stop` set at most once; deleted by retention. |
| `/job-status/<name>` | job controller | `state` (below), `node`, `epoch`, `tenure`, `started_at_ms`, `ended_at_ms`, `end` (`exited{code|signal}`, `failed{cause}`, `cancelled`), `stop_cause`, `diagnostic` (a `ZC-` code and sentence when failed), `decision` (the id of the last decision), `reported_at_ms`. Terminal states are written once. |
| `/job-endings` | job controller | Aggregate: `ended` (terminal statuses ever written). Rewritten by every terminal write, which compares it. |
| `/job-observed/<node>/<name>` | that node's agent | Its own record kind, `JobObserved` v1 (not the replica `Observed`, which is v2: `src/records.zig:411-424`): `run`, `node`, `tenure`, `assignment`, `status` (`claimed`, `running`, `stopped`), `exit`, `stop_cause`, `diagnostic`, `started_at_ms`. Admissible under authority.md's three conditions. |
| `/assigned/<node>/<name>-job` | scheduler | Assigned v2: a `job` member (the job name) and `service` empty; every reader of `service` (gap 9) takes the `job` branch. Epoch = its `mod_revision`. |

`/decisions` and `/decision-summaries` take a new subject kind `job`; `decisions_per_subject_max`
(200) is far more than a job needs, so a job never compacts its own chain while it lives. The
scheduler writes `placed` / `unschedulable` / `released` decisions with `job` as the subject.

### States

```
pending ─► placed ─► running ─► exited | failed | cancelled
   │          │                       ▲
   └──────────┴── stop (cancel, not_started, unreachable before a claim) ─┘
```

`pending`: no assignment. `placed`: assigned, not yet claimed. `running`: an admissible claim or
report. The job controller stores `placed` (from the `/assigned` it watched, so a client sees it
without listing `/assigned`). A job that fits no node, or whose node is at
`jobs_per_node_max`, stays `pending` with the reason in `why` (the scheduler's hold, ZC-W0308)
until its `start_by_ms`, when it ends `failed deadline`. The input's `admitted` and `refused`
belong to C6 (admission) and are not B1 states.

### The job controller

It runs in `ControlPlane.reconcile` after the scheduler and before the replica controller
(`src/control_plane.zig:67-73`).

`src/job_controller.zig`, in the core, one pass per wake, bounded like the replica controller
(`controller_txns_per_step_max` 64, watch prefixes `/jobs/`, `/job-runs/`, `/job-status/`,
`/job-observed/`, `/assigned/`, `/nodes/`, `/node-status/`). It writes no `/assigned/` and no
`/allocations/`. For each job, in this order:

1. **Create the run and status** when a job has none: one transaction, compares on `/jobs/<name>`
   (mod revision) and the absence of the run and status. Writes `/job-runs/<name>` and
   `/job-status/<name>` (`pending`) with a decision `job_created`. "Has none" means *never had*:
   a job whose run or status was deleted is never given another (I8a); it is ZC-E0307 and
   nothing changes (authority.md §7; how the controller knows is open:
   `docs/decisions/2026-11-05-b1-controller-never-recreates-a-run.md`).
2. **Phase one of an ending: `stop`.** Set `stop` in the run (compare on the job and the run) when
   `cancel_requested` is set (cause `cancel`), when the server's clock passes `start_by_ms` and
   no claim exists (`not_started`), or when the node is lost and no claim exists (`unreachable`).
   From the revision of this write, no placement of the run can commit (the scheduler compares the
   run and refuses one with `stop`) and no claim can commit (the agent's claim compares the run).
3. **Phase two: end without the agent** when the controller reads, at a revision at or after the
   `stop`, that no claim of the run exists: then nothing has started and nothing can. It writes the
   terminal status (`cancelled`, `failed deadline`, or `failed not_started` for a run whose node
   was lost before any claim: it never ran), comparing the run,
   the status and `/job-endings`. Whether the run was placed does not matter.
4. **Read `/job-observed`**, admissible only with matching tenure, epoch and node `ready` (I2/I6),
   and write the status: `running` on a claim or `running` report (recording `tenure` and `epoch`);
   the terminal state on an `exit`, mapped by the table in "Settled here".
5. **Node loss** is judged by the **run's tenure**: the tenure recorded in its status from the
   claim. When that tenure has ended (the `/nodes/<node>` record is gone, or holds a newer tenure,
   or the node status is `lost` for it) and `lost_grace_ms` has passed since the controller first
   saw it end, the run is ended `failed unreachable`. The agent fenced by then (I1b's bound) unless
   the node was wedged. A run that is placed but never claimed is ended through step 2 (`stop` with
   cause `unreachable`, ending `failed not_started`) once its node is lost, so a node that comes
   back cannot claim it. If the agent, under a new tenure, reports a run it fenced (`stop_cause:
   fence`, with the old epoch), and the status is not yet terminal, that report ends it `failed
   fenced`; if it is already terminal, the report is dropped (ZC-W0307) and recorded in the job's
   decisions. The run is never reassigned.
6. **No release here.** The scheduler releases the assignment of a run whose status is terminal
   (below). The agent stops whatever is left (nothing, normally).

**The scheduler** reads `/job-runs/` and `/job-status/` beside `/replicas/` and:

- places a run whose status is not terminal and whose run has no `stop`, as replicas are placed
  (fit, spread, locality, least allocated, name: c2.md:354), with the placement compare set plus
  the run and its status (`/job-runs/<name>`, `/job-status/<name>` at the revisions read: 7
  compares, within 16). Jobs count toward `/allocations` like replicas; spread treats all runs as
  one group, so runs spread across nodes. It also refuses a node holding `jobs_per_node_max`
  runs (counted from `/assigned/<node>/*-job` at the revision read, exact because the compare on
  `/allocations/<node>` fails on any concurrent placement there) or `runtime_handles_max`
  assignments in all (`Allocation.count`).
- releases the assignment of a run whose status is terminal, or whose job is gone: the release
  compare set plus the status (3 compares), with a `released` decision citing the ending.

**Writer table** (`src/writers.zig`): add `job_controller` with `/job-runs/`, `/job-status/` and
`/job-endings`; the API gets `/jobs/`, `/job-input/` and `/job-admission`; the agent gets
`/job-observed/<its node>/`; the scheduler keeps `/assigned/` and `/allocations/` (no change of
owner); retention gets deletes on `/jobs/`, `/job-input/`, `/job-runs/`, `/job-status/`,
`/job-observed/`. Each row is a test, as the table's tests already are. authority.md gains a
section "Jobs" with I1a/I1b/I2/I6/I7 restated for runs and one new invariant:

- **I8a (authoritative, always).** A job's terminal status is written once and never changes; no
  claim, placement or start record of its run commits after its run's `stop` or its terminal
  status; and a run id has at most one claim, ever.
- **I8b (physical, within the stated window).** No execution of a run is alive after its terminal
  status for longer than I1b's window (`lost_grace_ms` plus kill latency) after the fence bound,
  provided the node is not wedged and clock-rate skew is within bound. Under a wedged node the
  simulation records the overlap and does not count it as a violation, exactly as I1b.

### How the agent runs a job to completion

The agent's `GET /v1/agent/nodes/{node}/replicas` serves the replicas the scheduler assigned to the
node (`src/agent_api.zig:342-370`; docs/api.md:452). It gains a sibling list, `.../runs`,
serving the runs assigned there (`*-job` ids) whose status is not terminal: each the
`/job-runs` record, without the input. One unpaged page, as the replica list (gap 10); the bounds
below keep it under a page. The agent's reconcile (`src/agent.zig:246`) adds runs to its wanted
set (gap 8), so `orphan_containers` leaves them alone, labels their containers `zcube.replica`
(the run id) and `zcube.job` (the name), and treats a run as a replica with these differences:

- **Claim, then start, once.** Before it starts a run the agent (1) writes a start record in its
  state directory (run id, epoch, phase `claiming`), (2) commits a `claimed` observation to
  `/job-observed/<node>/<name>` comparing its tenure (`compare_sets.observed_write`,
  `src/compare_sets.zig:122`) and the run's revision as served (a run with `stop` is never
  claimed), (3) sets the phase `claimed`, fetches the input if any (`GET /v1/agent/nodes/{node}/
  runs/{name}/input`, checked against `input_digest`) and (4) calls `Runtime.start`. A failed
  compare in (2) means the run changed: read again. The start record is never removed while the
  run is assigned. On restart: phase `claiming` and no claim in the store → claim again (nothing
  started); phase `claimed` and a live container → adopt; phase `claimed`, no container → judged by
  the supervisor's exit file if one exists, else reported `exit.kind = lost`. A run the agent finds
  claimed in `/job-observed` (its own earlier report, kept across a lost state directory) is never
  claimed or started again.
- **No restart.** An exited container is reported once and left.
- **Deadline.** When the run starts the agent records `started_at_ms` (its report) and a deadline
  of `start + deadline_ms` on `CLOCK_BOOTTIME` with the `boot_id`, in the start record. At the
  deadline it records `stop_cause: deadline`, stops the container (`Runtime.stop`, `grace_ms`),
  then kills. The server never decides a running job's deadline.
- **Stop.** When the served run has `stop`, the agent records `stop_cause` (`cancel`,
  `not_started`, `unreachable`), stops with `grace_ms`, then kills, and reports the exit with it. A
  fence records `stop_cause: fence` for every run before it stops them; the report goes out under
  the next tenure (step 5 above).

`kill -9` of `zcube-agent`: the container is under its supervisor, so it runs on; the restarted
agent lists runtime handles, adopts the run (by its `zcube.replica` label and start record),
resumes the deadline from the stored monotonic time under the same `boot_id`, and reports. The
exit the supervisor recorded while the agent was away is still reported once.

### Input

`POST /v1/jobs` may carry `input` (a UTF-8 string without NUL, at most `job_input_bytes_max`
64 KiB decoded) and `input_env` (the variable it is given in, e.g. `BOTPIKE_INPUT`). The API
writes it once, to `/job-input/<name>`, and stores only its digest and size in `/jobs/<name>`.
The run never carries it, so the runs page stays small; the agent fetches it for one run at a
time, after its claim, from an endpoint that serves it only to the node the run is assigned to
(which, without identity, means only to a caller that names that node: question 12). The POST
body for this route may be up to `job_request_bytes_max` (`6 * job_input_bytes_max + 16 KiB`, 400 KiB, owner decision of 2026-11-05); every other route keeps
`api_request_bytes_max` (64 KiB). Slice 2 checks how the HTTP layer applies `http_body_bytes_max`
(`constants.zig:217`) and the arena asserts (`:698-733`), and raises it for this route only.
`GET /v1/jobs/{name}` returns `env` names (not values), `input_digest` and `input_bytes`, never the
input.

### The watch

A job's ending is a put to `/job-status/<name>` with a terminal state.

`GET /v1/jobs/watch?from=&timeout=&label=k=v` is `/v1/watch?prefix=/job-status/` with the values
decoded to job statuses. Same guarantees as docs/api.md:112: ordered, no gaps, a revision's events
never split, an idle response advances the bookmark, `from` at or below compaction is 410
`ZC-E0203`, `from` more than one past the head is 400 `ZC-E0204`.

**The contract a watcher gets:**

1. Within the store's history (`server_compact_keep_revisions`, 1000 revisions, about 100 jobs of
   activity; compaction every `server_compact_ms`, 60 s) the watch delivers each ending exactly
   once, at one revision, never rewritten (I8a). A client that records the last revision it handled
   and resumes from the next sees each ending once.
2. A client that fell further behind gets 410. It lists `GET /v1/jobs?state=ended` (every retained
   job with its end and the list's revision), handles each ending it has not handled, deduplicating
   by `(name, epoch)` (`(name, ended_at_ms)` for an unplaced ending; docs/api.md), and watches from the list's revision. That is at least once, made exactly
   once by the client's deduplication.
3. Nothing is missed if the client's outage is shorter than `job_finished_age_ms_min` (1 h): no
   ended job is deleted younger than that.

Botpike copies what it needs on the ending event (the input); its record of handled endings must
outlive its own outage, which it controls.

### Retention and logs

Retention is by age with a floor: the retention role deletes `/jobs/<name>`, `/job-runs/<name>`,
`/job-status/<name>` and `/job-observed/../<name>` of a job ended longer than
`job_finished_age_ms_max` (24 h) ago, oldest first, in batches of `retention_batch_pairs`
(`constants.zig:176`). The age is a server setting that cannot go below `job_finished_age_ms_min`
(1 h). `/job-input/<name>` is deleted as soon as the job has ended. No count-based deletion: the
store's bound comes from admission (Bounds, `job_admitted_window_max`). The job's decisions go with
the existing reachability-based decision retention (`src/retention.zig`). A name is free again
after its job is deleted.

**Logs.** Unsettled until question 4. The recommendation: a job's last `job_log_bytes_max`
(64 KiB) of combined output, read through `GET /v1/jobs/{name}/logs`, served by the *agent*
(the output file never moves into the store, since the store holds control state, not logs):
the server proxies to the node's agent address, which holds it until the run directory is
removed (ending + `job_finished_age_ms_max`). If the node is gone the answer is `410` with
ZC-W0309, and the ending does not depend on it. This needs the `Runtime` to expose output
(Ask-first) or the agent to read the supervisor's log file directly (which is Zigbox's file
layout, so a Zigbox request). B1 takes the second path if the owner approves it; otherwise
logs are cut from B1 and recorded in `docs/demos/b1.md`.

## The checks and their teeth

**`sim-cluster` gains jobs** (docs/core.md, "The cluster simulation"): the generated operation
mix adds create, cancel, and "the job ends" faults (exit 0, exit n, signal, oom, pid limit,
deadline) beside the existing node crash, partition, store slowness and agent restarts. The
simulator uses the real constants for compaction (`server_compact_keep_revisions`), retention and
the submit window. Checks, true at every revision unless stated:

- **J1.** I1a for runs: each run id has at most one assignment, and observations of it are
  admissible under at most one tenure. Physically, no job's run executes after its terminal status
  outside I8b's window; under a wedged-node fault the overlap is recorded, not counted (as I1b).
- **J2.** Each run id is started at most once, ever: across agent restarts, lost state
  directories, nodes and the job's whole life.
- **J3.** A terminal status is written once: no `/job-status/<name>` goes from terminal to anything
  else, and a deleted one is not recreated while its job exists.
- **J4.** Every ending reaches a watcher: a simulated client that records the last revision it
  handled and restarts at random, with outages drawn both inside and beyond the compaction horizon
  (but shorter than `job_finished_age_ms_min`), follows the watch → 410 → list → deduplicate
  contract and handles each ending exactly once, never missing one.
- **J5.** `retries` 0: no second assignment of a run after its `stop` or its terminal status.
- **J6.** A stopped (cancelled) run has no live execution later than, from the `stop`'s commit:
  `agent_resync_ms` + `grace_ms` + kill latency when the agent's link is up; and `ttl −
  fence_margin_ms + fence_stop_ms` + kill latency when it is partitioned (the fence: the agent's
  last acknowledged keepalive was sent before the `stop` committed). The bound is the larger of the
  two; a wedged node is exempt.
- **J7.** The oracle for J2 and I8a: the simulated runtime keeps a ledger of every
  `Runtime.start` (run id, node, tenure, epoch) that survives agent crashes and spans all nodes.
  Every start follows a committed claim for that run, epoch and tenure; no start follows the
  commit of the run's `stop`; and the ledger has at most one start per run id.
- **J8.** Deadline: no run executes longer than `deadline_ms + grace_ms` + kill latency after its
  start, on its node's monotonic clock, unless the node is wedged; and every run that is not
  claimed by `start_by_ms` ends `failed deadline`.
- **J9** (B2). A `running` or `stopped` report is stored only while the assignment it names is
  the one in the store; tooth `-job-stale` (the agent leaves that compare out).
- **`sim-c1`** runs J1 to J8 with I1 to I7 (the allocation and read-set checks cover
  `/assigned/<node>/*-job` and the new `/job-*` prefixes: its compare-set check learns that a
  placement of a run rests on the run and its status, a status write on the job, the run, the
  observation and `/job-endings`, and a create on `/job-admission`).

Teeth, as the repository already does (`sim-teeth`, `sim-c1-teeth-*`): each check has a test-only
fault that must make a seed fail: `sim-c1-teeth-job-restart` (the agent starts an exited run
again: J2/J7), `-job-claim` (the agent starts before its claim commits: J7), `-job-double` (the
scheduler places a run that has a `stop`: J5/J7), `-job-rewrite` (a status is rewritten: J3),
`-job-gap` (the watch drops one event: J4), `-job-cancel` (the agent ignores `stop`: J6),
`-job-deadline` (the agent ignores the deadline: J8), `-job-deadline-late` (the agent enforces it
9 s late: J8; added in slice 5's review), `-job-deadline-offline` (the agent does not
enforce the deadline while the server is unreachable: J8; added in the release review). Each passes only if a seed in 1 to 10 fails.
The fleet (`sim-fleet`) runs them in its next round (C3's slice that deploys it,
c3-sim-fleet.md, is separate; B1 only adds a `--jobs` flag's default-on to `sim_cluster`).

## `demo-b1`: what B1 alone can show

Stated against HANDOFF's rule: a demo is the script passing start to finish; unit tests never
stand in for it. `zig build demo-b1 -Dbackend=sqlite|postgres` starts `zcube-server`
(`--lease-ttl-ms 8000`) and two `zcube-agent`s with `FakeRuntime` (as demo-c1), each with
`--cpu-millis 1000`, then:

1. `job run` that exits 0, one that exits 3, one that is OOM-killed, one that passes its deadline
   (2 s), one cancelled while running, and one with a 1 KiB input that it echoes into its exit
   code: each ends in the right state and cause; the same `POST` again is a no-op and a different
   one under the same name is `ZC-E0131`.
2. A watcher reads the endings, is killed after the third, restarts from its last revision and
   sees the other three exactly once (J4 in a real run).
3. `kill -9` of a node's agent while a job runs: the job keeps running; the restarted agent
   reports its ending; the job ends `exited`.
4. Power off the node under a running job (the demo-c1 power-off): `failed unreachable` after
   lease expiry and grace, and `zcube why job` shows the chain; the job is **not** started on the
   other node (`retries` 0).
5. Five jobs requesting 500m each: four run (two per node by CPU), the fifth stays `pending` with
   `why` naming the shortfall, then runs when one ends. (`jobs_per_node_max` at 64 would need 129
   jobs on two nodes; its bound is tested in unit tests and the simulation, not the demo.)
6. `zcube job logs` for a finished job (if logs are approved).

Not in the demo (later milestones): the relay, identity, signed images, placement by tenant, API
identity (B2 to B6). The real-supervisor kill and a real OOM need the Zigbox runtime: the demo
uses `FakeRuntime`'s fault files (`oom`, `pid_limit`, `lost`; AGENTS.md) and says so; a real-runtime
check is a smoke test (`zbx` on a Linux host), not the demo, and the README says which was run.

2. **Retries above 0.** *Recommended:* refuse until C8 (ZC-E0130). Botpike sends 0.
3. **An ending the agent cannot determine** (a crash between claim and report with no exit file):
   `failed unreachable` with a diagnostic, or a new cause `unknown`? *Recommended:* add the cause
   `unknown` to the closed set now (it is honest and cheap); a client treats it as it treats
   `unreachable` (do not retry without asking).
4. **Logs.** (a) approve the agent reading the supervisor's log file (a Zigbox layout request),
   (b) approve a `Runtime` log method (Ask-first change), or (c) cut logs from B1. *Recommended:* (c)
   for B1, (a) as a follow-up slice once Zigbox states the layout; Botpike never uses logs for
   outcomes (the input), and the run page can show a placeholder.
5. **Botpike's input.** RT-Z1 puts up to 64 KiB in `BOTPIKE_INPUT`. It cannot ride in `env` (the
   POST limit, the double store, the unpaged runs list). *Recommended:* the `input` field, stored once
   in `/job-input/<name>`, at most 64 KiB of UTF-8 without NUL, given to the container in the
   variable `input_env` names; `env` capped at 8 KiB. Botpike confirms 64 KiB of text is enough and
   that an environment variable (not a file) is what it wants.
6. **Is `node_lost` observed or inferred?** It is both, depending on whether the agent comes back
   and says it fenced the run. *Recommended:* keep the input's name `node_lost` (Botpike has coded
   against it) and add `basis: observed | inferred` to the ending; `why` says "stopped being heard"
   for `inferred`. Alternative: rename to `unreachable`.
   *Answered:* two endings, not one with a basis: `failed fenced` (observed: the agent reported
   it stopped the run) and `failed unreachable` (inferred: the node stopped being heard); a run
   whose node was lost before any claim ends `failed not_started`. Clients recode.
7. **Deadline from submission or from start?** *Recommended:* from the start (the agent's monotonic
   clock, `boot_id`-checked; revision 1's question about wall-clock skew is moot), plus a start
   backstop of the same length from creation on the server's clock, which ends a job that never
   starts as `failed deadline`. A job therefore ends within at most twice `deadline_ms` of creation.
   Alternative: one deadline from submission, enforced by the server for `pending`/`placed` and by
   the agent for `running` (needs the agent to trust the server's wall clock).
8. **The constants**: `jobs_max` 512, `jobs_per_node_max` 64, `job_admitted_window_max` 8192 over
   73 h, retention 24 h with a 1 h floor, `job_submit_window_ms_max` 1 h, `job_input_bytes_max`
   64 KiB, `job_env_bytes_max` 8 KiB. *Recommended* as stated; they are constants and cheap to change.
9. **The run id `<name>-job`** in `/assigned` and as the container name. *Recommended:* yes (gap 7:
   it is a valid Zigbox name and never a replica id); the CLI and API show the job name only.
10. **May a partition kill jobs?** With self-fencing, a partition longer than `ttl − fence_margin`
    (7 s) kills every job on the node, ending `failed fenced`. *Recommended:* yes for B1: it is
    the price of I1b and of an ending that does not lie, and the same as replicas. Alternative:
    jobs survive a partition, but then the server cannot write any ending while the node is away
    (the job may still finish), capacity stays held, and Botpike needs its own timeout.
11. **The idempotency horizon.** A retried `POST` after the job's records are deleted would create
    it again and run it twice. *Recommended:* `submit_by_ms` required, at most 1 h ahead, and
    retention never deletes an ended job younger than 1 h, so every retry inside the window finds
    the job (bounded state, no tombstones). Alternative: a tombstone per deleted name for 7 days
    (unbounded by count unless capped too).
12. **Env and input exposure before identity.** Until mTLS and B3, anyone who reaches the server
    can read a job's input and env values through the agent endpoints. *Recommended:* accept for
    B1 with the server on a private address, never return them from the public job routes or the
    console, and state in docs/api.md that secrets must not be put in either until identity lands.
