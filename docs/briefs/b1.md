## Goal

A `job` object beside `service`: run one task to completion on one node, report how it ended,
and never run it twice. The cluster guarantees at most one live execution of a job (I1a/I1b of
authority.md carry over), and an ended job never starts again. Botpike's use: one job per agent
run, `retries` 0, the ending read through a gap-free watch.

## Non-goals

- Retries above 0 (the field exists, a value above 0 is refused: ZC-E0130; C8 builds retry with
  its own idempotency story). Botpike sends 0.
- Gang scheduling, builds (M7), the shared build cache (C8).
- `relay`, `placement`, identity and signed images (B2 to B6). B1 stores the `relay` and
  `placement` fields as absent and refuses them if sent (ZC-E0130, "not built yet"): a field
  that is accepted and ignored is a lie about isolation.
- Cron and recurring jobs. Job dependencies. Streaming logs.
- Authentication of the API (docs/api.md:232: writes are unauthenticated until auth exists). Jobs
  are no different; listen on a private address. mTLS brings identity.

What does not exist, and so is B1's work:

1. **No job object, key, controller, API route, CLI command or console screen.** `grep -ri job`
   finds only fetch jobs and a cert's commonName comment (`src/constants.zig:591-595`, which already
   expects a job name there: good for B3).
2. **The replica controller does the wrong thing for a job.** It replaces an exited replica,
   replaces a replica on a lost node under a new id, and holds a user-blame start failure
   (`src/replica_controller.zig` header). A job must do none of the first two. So a job cannot be a
   replica of a one-replica service. It needs its own desired and status records and its own
   controller. It does reuse the scheduler's `/assigned` + `/allocations` path, so I6/I7 (no
   double-spend of a node's capacity, no unadmitted assignment) apply to jobs unchanged.
3. **`deadline` is not a runtime concept.** `ExitReason` has no deadline. The agent must enforce it.
4. **`pids` is in `Runtime.Limits` but not in `records.Limits`** (`src/records.zig`, `Limits`). The
   input's `pid_limit` cause cannot be configured until the record gains it. Jobs' own record has it;
   services stay as they are.
5. **There is no log facility.** `Runtime` has no way to read output; both runtimes send it
   to `.ignore` (`src/fake_runtime.zig:308`, `src/zigbox_runtime.zig:241`); the only log file is a
   fetch's `fetch.log` (`src/agent_records.zig:54`). Zigbox's `zbx logs` (5 MiB per container, per
   the input) is not reachable through the `zigbox` module as `src/zigbox_runtime.zig` uses it.
   Reading output through `Runtime` is a change to the interface: **Ask-first**
   (HANDOFF; AGENTS.md says the agent's `Runtime` follows what `zigbox` exposes). See question 4.
6. **The API has no typed view of jobs and `/v1/why` has no `job` subject.** Both are added.
7. **Names.** Replica ids are `<service>-<n>`; names allow `[a-z0-9-]` only (`src/records.zig:196`).
   A job named `x-3` would collide with replica 3 of service `x` in `/assigned/<node>/<id>`.
   B1 gives a job's run an id outside that charset (`job.<name>`), so no collision is possible.

Where the input and the code disagree (all followed as the code says):

- **"`node_lost` once the node's lease expires."** The server learns of loss at expiry, plus
  `lost_grace_ms` (`constants.zig:139`). The ending is written then. It is only safe because the
  agent fenced itself earlier (`s + ttl - fence_margin`), the same bound as I1b. A *wedged* node
  (agent frozen, container still running) breaks it, as for services; `node_lost` therefore says
  "stopped being heard", never "has stopped" (see Design, "Node loss").
- **`exited` carries "the exit code".** A process killed by a signal has no code. `exited` carries
  `code` or `signal`, exactly one.
- **`limits` "as `Runtime.Spec`".** The record's `Limits` has no `pids` (gap 4).
- **`labels`.** `Runtime.Spec.labels` is `runtime_labels_max` (8) pairs, key 32 B, value 128 B
  (`constants.zig:96,99-100`); input's `run`, `org` fit. The input cites `src/agent_api.zig:680`
  for node labels; the constant is at `:683`. The input cites `docs/api.md:231` for unauthenticated
  writes; it is `:232`. Both are off by a few lines, not in substance.
- **`env`, up to 64 KiB in Botpike's RT-Z1 (`BOTPIKE_INPUT`).** `runtime_env_count_max` is 16 entries
  and `store_value_bytes_max` is 256 KiB per value (`constants.zig:95,41`), but a job record holds
  its whole spec, and a replica/run record is read by the agent in lists capped at
  `agent_node_replicas_max`. 64 KiB per job times a few hundred jobs per node is megabytes per
  list. B1 caps a job's total env at `job_env_bytes_max` (64 KiB) and a node's pending jobs at
  `jobs_per_node_max`, and the agent endpoint pages (see Bounds). Whether Botpike's input fits in
  the env at all is theirs to say; question 5.
- **"Placed → running" as states.** Placement is the scheduler's `/assigned`, not a job state the
  job controller writes, but `zcube why` reads it as the `placed` step. The states below are
  derived, and the stored status has fewer values.
- **O3 to O5** are listed open in the input's questions; the owner has answered O1 and O2 only.
  Nothing in B1 reads them.

## Design

### Keys (additions to keys.md)

| Prefix | Writer | Content |
|---|---|---|
| `/jobs/<name>` | API | Desired: the immutable spec (v1): `image`, `source`, `command`, `env`, `limits` (cpu, memory, pids), `deadline_ms`, `retries` (0), `labels`, `grace_ms`, `created_at_ms`, `applied_by`; and mutable `cancel_requested` (null or `{at_ms, by}`). |
| `/job-runs/<name>` | job controller | The run: a copy of the spec the agent needs, plus the id `job.<name>`, `generation` 1, the node once chosen, the placement epoch, `cancel` (copied from the job), and `deadline_at_ms` (wall time, set when the agent reports `started_at_ms`, see below). Created once, deleted by retention. |
| `/job-status/<name>` | job controller | The status: `state` (below), `node`, `epoch`, `started_at_ms`, `ended_at_ms`, `end` (`exited{code|signal}`, `failed{cause}`, `cancelled`), `diagnostic` (a `ZC-` code and sentence when failed), `decision` (the id of the last decision), `reported_at_ms`. Terminal states are written once. |
| `/job-observed/<node>/<name>` | that node's agent | What the agent reports (a v1 `Observed` with a job's name, tenure, assignment, `exit`, `diagnostic`, `started_at_ms`, plus `deadline_hit` and `stop_cause`). Same admissibility rule as `/observed`. |
| `/assigned/<node>/job.<name>` | scheduler | The ordinary assignment record, `service` empty and `job` set (Assigned v2: `job` optional). Epoch = its `mod_revision`. |

`/decisions` and `/decision-summaries` take a new subject kind `job`; `decisions_per_subject_max`
(200) is far more than a job needs, so a job never compacts its own chain while it lives. The
scheduler writes `placed` / `unschedulable` decisions with `job` as the subject.

### States

```
pending ─► placed ─► running ─► exited | failed | cancelled
   │                              ▲
   └──────── cancelled / failed ──┘     (cancel before placement; refused / unschedulable never ends a job)
```

`pending`: no assignment. `placed`: assigned, nothing reported. `running`: admissible
`/job-observed` says running. A job over `jobs_max` or its node's `jobs_per_node_max` stays
`pending` with the reason in `why` (`ZC-W0308`); the input's `admitted` and `refused` belong to
C6 (admission) and are not B1 states: B1 has no admission. The state is stored in `/job-status`;
`placed` is stored too (the controller writes it from the `/assigned` it watched, so a client sees
it without listing `/assigned`).

### The job controller

It runs in `ControlPlane.reconcile` after the scheduler and before the replica controller (`src/control_plane.zig:67-73`).

`src/job_controller.zig`, in the core, one pass per wake, bounded like the replica controller
(`controller_txns_per_step_max` 64, watch prefixes `/jobs/`, `/job-runs/`, `/job-status/`,
`/job-observed/`, `/assigned/`, `/nodes/`). It does, in this order for each job:

1. **Create the run and status** when a job has none: one transaction, compares on `/jobs/<name>`
   (mod revision) and the absence of the run and status. Writes `/job-runs/<name>` and
   `/job-status/<name>` (`pending`) with a decision `job-created`.
2. **Copy cancel**: when `/jobs/<name>`'s `cancel_requested` is set and the status is not terminal,
   write it into the run (compare on the job and the run). A job `pending` with no assignment is
   ended `cancelled` here at once: the scheduler may race (it assigns in the same revision), so
   the transaction compares on the *absence* of `/assigned/<node>/job.<name>` for every node: the
   scheduler's own assignment compare set already includes the run's key (below), so one of the two
   wins and the other retries.
3. **Placement**: the scheduler places runs exactly as replicas (fit, spread, locality, least
   allocated, name: c2.md:354), reading `/job-runs/` in addition to `/replicas/` for what needs
   a node. Jobs count toward `/allocations` like replicas. The scheduler never places a job whose
   status is terminal or whose `cancel` is set (compare on the run).
4. **Read `/job-observed`**, admissible only with matching tenure, epoch and node `ready` (I2/I6),
   and write the status: `running` on the first report; the terminal state on an `exit`:
   - `exited` with code or signal and no cancel and no deadline → `exited`;
   - cancel set → `cancelled` (whatever the exit);
   - the agent's `deadline_hit` → `failed deadline`;
   - `oom`, `pid_limit` → `failed` with that cause;
   - `start_failed` with user blame → `failed start_failed` (a bad image, an empty command): never
     retried, the diagnostic carried;
   - `start_failed` with environment blame (disk full, runtime unavailable) → also `failed
     start_failed` with `blame: environment`; B1 has no retry, so it ends. (C8's retries will decide
     which are retried; recorded in the status so they can.)
5. **Node loss**: when the node controller has marked the run's node `lost` (status `lost`
   under the same tenure), write `failed node_lost` and delete the assignment in the same
   transaction with `/allocations` decremented (the same release path the replica controller's
   `lost` handling uses). The run is **not** reassigned: terminal. If the same node's agent later
   reports an ending for it, it is dropped (the agent self-fenced, so a report is stale or a
   wedged-node symptom); ZC-W0307 and an audit entry.
6. **Release**: on a terminal status, delete `/assigned/<node>/job.<name>` and decrement
   `/allocations/<node>` in one transaction that compares on the status. The agent then stops
   whatever is left (nothing, normally).

Writer table (`src/writers.zig`): add `job_controller` with `/job-runs/`, `/job-status/` and
`/assigned/<node>/job.*` *deletes only*; the scheduler gets `/assigned/<node>/job.*` creates; the
API gets `/jobs/`; the agent gets `/job-observed/<its node>/`; retention gets deletes on
`/jobs/`, `/job-runs/`, `/job-status/`, `/job-observed/`. Each row is a test, as the table's tests
already are. authority.md gains a section "Jobs" with I1a/I1b/I2/I6/I7 restated for runs and one
new invariant, **I8: a job's terminal status is written once, and no run of the job exists after
it** (see the checks).

### How the agent runs a job to completion

The agent's `GET /v1/agent/nodes/{node}/replicas` serves the replicas named under
`/assigned/<node>/` (docs/api.md:552). It gains a sibling list, `.../runs`, serving the runs named
there (`job.` ids), each the `/job-runs` record with its `env`. The agent's reconcile (`src/agent.zig:246`)
treats a run as a replica with three differences:

- **No restart.** An exited container is reported once and left; the agent never starts it again.
  The agent persists a start record (`agent_state`, keyed by run id and placement epoch) *before*
  it calls `Runtime.start`, so a crash between "start" and "report" cannot start the run a second
  time. On restart, a run with a start record and no live container is judged by the supervisor's
  exit file if one exists; if none does, the agent reports `exit.kind = lost`, and the controller
  maps `lost` on a *live* node to `failed node_lost` with the diagnostic "the agent could not
  tell how it ended" (ZC-E0521). The input's closed set has no better cause; a cause `unknown` is
  question 3.
- **Deadline.** When the run starts the agent records `started_at_ms` (its report) and arms a
  deadline at `start + deadline_ms` on its monotonic clock; its state file keeps the wall-clock
  deadline too, for an agent restart. At the deadline it stops the container (`Runtime.stop`,
  `grace_ms`) and reports `deadline_hit`. The server never decides a deadline.
- **Cancel.** When the served run has `cancel`, it stops with `grace_ms`, then kills, and reports
  the exit with `stop_cause: cancel`.

`kill -9` of `zcube-agent`: the container is under its supervisor, so it runs on; the restarted
agent lists runtime handles, adopts the run (it recognises the `zcube.job` label the agent put on
the container), re-arms the deadline from the stored wall time, and reports. The exit the
supervisor recorded while the agent was away is still reported once.

### The gap-free watch

A job's ending is a put to `/job-status/<name>` with a terminal state. The watch is the existing
store watch, typed:

`GET /v1/jobs/watch?from=&timeout=&label=k=v` is `/v1/watch?prefix=/job-status/` with the values
decoded to job statuses. Same guarantees as docs/api.md:112: ordered, no gaps, a revision's events
never split, an idle response advances the bookmark, `from` at or below compaction is 410 `ZC-E0203`
(the client lists `GET /v1/jobs?...` and watches from the list's revision), `from` more than one
past the head is 400 `ZC-E0204`. **"Exactly once" means this:** each ending is exactly one event at
exactly one revision, never rewritten (I8), so a client that records the last revision it has
handled and resumes from the next sees each ending once; it cannot see one twice unless it replays
revisions it already handled. A watcher offline longer than retention cannot be told what it
missed beyond "compacted"; it lists, and the list contains every job still retained with its end.
Botpike copies what it needs on the ending event (the input), so retention only has to outlive a
watcher's outage: `job_finished_age_ms_max` is 24 h (below), and the 410 path is tested.

### Retention and logs

`job_finished_max` (1000 finished jobs) and `job_finished_age_ms_max` (24 h): the retention role
deletes `/jobs/<name>`, `/job-runs/<name>`, `/job-status/<name>` and `/job-observed/..` of a job
ended longer than the age or beyond the count, oldest first, in batches of `retention_batch_pairs`
(`constants.zig:176`). The job's decisions go with the existing reachability-based decision
retention (`src/retention.zig`). A name is free again after its job is deleted.

**Logs.** Unsettled until question 4. The recommendation: a job's last `job_log_bytes_max`
(64 KiB) of combined output, read through `GET /v1/jobs/{name}/logs`, served by the *agent*
(the output file never moves into the store, since the store holds control state, not logs):
the server proxies to the node's agent address, which holds it until the run directory is
removed (ending + `job_finished_age_ms_max`). If the node is gone the answer is `410` with
ZC-W0309, and the ending does not depend on it. This needs the `Runtime` to expose output
(Ask-first) or the agent to read the supervisor's log file directly (which is Zigbox's file
layout, so a Zigbox request). B1 takes the second path if the owner approves it; otherwise
logs are cut from B1 and recorded in `docs/demos/b1.md`.

## The checks and their teeth

**`sim-cluster` gains jobs** (docs/core.md, "The cluster simulation"): the generated operation
mix adds create, cancel, and "the job ends" faults (exit 0, exit n, signal, oom, pid limit,
deadline) beside the existing node crash, partition, store slowness and agent restarts. Checks,
true at every revision:

- **J1.** No job has live runs on two nodes (the same as I1a/I1b for services).
- **J2.** No job is started after its terminal status (I8). The simulated runtime counts starts
  per run id.
- **J3.** A terminal status is written once: no `/job-status/<name>` goes from terminal to anything
  else, and a deleted one is not recreated while its job exists.
- **J4.** Every ending reaches a watcher: a simulated client that records the last revision it
  handled, restarts at random and resumes sees each retained ending exactly once and sees `410`
  rather than a gap if it fell behind.
- **J5.** `retries` 0: a run on a lost node is never started elsewhere (no second `/assigned` for
  `job.<name>` after `node_lost`).
- **J6.** A cancelled job has no live run after the grace period plus the fence margin.
- **`sim-c1`** runs J1 to J6 with I1 to I7 (the allocation and read-set checks cover `/assigned/
  <node>/job.*` and the new `/job-*` prefixes: its compare-set check learns that a status
  write rests on the job, the run and the observation).

Teeth, as the repository already does (`sim-teeth`, `sim-c1-teeth-*`): each check has a test-only
fault that must make a seed fail: `sim-c1-teeth-job-restart` (the agent restarts an exited run:
J2), `-job-double` (the controller reassigns after `node_lost`: J1/J5), `-job-rewrite` (a status
is rewritten: J3), `-job-gap` (the watch drops one event: J4), `-job-cancel` (cancel is ignored:
J6). Each passes only if a seed in 1 to 10 fails. The fleet (`sim-fleet`) runs them in its next
round (C3's slice that deploys it, c3-sim-fleet.md, is separate; B1 only adds a `--jobs` flag's
default-on to `sim_cluster`).

## API, CLI, console

**API** (`docs/api.md`, a proposal until approved: Ask-first; the writes section there is
unauthenticated):

- `POST /v1/jobs` (body: the spec; 201 new, 200 same body again, 409 `ZC-E0131`);
  `GET /v1/jobs/{name}` (spec + status); `GET /v1/jobs?state=&label=&limit=&continue=`;
  `POST /v1/jobs/{name}/cancel` (202; a finished job answers 200 with its end);

## `demo-b1`: what B1 alone can show

Stated against HANDOFF's rule: a demo is the script passing start to finish; unit tests never
stand in for it. `zig build demo-b1 -Dbackend=sqlite|postgres` starts `zcube-server`
(`--lease-ttl-ms 8000`) and two `zcube-agent`s with `FakeRuntime` (as demo-c1), then:

1. `job run` that exits 0, one that exits 3, one that is OOM-killed, one that passes its deadline
   (2 s) and one cancelled while running: each ends in the right state and cause; the same
   `POST` again is a no-op and a different one under the same name is `ZC-E0131`.
2. A watcher reads the endings, is killed after the third, restarts from its last revision and
   sees the other two exactly once (J4 in a real run).
3. `kill -9` of a node's agent while a job runs: the job keeps running; the restarted agent
   reports its ending; the job ends `exited`.
4. Power off the node under a running job (the demo-c1 power-off): `failed node_lost` after
   lease expiry and grace, and `zcube why job` shows the chain; the job is **not** started on the
   other node (`retries` 0).
5. A job over `jobs_per_node_max` stays `pending`, with `why` saying so, then runs when one ends.
6. `zcube job logs` for a finished job (if logs are approved).

Not in the demo (later milestones): the relay, identity, signed images, placement by tenant, API
identity (B2 to B6). The real-supervisor kill and a real OOM need the Zigbox runtime: the demo
uses `FakeRuntime`'s fault files (`oom`, `pid_limit`, `lost`; AGENTS.md) and says so; a real-runtime
check is a smoke test (`zbx` on a Linux host), not the demo, and the README says which was run.

## Questions for the owner

Each has a recommendation; the brief is written to it.

1. **Refuse over `jobs_max`, or hold in `pending`?** The input says a job over either bound
   waits in `pending`. For `jobs_max` that is an unbounded set in the store. *Recommended:* refuse at
   `POST` (ZC-E0132, 429); `jobs_per_node_max` waits in `pending`.
2. **Retries above 0.** *Recommended:* refuse until C8 (ZC-E0130). Botpike sends 0.
3. **An ending the agent cannot determine** (crash between start record and report): `failed
   node_lost` with a diagnostic, or a new cause `unknown`? *Recommended:* add the cause
   `unknown` to the closed set now (it is honest and cheap); Botpike treats it as it treats
   `node_lost` (do not retry without asking).
4. **Logs.** (a) approve the agent reading the supervisor's log file (a Zigbox layout request),
   (b) approve a `Runtime` log method (Ask-first change), or (c) cut logs from B1. *Recommended:* (c)
   for B1, (a) as a follow-up slice once Zigbox states the layout; Botpike never uses logs for
   outcomes (the input), and the run page can show a placeholder.
5. **Botpike's input size.** RT-Z1 puts up to 64 KiB in `BOTPIKE_INPUT`. *Recommended:* keep it
   in `env` with `job_env_bytes_max` 64 KiB, and measure the store and `/runs` page cost in slice 3;
   if a node's list nears `store_page_bytes_max`, move to per-job `/job-input/<name>` read by the
   agent separately (a later slice).
6. **Node-loss wording.** Keep the input's `node_lost` (recommended), or rename it `unreachable` so
   it does not read as "stopped"? *Recommended:* keep `node_lost`: Botpike has coded against it, and
   `why` says "stopped being heard".
7. **Deadline authority.** The agent's clock enforces it (recommended), with an absolute wall time
   kept for restarts. A skewed agent clock after a restart can shorten or lengthen by the skew;
   acceptable?
8. **`jobs_max` 512, `jobs_per_node_max` 64, retention 1000 / 24 h.** *Recommended* as stated;
   they are constants and cheap to change.
9. **The `job.` run-id prefix** instead of the job's own name in `/assigned`. *Recommended:* yes
   (gap 7); the CLI and API show the job name only.
10. **O3 to O5** remain open and are not asked here.
