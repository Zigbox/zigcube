## Goal

A job that says `relay = "botpike"` runs with no network but one TCP listener on its own
loopback (`127.0.0.1:8080`, told to it as `ZCUBE_RELAY=http://127.0.0.1:8080`). Every connection
to it reaches the upstream named for `botpike` in the server's configuration, through the node
agent, unbuffered both ways. Nothing else answers. The agent knows which job a connection belongs
to by construction (one listener per job), never from anything the job sends.

## Fixed decisions

- **Configuration, not the API.** The server's config gains
  `relays = .{ .botpike = .{ .address = "broker.botpike.com:8443" } }` (at most `relays_max = 8`;
  a bad entry is ZC-E0106, the config code). A job names a relay; an unknown name, or a job that
  sets `ZCUBE_RELAY` in its own environment, is ZC-E0130 naming the field. A client cannot give an
  address. The assignment the agent receives carries the resolved name and address.
- **Who holds the listener.** The job's supervisor (`zcube-agent supervise` / `supervise-zigbox`)
  holds it and runs the relay for that one job: accept, connect upstream, copy both ways. When the
  job ends or is cancelled, the supervisor closes the listener and every relayed connection
  before it reports the ending. Threads are allowed there (shell, not core).
- **Bounds** (constants in `src/constants.zig`, asserted, each with a coded diagnostic when hit):
  `relay_connections_max = 16` per job, `relay_connection_bytes_max = 1 GiB` each way,
  `relay_idle_ms = 300_000`, `relay_connect_timeout_ms = 10_000`, port `relay_port = 8080`.
  These are the supervisor's choices for B3; a slice that wants another value asks first.
- **The upstream connection in B3 is plain TCP**, behind an interface that B4 replaces with mTLS
  (the workload's certificate; `tls_conn.zig`). **Cut from the input:** B3's acceptance line "a
  request arrives carrying the identity of the job that sent it" moves to B4, because O2 forbids
  any identity but the client certificate. B3 proves the route: only this job's connections reach
  the upstream, and only through its own listener.
- **The fake runtime** cannot make a namespace. Its listener is `127.0.0.1:<ephemeral port>` on the
  host, given to the supervisor the same way, and `ZCUBE_RELAY` names that port. Tests say so; the
  isolation checks run only on the real runtime (slice 4).
- **The real runtime** passes `listen` to Zigbox's library (M8b) and receives the descriptor; this
  waits for Zigcube's Zigbox pin to move to the release that carries M8b.

## Diagnostics

`ZC-E0701` to `ZC-E0705` and `ZC-W0701`, `ZC-W0702` are approved (`07xx`, mesh). Suggested:
connections at the bound (W, the new connection is closed and counted); the upstream unreachable
or refusing (E, per connection, shown in `zcube why job`); a connection's byte bound or idle time
reached (W); a relay named by an assignment that the agent's build cannot serve (E). One line
each, `explain` text, the errors site regenerated. Ask before any other.

## Slices

1. **Zigbox M8b** (in `Zigbox/zigbox`, its own brief). Merges after Zigbox's M8 tag.
2. **The relay over the fake runtime** (now, beside slice 1): config, the job field, admission
   refusals, the assignment, the supervisor's relay with its bounds and codes, `ZCUBE_RELAY`,
   closing on every ending (exit, cancel, deadline, `node_lost` adoption by a restarted agent: a
   restarted agent must not leave a listener with no relay behind it). Tests against a test
   upstream (an in-process echo server), fuzz the relay's copy loop with short reads and writes,
   and `agent-smoke` gains one relayed job. `docs/api.md`, `docs/keys.md`, `docs/agent.md` updated.
3. **Simulation** (after 2): the cluster simulation's jobs may name a relay; a check that a job's
   relay is open only while the job runs on that node (opened at start, closed before its ending is
   reported, never two for one run), with a tooth that leaks a listener past the ending.
   `sim-c1` runs it; the fleet picks it up.
4. **The real runtime and the hostile tests** (after Zigbox's M8b release and the pin moves):
   `supervise-zigbox` passes `listen`; a test image runs the input's hostile list (connect to
   `1.1.1.1:443`, the node's address, `169.254.169.254:80`, `zcube-server`, another job's relay
   port; a DNS lookup; a raw socket): each fails, and a request to the relay reaches the test
   upstream. Runs in the demo VMs (`demo_c2_vms.zig`'s rig). This becomes `demo-b3`.

## Non-goals

Workload identity (B4), TLS to the upstream (B4), more than one relay per job, UDP, a relay for a
service (jobs only), signed images (B5), placement by tenant (B6), any host firewall or routing
change, O3/O4/O5 (still open; O5, whether Fly Machines can run Zigbox, gates the demo's hosting,
not this work).
