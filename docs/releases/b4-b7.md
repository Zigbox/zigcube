## The Zigbox v0.5.2 pin

Zigbox v0.5.2 is tagged at 82132cf ("Release 0.5.2", Zigbox #172; `git ls-remote` shows
`refs/tags/v0.5.2` at 82132cfd19838ffe6f2052be414d6a517f08d754). On `claude/release-0.5.2`:

- [x] **Change the pin.** `build.zig.zon` names
  `https://github.com/Zigbox/zigbox/archive/82132cfd19838ffe6f2052be414d6a517f08d754.tar.gz`
  with hash `zigbox-0.5.2-RBMWEAW0ywAuRx3krVAbWARTYrh6GImYtGPKdg7_03bY`. The hash was computed
  with `zig fetch` on a local tarball made by `git archive --format=tar.gz
  --prefix=zigbox-<sha>/ <sha>` from a clone of Zigbox; the same method gives v0.5.1's recorded
  hash (`zigbox-0.5.1-RBMWED7D...`) for 7901666. The package was unpacked into `zig-pkg/<hash>`
  as AGENTS.md's environment note says. Zigcube's `.version` is 0.5.2.
- [x] **Adapt to the API change.** One change reached Zigcube: `zigbox.start` now runs Zigbox's
  trust start gate (`trust/start_gate.zig`, the same policy files and refusals as `zbx run`) and
  takes a `GateWorkspace` (about 17 MiB) before the `Diag`. The zigbox supervisor keeps one in
  its heap `Storage`; the simulated start in `zigbox_runtime.zig`'s tests uses a static one.
  With no Zigbox policy file the gate reads nothing more and changes nothing.
- [ ] **Check the version demo-b3, demo-b4 and demo-b5 use in the guest** (KVM, CI only).
- [ ] **Confirm CI's Zigbox fetch works at the tag.**

## The Zigbox v0.5.1 pin (the bundle; superseded)

Zigbox v0.5.1 is tagged. The tag points to 7901666, not to 30ede01, which is Zigbox `main` and
already carries the 0.5.2 work. The bundle pins 7901666 (was main aa4d64c, 0.5.0 plus
`zigbox.trust`, #124); the integration record says how the hash was made.

**Zigbox 0.5.2.** Zigbox's ZB-5 to ZB-8 merged to Zigbox `main` as 5d1b0ba (PR 157):
`zigbox.container_socket`, `--hosts-file`, exec with `--net host`, and a socket that survives a
re-exec, with ZBX-E0610, ZBX-E0611 and ZBX-E0612. They ship in Zigbox 0.5.2, not 0.5.1. B4 slice 4,
and every slice that needs them, waits for the supervisor's 0.5.2 pin. The bundle is never pinned to
an untagged commit for them.

The steps for the tag:

- [x] **Change the pin.** In `build.zig.zon`, set the `zigbox` URL and `.hash` to the v0.5.1
  tarball, and update its comment's pin history.
- [x] **Check B5's trust surface against the tag.** Between aa4d64c and 7901666 the only
  change under `src/trust/` is a comptime bound in `provenance.zig` (255 to 256) and its tests;
  the policy parser, `job_trust` and the envelopes are unchanged. agent-smoke's trust rows pass
  on e6e7b86.
  - The surface is `zigbox.trust`: `job_trust.judge_run`, the policy parser, and the signature
    envelopes behind ZBX-E0905 and ZBX-E0906.
  - It is the only reason the pin is off a tag today.
- [ ] **Check the version demo-b3 and demo-b5 use in the guest.**
  - The guest's `zbx` (`zbx sign`, `zbx trust export`) and the `zigbox` runtime of
    `zcube-agent --runtime zigbox` must come from v0.5.1.
  - Both demos run only on the KVM host in CI.
- [x] **Run the shared diagnostics against the tag.** `src/diag/codes.zig` gains ZBX- codes at
  the tag, which cannot collide with ZC- codes. `errors-site` and `tidy` pass in check on e6e7b86.
  - Zigbox is canonical for DIAGNOSTICS.md and the shared `diagnostic`, `product`, `render` and
    `explain` modules.
  - Rerun `zig build errors-site` and the tidy-checked code registry against the tag.
- [ ] **Confirm CI's Zigbox fetch works at the tag.** CI fetches the pinned tarball.
- [ ] **Check the adapter against Zigbox 0.5.2** (B4 slice 4 and the slices that need ZB-5 to
  ZB-8), once the supervisor sends that pin.
- [ ] **Rerun every gate after the pin change.** That means `zig build check`, the demos and the
  sweeps, on the new commit.
  - On e6e7b86 these passed: `check: PASS e6e7b868e211 (... store:memory,sqlite,postgres ...)`,
    mtls-interop (38 cases, 0 failed), agent-smoke, demo-c0, demo-c1 and demo-b6 (all on
    sqlite), and demo-b7.
  - Still to run: the 40-seed sweeps, and demo-b3 and demo-b5, which need KVM.
