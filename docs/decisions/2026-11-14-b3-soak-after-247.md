# The b3 soak moves to the commit that fixes #247 and #248

Date: 2026-11-14. Status: supervisor's decision (the soak); implementer's decisions (the fix,
the tooth, the replays and the re-pins), recorded here as the brief asks.

## The decision

The simulation fleet has run no seeds on fb385b2 (main, frozen for the b3 soak): tracker #29's
last ingest was at f49041a. So the b3 soak moves to the commit that fixes #247 and #248, and b3
does not ship with a known J6 defect. Main stays frozen except for this fix.

## The defect

#247 (`sim_cluster 870682998 80 3 --strong --profile=slow_store --lease-ttl-ms=8488
--replicas-pct=100 --heal-at=76`) and #248 (`sim_c1_evict_world_main 225 300 1 --c1`; seed 180
with `--tenants --heal-at=238` on the B6 branch) are one bug. In `agent_jobs.pass`, a failure that
is not the runtime's (a server call: here a write the store committed whose answer was lost,
server 503 ZC-E0201, agent ZC-E0504) makes `Kept.fail` set `kept.stopped`, and the loop ended
there. Every run later in name order was skipped, among them an orphan whose stop had already
committed, and the replica stage's own such failure skipped the whole job pass. The agent stayed
linked, so J6's linked bound (resync + grace + kill latency) assumes the next pass stops the run;
under a slow or lossy store the next pass failed the same way, and the run kept executing past
the bound. The fix of #205 had covered only the runtime's failures.

## The fix (the brief's option 1)

After a server failure the pass makes no other store call, but stops every run whose stop needs
none (`Work.stop_only`): it reads the start record from the state directory, records the cause
`one` would decide from what the pass already holds (the runs list read at the pass's start, the
node clock), and stops the container. The report waits for the next pass, which finds the cause
in the start record. The observed list is not read after an earlier stage's server failure, and
the job pass now runs after the replica stage's server failure too (it then makes one read, the
runs, and no write). Option 2 (stops ordered first) was not needed: option 1 bounds J6 for every
subject in the pass, whatever its order. A failure of `Pass.load` or of the heartbeat still ends
the step before the job pass; neither replay needs it, and it is left as it was.

## Tests

- `agent_jobs_test.zig`, "a lost answer to an earlier run's write does not hold back a later
  run's stop (#247)": a test-only `SwitchedStore.lost_answer_prefix` commits a write and returns
  ZC-E0201; "other-job" (first in name order) loses its answers while "train-job" is cancelled.
  With fb385b2's `agent.zig` and `agent_jobs.zig` it fails (the cancel is not recorded); with the
  fix it passes.
- The tooth `sim-c1-teeth-job_pass_break` (`c1_teeth.job_pass_break`: the old break, and the
  job pass skipped after a replica's server failure) must fail J6 at seed 225 of the
  `job_evicted` world, 300 operations, `--c1`. It is sparse: SPARSE_NOTE. Its canary is the
  fixed range `225+1@300`.
