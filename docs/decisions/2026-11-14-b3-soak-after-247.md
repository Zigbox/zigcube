# The b3 soak moves to the commit that fixes #247 and #248

Date: 2026-11-14. Status: supervisor's decision (the soak); implementer's decisions (the fix,
the tooth, the replays and the re-pins), recorded here as the brief asks.

## The decision

The simulation fleet has run no seeds on fb385b2 (main, frozen for the b3 soak): tracker #29's
last ingest was at f49041a. So the b3 soak moves to the commit that fixes #247 and #248, and b3
does not ship with a known J6 defect. Main stays frozen except for this fix.

## The defect

#247 (`sim_cluster 870682998 80 3 --strong --profile=slow_store --lease-ttl-ms=8488
--replicas-pct=100 --heal-at=76`) and #248 (`sim_c1_evict_world_main 225 300 1 --c1`; seed 180
with `--tenants --heal-at=238` on the B6 branch) are one bug. In `agent_jobs.pass`, a failure that
is not the runtime's (a server call: here a write the store committed whose answer was lost,
server 503 ZC-E0201, agent ZC-E0504) makes `Kept.fail` set `kept.stopped`, and the loop ended
there. Every run later in name order was skipped, among them an orphan whose stop had already
committed, and the replica stage's own such failure skipped the whole job pass. The agent stayed
linked, so J6's linked bound (resync + grace + kill latency) assumes the next pass stops the run;
under a slow or lossy store the next pass failed the same way, and the run kept executing past
the bound. The fix of #205 had covered only the runtime's failures.

## The fix (the brief's option 1)

After a server failure the pass makes no other store call, but stops every run whose stop needs
none (`Work.stop_only`): it reads the start record from the state directory, records the cause
`one` would decide from what the pass already holds (the runs list read at the pass's start, the
node clock), and stops the container. The report waits for the next pass, which finds the cause
in the start record. The observed list is not read after an earlier stage's server failure, and
the job pass now runs after the replica stage's failure that is not the runtime's too (it then
makes one read, the runs, and no write). The replica stage itself makes no store call (its
writes wait for the flush, which follows the job pass), so what fails it there is the step arena
running out (ZC-E0207) or a value too large to encode; a lost answer to a replica's write fails
the flush, after the job pass has run. `stop_only` follows a failed `one` on the same subject,
so a stale container `one` already stopped is stopped again with grace 0: harmless on a real host
(`pending_stop` keeps one stop per container); in the simulation a state-directory crash in
mid-step is folded into `node.sim.crashed` only after the step, so such a stop can still reach
the runtime there. Option 2 (stops ordered first) was not needed: option 1 bounds J6 for every
subject in the pass, whatever its order. A failure of `Pass.load` or of the heartbeat still ends
the step before the job pass; neither replay needs it, and it is left as it was.

## Tests

The unit tests of `agent_jobs_test.zig` named `(#247)` are the real guard of both halves of the
fix; the tooth and the replays are sparse.

- "a lost answer to an earlier run's write does not hold back a later run's stop": a test-only
  `SwitchedStore.lost_answer_prefix` commits a write and returns ZC-E0201; "other-job" (first in
  name order) loses its answers while "train-job" is cancelled. With fb385b2's `agent.zig` and
  `agent_jobs.zig` it fails (the cancel is not recorded); with the fix it passes. It also asserts
  that no store call follows the lost answer in that step (`SwitchedStore.calls_since_mark`).
- "after a lost answer, a running run whose start record is gone or damaged is stopped" and
  "... the server no longer serves is stopped": `stop_only`'s absent and damaged branches and its
  `unreachable` fallback (PR #250 review).
- "a replica stage's failure does not hold back a run's stop": the step arena fails once just
  after a replica's container starts (ZC-E0207, a test-only `World.arena_override`), and a
  committed cancel is still recorded and its container stopped in that step, with one store call
  (the runs) and no transaction after the failure.
- The tooth `sim-c1-teeth-job_pass_break` (`c1_teeth.job_pass_break`: the old break, and the
  job pass skipped after a replica stage's failure) must fail J6 at seeds 225 and 44 of the
  `job_evicted` world, 300 operations, `--c1` (J6 at 21,596 and 23,406 ms). It is sparse: with
  the fault on, none of seeds 1 to 40 fails (300 operations, `--c1`, 2026-11-14). Its canary is two
  fixed ranges, `225+1@300` and `44+1@300` (`also_seeds` in `c1_teeth_roots`), so it re-proves
  those two seeds and no hit rate.
- The `c1_regressions` line of #247 records the issue and guards nothing: fb385b2 passes it by
  timing, and so does the loop's `break` put back.
