## Relabel eviction (product)

- A node's registration is one put of `/nodes/<n>` by its agent, and only the scheduler may write
  `/assigned/` (writers.zig). So a relabel cannot move work in the same transaction: the agent
  registers, then the replica or job controller acts, then the scheduler releases. A refused hold
  therefore exists for a few revisions; the supervisor was told (send_message, with this
  evidence) before the check was settled.
- Replica controller (`refused_placement`): a live or held replica whose node's stored labels
  refuse it (`scheduler.refuses`: the same filter placement uses, with no `require`) is dead: it
  writes a `stop_replica` decision ("...registered again with labels that do not take a service
  replica (...); it is being removed and replaced under a new id", cause `observed` on the
  `/nodes/<n>` key at its revision), compares the replica, its assignment and the node key, and
  deletes the replica. The scheduler places a successor under a new id.
- Job controller (`refused`): a run with no stop whose node's labels refuse its `require` gets the
  existing `unreachable` stop ("the node of the run was registered again with labels that refuse
  the job"); it then ends `failed unreachable` as any unreachable run does. No new enum, code,
  bound or default.
- Tooth `relabel_kept` (`c1_teeth.zig`) turns both off.

## The tenant world now

- As before: `--tenants` (and `auto` operations and the two P1 teeth) gives each node a seeded set
  from `{tenant=a}`, `{tenant=b}`, `{tenant=a, exclusive=tenant}`, `{tenant=b, exclusive=tenant}`
  (even-index nodes never exclusive; `replicas_for` counts only those), jobs `require =
  {tenant=<t>}` per `job_tenant` (every fourth none, every eleventh `c`). All tenant draws come from
  `label_prng`; a run without `--tenants` draws exactly as before.
- New: before one operation in eight until the heal (`label_prng` draws it), an operator restarts one
  node's agent (a process crash) configured with a *different* set (`relabel_node`,
  `operator restarts` in the report). Its containers keep running and it registers again in place,
  within its lease, so what it holds may now be refused. Without this, refused holds were rare
  (1 seed of 60 had any) and no tooth could bite. `relabels=` now counts only real changes.
- The restart of the tenant world takes the main generator's draw for its restart time, so tenant
  runs differ from the first version's; non-tenant runs do not.

## P1, as judged now (`src/sim_tenancy.zig`)

The judge is independent of the code under test: it records the set each node's agent was
configured with when its registration committed (a new `/nodes/<n>` mod revision; only the agent
writes that key) and checks the stored labels are exactly that set; it takes each job's tenant from
the simulation's own `job_tenant(number)` and checks the stored run's `require` is exactly that; and
it decides with its own three-line rule (`refuses`), not the scheduler's.

- **P1a, at every revision** (`placed_problem`, in the tap's `before`): no new assignment lands on
  a node whose registered labels refuse it.
- **P1b** (`scan`, once a simulated second while the store is healthy, so at least every second
  across every revision that touches `/assigned/` or `/nodes/`): every assignment a registration
  made refused is tracked from when it is first seen, and must be acted on (replica gone; run gone,
  replaced, stopped or ended) within `acted_ms_max` = 35,000 ms (the controllers' 30 s resync plus 5 s; a sim-check constant,
not a product bound) counted from the later of its first
  sighting and the store's last failure. Sentences: "P1: a service replica held on an exclusive
  node past the bound", "P1: a job held on a node that refuses it past the bound".
- **At rest** (`converged`): no assignment its node's registration refuses remains ("P1: a refused
  assignment remains at rest").
- A node with no registration (lease expired, not yet back) is not judged: its holds are I7's and
  the node controller's.

## P1's teeth

- `placement_exclusive` (unchanged): the scheduler skips its exclusive rule; P1a catches it.
- `relabel_kept` (new): no eviction; P1b (bound or at rest) catches it.
- The `require` half: no separate tooth. P1a checks the stored `require` against `job_tenant`
  and rejects a run on another tenant's node; a scheduler that ignored `require` is caught by the
  same `placed_problem` path as `placement_exclusive` (both go through `placement_refusal`). Noted
  here rather than given a 26th runner.
