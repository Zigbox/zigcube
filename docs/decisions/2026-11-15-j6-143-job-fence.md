## Why #143 was closed on 11-08 and came back

#143's fingerprint is "J6, step: faults", and three different causes have filed under it:

1. The first lines (0e48442, e2dca51, 11-07) were the simulator's step overrunning the node
   clock. B2's #171 (75d745b, 11-08) fixed that, and the lines are pinned in `sim-c1-regress`
   (2461711096, 1784779402). That fix was complete for its cause.
2. The e1e9bc0 line (11-09, `1592492511 310 2 --strong ...`) passes on ad4c6ca and on main;
   it was fixed by a later commit before ad4c6ca (not bisected; #212 and #254 are candidates).
3. The ad4c6ca line is the runs-unread gap, which #254's slice documented as remaining and the

So the earlier fixes were not incomplete; the fingerprint groups distinct root causes.

## The fix (option B)

- The agent keeps `runs_read_mono_ms`: when the last successful read of `/job-runs` was sent
  (monotonic). The job pass sets it after `list_all` succeeds; the lease file carries it
  (`runs_read_ms`) so a restart in the same boot keeps it, and an older file falls back to the
  lease's `sent_ms`. A restart can only move it earlier (`@min` with now), never later.
- `Agent.job_fence_at_ms` = `fencing.fence_at_ms(runs_read_mono_ms, ttl)`, the lease fence's
  own term. Null with no lease or while the lease fence is active (that one stops everything).
- `enforce_deadlines` (no server call, before the heartbeat, and mid-step via `before_call`)
  stops every running job past it with cause `unreachable` and a grace of at most
  `fence_stop_ms`, so J6's fenced term bounds it. Before that it arms the deadline wake at the
  job fence, so waits and calls are cut to it.
- Replicas, the lease and the tenure are untouched. The run's report waits for the server.

Not new codes and no new bound: the term is the lease fence's. The behaviour change (a job on a
node with a failing `/runs` is stopped while its replicas run on, and a job's own grace is cut
to `fence_stop_ms` in that case) is the one the owner accepted with option B.

## Rollback note

`LeaseFile` gains `runs_read_ms`. An agent from before this change parses the lease file
without `ignore_unknown_fields`, so after a downgrade it fails to read the file and fences once
(stops its containers and registers again). Upgrading is unaffected.
