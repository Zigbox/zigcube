# C4: the mesh plan, readiness and `why grant`

*Decided 2026-11-13, by C4 slice 2 (`src/mesh_plan.zig`, `src/why_grant.zig`); revised 2026-11-14
by its review fixes.*

- **Readiness admits reports as the controllers do.** A desired replica is ready when the node it
  is assigned to has an observed record for it that the replica controller would act on
  (`controller.Snapshot.admission`, shared with `replica_controller.zig`; authority.md §3): the
  record's tenure is the node's current `/nodes` mod_revision, its assignment epoch, when it names
  one, is the current `/assigned` mod_revision, and the node controller has judged the node `ready`.
  The record must then be `running` at the replica's generation and, if the service has a health
  check, last report healthy. A report that fails admission is `stale_report` or `node_not_ready`,
  never ready and never an endpoint. A C0 report has no tenure and is admitted as it is, as the
  replica controller admits it.
- **The `min_ready_ms` dwell is deferred to C3's readiness.** The brief's readiness includes it,
  and C3 (health and rollouts) defines the readiness function that applies it; the plan will call
  that function when it lands. Until then a replica is ready as soon as the rule above holds. A
  `TODO(C3 readiness)` marks the place in `replica_of_snapshot`.
- **Orphans are skipped.** A desired replica whose service record is gone (deleted, the replica
  controller not yet run) is not in the plan's input, so a `why grant` between a delete and the
  next controller pass answers instead of failing an assertion.
- **Draining.** An observed copy that is not `stopped` drains when its replica is no longer
  desired, or is desired and assigned to another node (it moved, or is not assigned at all): it is
  listed once per (replica, node), is never an endpoint, and its accepts take no new connection. A
  report on the assigned node at another generation is the replica being replaced in place, not a
  copy: it is the replica itself, not ready until the new generation runs. So a copy is keyed by
  (replica, node), and the generation decides only whether the copy on the assigned node is ready.
- **Endpoint order.** In the plan, endpoints on the planning node come first, then the others,
  each group rotated by a Wyhash of the source replica's id, so sources spread over the
  destination's replicas and one source always tries them in the same order. `why grant`'s
  `endpoints` are in ascending replica id; it answers for the service, not for one source.
- **ZC-W0704 is reported by `why grant`** (verdict `no_source`). Apply has no warnings mechanism
  today; the apply-time warning goes to slice 9, which builds the CLI's apply output, where a
  warning has somewhere to be shown.
- **The address verdicts carry no code.** `destination_has_no_address` and
  `source_has_no_address` can only mean a service written before C4 (every apply since slice 1
  gives one, and a create with none free is ZC-E0207). The remedy, apply it again, is in the
  verdict's text; a code would add no other fix. Not registered, by decision of this slice; a
  code needs the supervisor's approval first.
- **Attribution** (`allows[].added`, `removed`) lists the destination's newest
  `decisions_per_subject_max` index entries at the snapshot's revision, newest first, and takes the
  first `grant` decision whose change names `"{from} → {port} added"` (or `removed`). The change
  text is written and parsed by one formatter, `records.grant_change_write` /
  `grant_change_names`, which apply uses too. The grant decision carries the apply's `cause` and
  `cause_evidence`; `by` is `cause_evidence.applied_by`, else the decision's `actor`. A decision
  lost to retention is simply absent.
- **API path** is `GET /v1/why/grant/{from}/{to}/{port}`, with `connection` as an alias
  (docs/api.md). The CLI rendering is slice 9.
- **Not done here:**
  - `why service` listing the service's grants out and in goes to slice 9, with the CLI that
    prints it.
  - The agent does not publish mesh endpoints yet (slice 3), so until then every destination
    answers `no_endpoint` outside tests.
- **Known, for a later slice:**
  - A `removed` (or `added`) attribution can name a decision of an earlier incarnation of the same
    service name: decisions are indexed by subject name, and a deleted and re-created service
    shares it (review A, NIT 9).
  - `plan` and `check` scan every replica for every grant: O(services × grants × replicas), about
    8 million steps at the limits, per `why grant` request and per plan. Slice 4, which runs the
    plan on every agent, should index replicas by service (review A, NIT 11).
