# tls_conn: the shell around the TLS client (slice 6)

Status: implemented in `src/tls_conn.zig`; tests in `src/tls_conn_test.zig`.

- **No new diagnostic codes.** A handshake that is refused is ZC-E0813; one that times out is ZC-E0816 (E0813's page describes a refusal, not a stall); a transport
  that ends or is cut is ZC-E0816; record and key limits are ZC-E0815; an untrusted server CA is
  ZC-E0810; a failing signer is ZC-E0820. Reusing them keeps the goldens and error pages as they are.
- **Every wait is a `poll` with an absolute deadline** (`peer_stream.wait_ready`), followed by a
  non-blocking `recvfrom` or `sendto`. A socket timeout is never set: it would panic the std reader.
- **A read that times out is not fatal; a write that times out is.** A partly written record cannot
  be taken back, so the connection is `broken` and later calls answer `Closed`.
- **`close` flushes, sends close_notify and does not wait for the peer's.** It ignores a push
  failure and raises no diagnostic, because `Diag.raise` asserts it is raised once.
- **After the peer's close_notify** reads return 0 and writes return `Closed`. Half-close is not
  supported: the client state machine is `closed` after either side's close_notify.
- The handshake timeout is `tls_handshake_timeout_ms` (10 s); a refusal flushes its alert for at
  most `tls_alert_flush_ms` (1 s).
- **`write` seals and sends per call**, as the brief says; `flush` stays for the interface but has
  nothing queued after a `write`. So `close` after a peer close_notify can never drop bytes. (A seal that fails, ZC-E0815, drops the
  queued bytes and wipes them: that write returned `Refused`, so the caller knows.)
- **Sends made on `read`'s behalf are fatal on timeout** (the answer to a KeyUpdate moves the write
  keys first): `read` returns `Refused` with ZC-E0816, not `Timeout`, and the answer has its own
  budget of at least `tls_alert_flush_ms`, so a spent read deadline does not kill a healthy connection.
  The courtesy close_notify (reply or `close`) is bounded by `tls_alert_flush_ms` too. The reply to the server's close_notify is best effort and ends the stream either way.
