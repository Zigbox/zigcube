# 2026-11-14: B4 slice 4, stock servers and demo-b4

*Decided 2026-11-14, by the slice (B4 slice 4).* Brief: docs/briefs/b4.md, "Slices", item 4.

## Decisions

- **demo-b4 is demo-b3's driver with a second script.** `src/demo_b3.zig` takes `--demo b3|b4`;
  both demos share the rig, the guest script and the TLS upstream (`src/demo_relay_tls.zig`).
  `build.zig` adds `demo-b4` beside `demo-b3`; `demo-b3-build` (in `check`) compiles the one
  executable and tests both scripts. In `.github/ci-changes.sh` whatever runs demo-b3 runs demo-b4
  too; `src/demo_b4*.zig` runs demo-b4 alone.
- **demo-b3's Debug builds are gone.** `built_debug` is removed; both demos run the binaries the
  build makes (CI: ReleaseSafe). botpike's upstream is a stock TLS 1.3 server (Python's `ssl`)
  that pins the cluster CA and the demo's job IDs. The host makes the upstream's CA and server
  certificate per run (keys derived from the run's unique work directory: test code, no
  `secure_random`), and copies them to the guest in 800-byte base64 chunks (a guest command is at
  most 1024 bytes).
- **openssl s_server has no SPIFFE allow-list.** mtls-interop's "another job" case on s_server
  asserts that the server sees the other job's ID; the JDK server, which has an allow-list,
  refuses it.
- **"No certificate" is the relay never dialing.** mtls-interop shows it as ZC-E0705 after the
  relay's connect timeout (shortened to 5 s in that test's limits), with no connection at the
  stock server.
- **The relay-stop fault on the real runtime** is root taking a copy of the relay's listener from
  the supervisor (`pidfd_getfd`) and shutting it down: the zigbox runtime has no `relay_stop`
  fault. It drives the same `ended_early` path as the fake runtime's fault.
- **The key search uses candidates from the supervisor's memory:** the 32 bytes before each copy
  of `relay.pub`'s public key, with at least 16 distinct byte values. The job looks for them raw,
  hex and base64 in its environment and under every mount it sees.
- **The cancel bound (10 s) is measured on the host,** which over-counts.
- **Each job's Python fits one argument** (`cli_arg_bytes_max`, 1024 bytes), which is why the
  fence row runs two jobs, `fence` (processes) and `net` (IPv6, UDP).

No user-visible bound, limit or default changed, and no code was registered.

## Not run

demo-b3 and demo-b4 need KVM; the cloud container has none, and the repository's workflows have
no `vm/*` scratch-branch trigger. Neither demo was run by the slice; CI's `demo-b3` and `demo-b4`
jobs run them once a pull request exists.
