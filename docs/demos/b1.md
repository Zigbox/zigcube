# B1 demo: what runs, what is asserted, and what is not

`zig build demo-b1 -Dbackend=sqlite|postgres [-Dtranscript=FILE]` is B1's demo run for real
(slice 10, `src/demo_b1*.zig`, brief [b1](../briefs/b1.md), "`demo-b1`"): `zcube-server`, two
`zcube-agent`s with `FakeRuntime` and the `zcube` command as separate processes, driven through the
command line as a person drives it. **A local pass is a check; the demo counts as demonstrated only
when its `demo-b1` CI job is green** (two jobs, one per backend, each keeping its transcript as an
artifact). It reuses `demo-c1`'s machinery (`demo_host.zig`, `host_procs.zig`, `demo_c1_state.zig`'s
node reads). The Postgres run uses the database like `demo-c1` (it drops the `zcube` schema before
and after) and does not stop it.

## The script

The server runs with `--lease-ttl-ms 8000`; `lost_grace_ms` is the default. The two agents
(`node1`, `node2`) have `--cpu-millis 1000` and state directories of their own. Every wait is
bounded by a named constant in `demo_b1_state.zig`, and a timeout names its step.

| # | Step | What it asserts |
| --- | --- | --- |
| 1 | `job run` of six jobs; `--wait` on each | exit 0 → `exited (code 0)`, `--wait` exits 0; exit 3 → `exited (code 3)`, exit 10; OOM (the fake runtime's fault file `oom`, written while it runs) → `failed (oom)`, exit 11; `--deadline 2s` → `failed (deadline)`, exit 11; cancelled while running → `cancelled`, exit 12; a 1 KiB input given in `IN` is the exit code (1024 / 128 = 8) and the CLI shows only `input: 1024 bytes, given as IN`, never its text. `job run` of the same spec again says `unchanged`; another command under the name is `ZC-E0131` (exit 1) and the job's state and revision do not change |
| 2 | Watcher killed and restarted (J4 in a real run) | a `zcube job watch` started before the first three jobs prints exactly those three endings, once each, and is killed (`kill -9`) after the third; the head revision is its bookmark; the next three end while no watcher runs; a watcher started from the bookmark + 1 prints those three, once each, and none of the first three |
| 3 | `kill -9` of the agent under a running job | the job's command lives on (host check); the restarted agent reports its ending: `exited (code 5)`; the command's marker file has one line (it was started once) |
| 4 | Power off the node under a running job (`kill -9` of its agent and of its supervisors' groups) | the job is `failed (unreachable)` after the lease ran out and the grace passed, `--wait` exits 11, `retries` is 0; for 3 s it is not started on the other node; `zcube why job` shows "the node of the run was lost and did not come back within the grace"; the node, restarted, is `ready` again |
| 5 | Five jobs of 500m on two nodes of 1000m | four run, two per node (host check); the fifth stays `pending` for 3 s and `zcube why job` says "no node fits 500m CPU and 128 MiB: 2 of 2 nodes lack the room"; when one of the four is cancelled the fifth runs |
| — | Cleanup | every process the demo started is gone |

## Cuts and deviations

- **Step 6 of the brief (`zcube job logs`) is cut**: slice 8 (logs) is not built (brief question 4),
  so the demo does not use it.
- **OOM is the fake runtime's.** `FakeRuntime` has fault files (`oom`, `pid_limit`, `lost`), and
  the demo says so in its transcript. A real OOM kill needs the Zigbox runtime: a smoke test on a
  Linux host, not this demo.
- **Step 5 uses `POST /v1/jobs`**, not `zcube job run`: the CLI has no flag for `limits`
  (slice 7). The jobs are otherwise the same. `jobs_per_node_max` (64) is not exercised here (129
  jobs would be needed); its bound is covered by the unit tests and the simulation.
- **The watcher's bookmark** is the job list's head revision (`GET /v1/jobs?limit=1`): the CLI's
  text output does not print revisions.
- Not shown (later milestones, as in the brief): the relay, identity, signed images, placement by
  tenant, API identity.
