# B6 demo: what runs, what is asserted, and what is not

`zig build demo-b6 -Dbackend=sqlite|postgres [-Dtranscript=FILE]` is B6's demo run for real
(slice 3, `src/demo_b6*.zig`, brief [b6](../briefs/b6.md), "The demo"): `zcube-server`, three
labelled `zcube-agent`s with `FakeRuntime` and the `zcube` command as separate processes. No KVM.
**A local pass is a check; the demo counts as demonstrated only when its CI steps are green**
(`demo-b6 on SQLite` in the `demos (sqlite)` job and `demo-b6 on Postgres` in `demos (postgres)`,
each keeping its transcript as an artifact). It reuses demo-b1's machinery (`demo_host.zig`,
`host_procs.zig`, `demo_b1_state.zig`'s job reads). The Postgres run uses the database like
`demo-b1` (it drops the `zcube` schema before and after) and does not stop it.

## The nodes

The server runs with `--lease-ttl-ms 8000`. Each agent has `--cpu-millis 1000` and a state
directory of its own.

| Node | Labels | Given by |
| --- | --- | --- |
| `node1` | `tenant=a` | `--label tenant=a` |
| `node2` | `tenant=a exclusive=tenant` | `--label tenant=a --label exclusive=tenant` |
| `node3` | `tenant=b` | `.labels = .{"tenant=b"}` in `node3.zon` (`--config`) |

Every job is `POST /v1/jobs` of `sh -c 'sleep 300'`, 128 MiB, with the CPU and, where stated,
`placement.require` `tenant=<x>`.

## The script

| # | Step | What it asserts |
| --- | --- | --- |
| 0a | Labels the agent refuses | `--label tenant=a` with a file whose `.labels` is `tenant=b` → `ZC-E0505` "the node's labels are given by --label and by .labels in the file, and they differ", non-zero exit; `--label exclusive=tenant` alone → `ZC-E0505` "an exclusive label names a key the node does not carry" |
| 0b | Start | the server answers; the three nodes are `ready` |
| 0c | Labels registered | `GET /v1/list?prefix=/nodes/` holds exactly the three nodes, each with the labels of the table above |
| 1 | Jobs for tenant a, then b | `a1`, `a2` (250m, require `tenant=a`) each run on `node1` or `node2`, and between them on both (least allocated), so the exclusive node takes its own tenant's job; `b1` (require `tenant=b`) runs on `node3`. Each is checked on the host: its container `<job>-job` runs on that node |
| 2 | Jobs with no placement | `node2` runs `a2` alone; `n1`, `n2`, `n3` (250m, no placement) each run, none on `node2`; then `node1` and `node3` each run two jobs or more, and `n4` (700m, no placement), which only `node2` has room for, stays `pending` for 3 s and `zcube why job n4` says "… 1 of them by the placement of the job" |
| 3 | A job for tenant c | `c1` (require `tenant=c`) stays `pending` on no node for 3 s; `zcube why job c1` says "no ready node has tenant=c"; it is cancelled |
| 4 | Power off a tenant=a node | the `n` jobs and `b1` are cancelled (node3 runs nothing, 1000m free); the node under `a1` (`node1`) is powered off (`kill -9` of its agent and of its supervisors' groups): `a1` reads `failed` no sooner than the ttl less one keepalive pass, `job get --wait` exits 11 with `end: failed (unreachable)`, `zcube why job a1` says "the node of the run was lost", and after 3 s it is still `failed` with 0 retries and not running on `node3`. Then `a3` (900m, require `tenant=a`) stays `pending` for 3 s although `node3` has the room, and `zcube why job a3` says "… 1 of them by the placement of the job"; when `a2` is cancelled, `a3` runs on the surviving tenant=a node; `node3` runs nothing, and none of `a1`, `a2`, `a3` has `status.node` `node3` |
| — | Cleanup | every process the demo started is gone |

## Cuts and deviations

- **"Its job ends `node_lost`"** (the brief) is, in the product, the ending `failed (unreachable)`
  with `zcube why job` saying "the node of the run was lost and did not come back within the
  grace": `node_lost` is the job controller's name for that path, not a state or ending the API
  shows. The demo asserts both texts.
- **Jobs are `POST /v1/jobs`**, not `zcube job run`: the CLI has no flag for `placement` (nor for
  `limits`, as in demo-b1). **Labels are read with `GET /v1/list`**: `zcube get nodes` does not
  show them, and `zcube job get` does not show a job's placement. These are CLI gaps, reported.
- **"No `a` job ever lands on the `b` node"** is asserted at each placement (host and server), at
  the end for every `a` job's `status.node`, and by `a3` waiting while `node3` has room. Every
  revision is not watched: that is check P1 of the simulation (slice 2).
- **The nodes are not relabelled** in the demo: relabelling is a reinstall with an emptied state
  directory ([agent.md](../agent.md#running-it)), and its effects are slice 2's P1 world.
- Not shown: `placement` on services and anti-affinity (the brief's non-goals).
