# B5: signed jobs

## demo-b5 (slice 4)

`zig build demo-b5 [-Dtranscript=FILE]` (`src/demo_b5.zig`, `src/demo_b5_script.zig`,
`src/demo_b5_inject.zig`, `ops/demo-b5/guest.sh`) runs on B3's rig (`src/demo_c2_vms.zig`, one
guest): the server on the host over SQLite, one QEMU guest whose agent runs `--runtime zigbox
--trust-policy` as root. It skips unless `ZCUBE_REAL_HOST=1`, and needs KVM and GHCR (demo-c2's
`python-app` v1 and v2).

0. **Signing, in the guest.** A signer's own Zigbox store and key directory (`/root/signer`, apart
   from the node's store) pulls v1 and v2 and makes two keys with `zbx key new --no-passphrase`,
   `release` and `stranger`. `zbx sign <v1 tree> --key release` and `zbx trust export <v1 tree>`
   give the good line; `zbx sign <v1 tree> --key stranger` adds a second, and the line that is
   not the good one is the stranger's; `zbx sign <v2 tree> --key release` and its export give the
   other-tree line. The server's policy (written on the host) and the node's (written in the
   guest) both trust `release` alone and set `require_signature`.
1. **Start.** `zcube-server --config` with `.trust = .{ .policy = ... }`; the agent with
   `--images` (both trees) and `--trust-policy`; the node joins.
2. **Signed, runs.** `POST /v1/jobs` with image v1 and the good line: 201, the job ends `exited`
   with code 0.
3. **Refused at the server.** The same request, unsigned; with the stranger's line; with the v2
   line: each answers 403 with ZBX-E0905, and `GET /v1/jobs/<name>` answers 404 after it.
4. **Refused at the agent.** The server is stopped (SIGTERM, exit 0). The demo opens the store
   itself and writes the same three jobs with `job_api.create` and no policy: the API's own
   validation, admission and write, with only the trust check left out. The server starts again;
   its job controller and scheduler make each run and its assignment, and the node's agent
   refuses each: `failed`, cause `refused`. `guest.sh containers` lists `<state>/zigbox/` (and
   fails if there is none) and holds no `<name>-job` for any of the three.

What was run where: the cloud container this slice was written in has **no KVM**, so demo-b5 was
**not run there**; it runs in CI (`demo-b5` job). Nothing in this file is a passed demo until that
job is green. What did run there, piece by piece:

- `guest.sh key-new`, `pull`, `sign` and `export` on the host, with `zbx` built from the pinned
  Zigbox and a pull from GHCR through the proxy: the two keys, both trees, one line after one
  sign, two after the second, one for v2.
- The real `zcube-server` with that policy and those lines: the good line 201, the stranger's
  line, no line and the v2 line each 403 with ZBX-E0905 and 404 after.
- The real `zcube-agent` (FakeRuntime, not the Zigbox runtime) with `--trust-policy` and the same
  lines, the server without a policy standing in for step 4's write: the good job `exited` 0 and
  was the only command that started; the other three `failed`, cause `refused`.
- `demo-b5-build` (in `check`): the demo compiles, and the store write of step 4 is tested
  against a real SQLite store (`src/demo_b5_inject.zig`).
- `ops/demo-b5/test-guest.sh` (in `zig build test`): the guest script's output the host parses.

### Cuts, gaps and deviations of slice 4

- **Jobs go through the API, not the CLI.** `zcube job run` has no way to attach a signature, so
  every job of the demo is a `POST /v1/jobs` with `signatures`. A `--signature FILE` flag would
  be new CLI surface; it is left for the owner to ask for.
- **"An assignment written straight into the store" is a job written straight into the store.**
  The demo writes the job record around the server's check and lets the server's own controllers
  write the run and its assignment. Writing an assignment by hand would mean forging a run, its
  epoch and the scheduler's decision, which tests the forgery more than the agent. What reaches
  the agent is the same: an assignment for a run whose job carries lines its policy refuses.
- **The server is stopped for that write.** The demo opens the SQLite file itself; two writers at
  once would race the server's watches for no gain.
- **No positive control for the container listing.** Whether a finished job's container
  directory is kept depends on the agent's cleanup, so the demo does not require `signed-job`
  to be listed; `containers` failing without `<state>/zigbox/` is what stops the check from
  passing on a wrong path.

### Zigbox, as pinned (0.5.0, aa4d64c)

- `zbx key new <name>` writes `$XDG_CONFIG_HOME/zbx/keys/<name>.{key,pub}`; there is no flag for
  another key directory, so the signer is set apart by its XDG variables.
- `zbx sign` needs the whole tree in the local store (hence the signer's own pull) and binds the
  operand: a `b3:` tree signs the tree.
- `zbx trust export <tree>` prints every stored signature of the tree, not one key's: the demo
  tells the stranger's line apart by difference. A `--key` filter on export would make that
  direct; it is not a gap that blocks anything.
