# B4: the relay's own identity

## demo-b4 (slice 4)

`zig build demo-b4 [-Dtranscript=FILE]` (`src/demo_b3.zig --demo b4`, `src/demo_b4_script.zig`,
`src/demo_relay_tls.zig`, `ops/demo-b3/guest.sh`) runs on demo-b3's rig (docs/demos/b3.md): the
server on the host over SQLite with cluster `demo.zcube.test` and the relay `botpike` pinned to an
upstream CA the host makes for the run, one QEMU guest whose agent runs `--runtime zigbox` as root,
and on the guest's loopback (127.0.0.1:9443) a stock TLS 1.3 upstream, Python's `ssl` over OpenSSL,
with `CERT_REQUIRED`, the cluster CA as its only trust anchor and an allow-list of the demo's jobs'
SPIFFE IDs. It logs each request with the client's URI and certificate (`der=<hex>`). The
binaries are the ones the build makes (CI: `-Doptimize=ReleaseSafe`). It skips unless
`ZCUBE_REAL_HOST=1` and needs KVM and a GHCR image (demo-c2's `python-app` v1).

Every job runs `python -c SOURCE NAME` (the trailing name lets the node's tools find it) with
`--relay botpike`. The real runtime does not capture a job's output, so each job reports through
its relay and the upstream's log is the evidence.

1. **Identity.** `identity` requests `/whoami` through `ZCUBE_RELAY` and exits 0. The upstream
   logs `uri=spiffe://demo.zcube.test/job/identity`; the host decodes the logged certificate
   (`x509.parse_profile`, `.cluster`) and its identity extension (`x509_identity.decode`) and
   asserts the URI, the image digest (the job's `b3:` tree) and the placement epoch (the job's
   epoch as `zcube job get` shows it), and prints the labels.
2. **No key bytes.** `keys` makes one request, then waits for candidates. Root on the node
   (`guest.sh key-candidates keys`) finds the job's supervisor through the job's listener,
   scans its memory for `relay.pub`'s public key and takes the 32 bytes before each hit (Zig's
   Ed25519 secret key is seed then public key) with at least 16 distinct byte values; the
   upstream serves them as `/candidates`. The job searches its environment (`os.environ` and
   `/proc/self/environ`) and every regular file under every mount in `/proc/self/mountinfo`
   (but `/proc`, `/sys`, `/dev`) for each candidate raw, as hex (both cases) and as base64
   (both alphabets), and reports `/keys?candidates=&files=&found=&first=`. Asserted: at least
   one candidate, at least one file searched, `found=0`.
3. **The fence.** `fence` reports `/fence?see=&outside=&ptrace=&mem=&others=`: processes it can
   see whose command line holds `zcube` or `zbx` (its supervisor, the agent), pids outside its
   own `/proc` that `kill(pid, 0)` finds (up to `pid_max`), other processes it can
   `PTRACE_ATTACH`, and other processes whose `/proc/<pid>/mem` it can read. Each must be 0.
   `net` (with `NODE_ADDR` in its environment) reports `/net?ipv6=&udp_internet=&udp_node=`: a
   TCP connect to `[2606:4700:4700::1111]:443` and a UDP send to 1.1.1.1:443 and to the node's
   address on 9091 (where the guest runs a UDP echo that logs `udp from`). Each must read
   `failed`, and the echo must have heard nothing.
4. **Cancel.** `cancelme` opens a connection through its relay and requests `/hold`; the upstream
   logs `hold-open` and holds it until EOF, then logs `hold-closed`. The host runs
   `zcube job cancel cancelme` and polls the log every 200 ms: `hold-closed` must appear within
   10 s of the cancel, measured on the host (an upper bound: it includes the polling and the
   guest command round trips). The job must end.
5. **Relay stopped mid-run.** `orphan` makes one request and sleeps. Root on the node
   (`guest.sh stop-relay orphan`) takes a copy of the relay's listening socket from the job's
   supervisor (`pidfd_open`, `pidfd_getfd`) and shuts it down, so the relay's accept fails. The
   job must end killed by a signal (`end_kind` `exited` with no code), and the container's
   `relay.log` must say ZC-E0702 and that the job's command was killed.
6. A summary: every assertion held.

Not run: the cloud container B4 slice 4 was written in has no KVM, and this repository's
workflows have no `vm/*` scratch-branch trigger, so demo-b4 was **not run**; CI's `demo-b4` job
runs it. Nothing in this file is a passed demo until that job is green. `demo-b3-build` (in
`check`) compiles it and checks that each job's script fits one command-line argument
(`cli_arg_bytes_max`); whether each parses as Python was checked by hand only.

### Cuts, gaps and deviations of slice 4

- **The fault that stops the relay is a pidfd trick, not a runtime fault.** The fake runtime's
  `relay_stop` fault (SIGUSR1 to the supervisor) does not exist under `--runtime zigbox`; the
  demo stops the real listener from outside instead, which exercises the same `ended_early`
  path (`src/relay.zig`).
- **The key search is as wide as the job's view.** Candidates come from the supervisor's memory,
  so the row proves the key that the relay actually uses is not in the job's files or
  environment; it cannot prove it is absent from memory the job cannot read (the fence row
  covers that: no other process's `mem` is readable).
- **The ptrace row is strict:** it counts any other process in the job's PID namespace the job
  can attach to. If the runtime ever puts a traceable helper (an init) inside that namespace,
  the row fails, which is the intended reading.
- **The cancel bound is measured on the host,** from before `zcube job cancel` to the poll that
  sees `hold-closed`; the true time is shorter.
- **mtls-interop's "another job" row on openssl s_server** asserts that the server sees the other
  job's SPIFFE ID; `s_server` has no allow-list. The JDK server refuses it
  (docs/decisions/2026-11-14-b4-slice4-demo.md).
