# C1 demo: what runs, what is asserted, and what is not

`zig build demo-c1 -Dbackend=sqlite|postgres [-Dtranscript=FILE]` is HANDOFF's C1 demo run for
real (slice 8, `src/demo_c1*.zig`, brief [c1-8](../briefs/c1-8.md)): `zcube-server`, three
`zcube-agent`s with `FakeRuntime` and the `zcube` command as separate processes, driven through the
command line as a person drives it. Nothing is simulated. **A local pass is a check; the demo
counts as demonstrated only when its `demo-c1` CI job is green** (two jobs, one per backend, each
keeping its transcript as an artifact). It reuses `demo-c0`'s machinery (`demo_host.zig`,
`host_procs.zig`). The failover runs of slice 10d, below, are a separate test
(`test-store-faults`), not part of it.

## Cuts

- **The `/job-observed/` sweep of job retention.** One pass reads at most `observed_pages_max`
  (64) pages, 32,000 keys. A longer scan is reported (ZC-E0302, `Cursor.truncated`) and the sweep
  resumes from the last key on the next pass, so it covers any number of keys over several
  passes; a job is deleted only when it was old at the start of the cycle that read to the end,
  and until the first cycle ends no job is deleted. Within a pass an ended job's own node's
  observation is deleted by key. Not tested at a scale past this bound in a demo.
  `docs/decisions/2026-11-08-observation-cut-and-unreadable-report.md`.

## The script

The server runs with `--lease-ttl-ms 8000` (the default is 10 s; this shows the timeout is
configurable and shortens the run); `lost_grace_ms` is the default 1 s. The three agents have state
directories of their own under the run's directory. `node1` reaches the server through a fault
proxy (`testing/fault_proxy.zig`); `node2` and `node3` connect directly. Every wait is bounded by a
named constant in `demo_c1_state.zig`, and a timeout names its step.

| # | Step | What it asserts |
| --- | --- | --- |
| 0 | Start | the Postgres schema emptied (SQLite: a new file); the server and the three agents start |
| 1 | Three agents join | `zcube get nodes` lists `node1..node3` `ready` with capacity `4000m / 8.0Gi`, each lease with a ttl of 8000 ms (`s/8s` in the table) |
| 2 | `zcube apply` of `hello`, 6 replicas | 6 running; two per node in `get replicas -o wide`; the host runs 6 commands under 6 supervisors, two under each agent, each supervisor leading a session and group of its own and a child of its node's agent |
| 3 | Power off `node3` (`kill -9` of its agent and of its supervisors' groups, as `demo/kill-node.sh`) | `node3` reads `lost` between `ttl − ttl/3 − 1 s − 250 ms` (the last keepalive was at most one keepalive interval before the kill) and `ttl + 250 ms + 2 s` after the power-off; `hello` is 6/6 again within `ttl + lost_grace_ms + 5 s`, under new ids (owner decision), none on `node3`; the survivors' four original commands are the same processes; `zcube why node node3` prints "(ttl 8000 ms) ran out", "the server last heard from it N ms ago" with N between the ttl and ttl + 2.25 s, and the node controller's decision; the store holds one `mark_lost` decision for `node3`, cause `lease_expired`, evidence `ttl_ms` 8000 and `last_heard_ms` present |
| 4 | Restart `node3` | it registers under a new tenure with no container and no replica assigned; for 3 s nothing moves (the same 6 ids on the same nodes); `zcube why node node3` says it is ready, registered again, and that replicas are not moved back (no rebalancing) |
| 5 | Partition `node1` (the proxy drops traffic both ways; its agent stays alive) | below |
| 6 | Local mode | on copies of the executables, `zcube local up` starts a server and an agent; `zcube apply hello.zon` reaches 3 running; `zcube local down` stops both; the demo stops the containers |

**The partition test (step 5).** Asserted from process facts on the host, polled every 25 ms. `P`
is the moment the demo told the proxy to drop traffic; `s`, the send time of the agent's last
acknowledged keepalive, is not observable. The server's expiry `E` of the lease (read from
`zcube get nodes` 200 ms after the cut, when no keepalive can land any more) is at or after
`s + ttl`, and the agent fences at `s + ttl − fence_margin`, so the bounds are stated against `E`:

- the agent is still running at the end (it fenced; nobody killed it);
- every command of `node1` is dead by `E − fence_margin + fence_stop + kill latency` (`E − 100 ms`
  with these constants), within 250 ms of tolerance for the poll, and in any case before `E`. An
  agent that ignored `fence_margin` (fencing at `s + ttl`) fails this; a bound counted from `P`
  would let it pass;
- the first replacement runs no earlier than the server's expiry of the lease plus `lost_grace_ms`
  (the expiry is read from `zcube get nodes` 200 ms after the cut, when no keepalive can land any
  more), within 250 ms of tolerance;
- the last old command died before the first replacement was seen, and in no poll did an old
  command and a replacement run together (the number of polls is printed);
- 6 replicas run, none on `node1`; `node1` reads `lost`;
- after the heal (connections reset first, so nothing held back arrives late) the agent registers
  again under a new tenure with nothing assigned, prints `warning[ZC-W0501]`, and an observed
  write under the old tenure is refused with 503 `ZC-E0510` (I2).

**Not covered, and why.** Server and agent restarts, the broken digest and the store outage are
`demo-c0`'s and are not repeated. A second server, rebalancing and the Postgres failover are out of
scope for C1's demo (the failover is `test-store-faults`, below). The partition is `node1` only, and
one fence timing is asserted, not a sweep of them; the simulation fleet and `sim-cluster` cover the
rest. The lease timeout is read from the CLI, not from a stored decision record. Container
processes are plain host processes; no isolation is tested.

**Cuts and deviations.** Three places where the demo differs from HANDOFF's text or the brief.
HANDOFF's step 3 says the replacements run "within the lease timeout"; the demo asserts that
`node3` reads `lost` within the lease timeout (plus the controllers' pass) and that 6 replicas
run again within `ttl + lost_grace_ms + 5 s`, since replacement waits for `lost_grace_ms` and
the controllers' and agents' one-second passes. `zcube why node` prints the decision's cause
("node node3 is lost: its lease 3 (ttl 8000 ms) ran out") rather than the string `mark_lost`, so
that is asserted from the CLI, and the `mark_lost` record is read from the store. The lease expiry
of the partition test is read with `zcube get nodes` (the brief said `GET /v1/leases`, which the
demo does not call).

**Running it.** `zig build demo-c1 -Dbackend=sqlite`, or `-Dbackend=postgres` (with `-Dpostgres=`
or `ZCUBE_TEST_POSTGRES`, as `test-store`; the demo owns that database's `zcube` schema). About
35 s.

## Failover (slice 10d)

**The supported setup.** One primary. High availability only through a **synchronous** standby:
`synchronous_commit = remote_apply` (or `on`) with the standby named in
`synchronous_standby_names`, so a failover never loses an acknowledged commit. Only
`remote_apply` is run here: `on` (the standby has flushed the commit, not yet applied it, and
promotion replays it) is supported on Postgres's word and untested. Nothing reads from
a replica: no reader endpoint, no pooler that routes reads. An asynchronous standby is not
supported: a failover to one can lose acknowledged writes, and the server then halts with
`ZC-E0215` rather than act on the older store (`docs/operations.md`).

**What runs.** `zig build test-store-faults -Dbackend=postgres` ends with two failover runs
(`src/store_failover.zig`; `-Dfailover=false` leaves them out). Each makes a primary and a
streaming standby on the machine with `pg_dev pair-up sync|async` (Postgres 16 programs, as
`zig build pg-up`), routes the standby's replication through a fault proxy `R`, and starts a real
`zcube-server` on the primary through a client proxy `C`. 10c's four recorded clients and its
watcher load a store of their own on the same primary through `C`, and the run applies a service
through the server so the server's own revision moves. A quarter of the way through the load the
run holds the clients (so a slow machine stretches the run rather than letting the load end
first) while the server sees and saves 20 more revisions, releases them, and cuts replication off
(partitions `R`) for a 300 ms window in which it counts the clients' acknowledged writes. Then it
fails over: `C` black-holes new connections, the primary is crashed (`pg_ctl -m immediate`), the
standby promoted, `C` repointed at it and healed.

The pair runs with `fsync` off (as `pg-up` does): sound for the process crash `-m immediate` makes,
whose written WAL stays in the page cache, not for a host crash, which is not tested. Each mode's
scratch is `.zig-cache/store-failover-<mode>`, with the server's pid: a run killed with SIGKILL
leaves the server to the next run of that mode, which kills it first. The pair's default ports and
directory come from a hash of the working directory, so two worktrees can run it at once.

| Run | Before the failover | Asserted after it |
| --- | --- | --- |
| `sync` | the primary reports the standby `sync`; the server sees 20 revisions past the moment held and saves its pair; then `R` is cut and the primary acknowledges **no** write in the window (each commit waits for the standby), so the crash lands mid-commit; clients are still running at the failover | the clients finish on the promoted standby, with at least one write of unknown outcome (the commit in flight at the crash) and at least 20 writes acknowledged after the heal; the history checker passes over the whole run (no acknowledged write lost, compare-and-set linearizable across the switch); the server answers `store.ok` with a remembered revision at least the one before, and an apply succeeds |
| `async` (the teeth test) | `R` is partitioned first, so no WAL after that moment reaches the standby; the server sees 20 more revisions and saves them; the window sees writes acknowledged | the promoted store's revision, read right after promotion, is below the server's remembered one (the loss is certain, not lucky); `POST /v1/apply` is refused, 502 with `ZC-E0215`, before any status call (the write path on its own); then `GET /v1/status` answers `store.ok: false` with `ZC-E0215` naming the store's revision; a restarted server starts halted with the same diagnostic; the promoted store's revision has not moved; the history checker reports `lost_write` over the promoted store's log |

**Mutation checks** (by hand, 2026-11-02, reverted): the `sync` run on an asynchronous pair fails
at the window ("the primary acknowledged 22 writes its synchronous standby could not have
applied"), and with that check off too the history checker rejects it (`event_mismatch`); a
`VerifiedStore` whose comparison accepts everything fails the `async` run ("an apply on the
promoted store answered 200, not 502 with ZC-E0215").

**Not covered.** Automatic failover, or a multi-host connection string in the server (the test
moves the address, as a virtual IP or DNS name would). Recovery after the halt
(`zcube store accept-rollback --confirm`, tested in 10b). Reads from a standby, poolers, logical
replication, OrioleDB. 10c's random fault schedule during the failover (the failover is the
fault). The daily run of the failover runs in the simulation fleet is slice 9's, as follow-up.
