# C2 demo: what runs, what is asserted, and what is not

C2's demo script (`zig build demo-c2`) is not written yet. This document records what the real
Zigbox runtime's smoke (`zig build zigbox-smoke`, C2 slice 1) runs and asserts. **A pass of the
smoke is a check, never `demo-c2`.**

## `zigbox-smoke`

`ZCUBE_REAL_HOST=1 zig build zigbox-smoke -Doptimize=ReleaseSafe` (`src/zigbox_smoke.zig`,
`ops/zigbox-smoke/guest.sh`) needs QEMU and `/dev/kvm`; without `ZCUBE_REAL_HOST=1` it prints a
skip. It boots Zigbox's pinned Ubuntu 24.04 guest through the `zigbox_vm` module, provisions the
ordinary user `cube` (subuid range, lingering, the userns sysctl), copies in `zcube-server`,
`zcube-agent` and `zbx` (only for `zbx doctor` in a failure's log) and runs `guest.sh` one stage
at a time as `cube`. The server uses the memory store; the agent runs `--runtime zigbox` with
`ZBX_REGISTRY_MIRRORS=mirror.gcr.io`. The images are Zigbox's own pinned ones
(`src/testing/vm/zbx.lock` in Zigbox): `alpine:3.20` and `python:3.12-slim`, each with its manifest
digest and the locked tree. CI runs it as the `zigbox-smoke` job (KVM, 15-minute timeout).

| Stage | Asserted (each with a timeout) |
| --- | --- |
| setup | `zbx doctor` passes; the server answers; the agent starts under `--runtime zigbox` |
| replicas | 2 replicas of a pulled Alpine image (limits 500 millicores, 128 MiB) are running and observed `running`; each PID 1's cgroup has `memory.max` 134217728 and `cpu.max` `50000 ...` (read from `/sys/fs/cgroup`); each container's `/proc/<pid>/net/dev` lists only `lo` |
| kill | `kill -9` of one container's PID 1: replaced within 90 s, the other untouched |
| restart | stop the agent: containers keep running; start it: the same PIDs, the same number of supervisors, both observed `running` |
| oom | a container that fills a 32 MiB limit (`sh -c 'sleep 4; exec tail /dev/zero'`) is seen to end as `oom`: observed `stopped` with exit `oom`, or a controller decision whose `cause_evidence` says `oom` (the observed record is deleted at once, see below). On a timeout the stage dumps `zbx ps --all --output json`, the run-record count, what was observed and decided |
| refusals | a digest whose pull gives another tree is held with `ZC-E0511`; a service with no `source` whose tree the node does not have is held with `ZBX-E0410` |
| scale0 | a service on a not-yet-pulled image (`python:3.12-slim`) is deleted while its supervisor runs; the agent stays up and `box` is undisturbed (regression for the pid-0 fix) |

## The oom stage, and what the first runs showed

The first CI runs timed out waiting for `stopped oom`, though the guest kernel log showed the hog
OOM-killed every round. Read from the run of c6ad983: each round the kernel killed **two**
processes in the container's memory cgroup, `tail` and a `zcube-agent` of 51 MB. That one is
Zigbox's scope keeper (`Session.spawn_keeper`): a fork of the supervisor, so it carries the
supervisor's touched pages, and it lives in the scope for the container's life. So a container
limit below about 50 MiB makes the OOM killer take the keeper first; the container still ends as
`oom` (the scope's `oom_kill` counts), so this is noise, not the cause. Not fixed here; for the
owner: the keeper's footprint counts against a container's limit (see the owner question).

The likely cause of the timeout is the stage's witness, not Zigbox: `docs/keys.md` has the replica
controller delete an ended replica's observed record and replace it at once (no restart backoff),
so `stopped oom` is observed for an instant a 1 s poll can miss. The stage now also accepts the
decision that replaces the replica, which keeps the exit in `cause_evidence`. CI run 41574896046 (ac94f8a) confirmed it: the hog was then seen as `stopped oom` within 14 s.
It also confirmed the record pruning: with the `sh -c` wrapper dropped there were 47 hog replicas
in those 14 s, and box was left `starting`. So the sleep that paces the restarts stays.

### Owner questions

- Zigbox keeps at most 32 run records and prunes the oldest, live ones included. With no restart
  backoff in Zigcube a crash-looping service churns records fast. Should Zigbox skip live runs when
  pruning, or should Zigcube add a restart backoff (policy; not invented here)?
- The scope keeper is a fork of the supervisor and so counts about 50 MB of resident memory in the
  container's cgroup. Should the supervisor's footprint be smaller (its 60 MiB `Storage` is
  touched by `network_memory.init()`), or the keeper start from a small process?

## Cuts and gaps

- **`pid_limit` and the pids cgroup limit are not tested.** `POST /v1/apply` takes `cpu_millis` and
  `memory_bytes` in `limits`, not `pids`; the runtime carries a `pids` limit, but nothing sets it. A
  fork bomb would not end as `pid_limit`. Adding `pids` to the service is a change to `docs/api.md`
  (Ask first); until then this is not reachable from a service.
- **`stop` with a grace** is not tested.
- **The network check reads `/proc/<pid>/net/dev`** instead of running `ip link` in the
  container's namespace (an Alpine image has `ip`, but entering the namespace from the host needs
  `nsenter`'s user-namespace flags; the interface list is the same).
- **The tree is pinned, not learned.** The locked trees come from Zigbox's `zbx.lock`; a changed
  tree fails the `replicas` stage with ZC-E0511 naming the tree that came.
- **KVM only.** The stage timeouts assume KVM.

## Slice 2 (`source`): cuts and open questions

- **The `zigbox_image` table case was dropped.** The brief asked for one case showing that
  Zigbox's `parse_reference` diagnostic is kept when apply's prefilter accepts a reference that
  Zigbox refuses. `src/zigbox_image.zig:259` already covers the kept diagnostic; a second case
  would test the same path.
- **Owner question: "full on hover".** The brief says the console shows `source` under the rule
  "shortened, full on hover". `docs/console.md` (Accessibility) says "No hover-only information".
  The console follows the existing `image` precedent (full value in the `title`) and also shows the
  full value on the service detail page, where it is not hover-only. Which rule wins is the
  owner's to say.
- **`ops/zigbox-smoke/guest.sh` uses `source`** (review item 1, done after #37 merged). Its services carry `source` and the agent has no `--images`; `cached`, a service without `source` whose tree is already in the node's store, keeps the fallback path covered. Not run here (needs KVM); CI runs it.

## Slice 5 (`locality`): deviations, cuts and rollback

- **L1 checks spread only.** The simulators' locality check (`scheduler.placement_problem`, L1)
  fails a placement only when a rival node that was no worse on fit and carried fewer of the
  service's replicas existed, judged over the head of the store but counting only rivals whose
  node, status, allocation and audit records are no newer than the decision's `read_revision`
  (a rival that changed after the scheduler read is a lost race, not a wrong placement). It does
  not check that the chosen node had the most `locality_bytes` among equals; that is covered by
  the scheduler's unit tests.
- **L1 runs in `sim-c1` only** (and its teeth, `sim-c1-teeth-locality`), not in `sim-c0` or
  `sim-cluster`, which have no `/node-store/` records.
- **Rolling back from C2 to C1 is unsupported.** A placement decision of C2 is written as
  `Decision` v3 (it carries `locality_bytes`); a C1 reader refuses a v3 decision as too new
  (ZC-E0303). Decisions without locality members are still written as v2.
- **A refused summary write does not stop the agent.** A C1 server answers `404` to the summary
  endpoint; the agent notes ZC-E0504 once on stderr, keeps working and retries the write on a later
  step. `zcube-agent` against a C1 server therefore works, with no locality.

## demo-c2

`zig build demo-c2 [-Dtranscript=FILE]` (src/demo_c2.zig) runs SPEC's C2 demo for real. It is
skipped unless `ZCUBE_REAL_HOST=1`, since it boots four QEMU guests and pulls images from GHCR.
CI runs it in the `demo-c2` job, on a KVM runner, with `-Doptimize=ReleaseSafe`. The job keeps
`demo-c2.txt` and the transcript as the artifact `demo-c2-output`.

### The pieces

- **Server.** `zcube-server` runs on the host over SQLite, on `127.0.0.1:P`. The `zcube` command
  also runs on the host. Every assertion reads its JSON output: `-o json get replicas`,
  `stats pull` and `why replica`. The rules are in src/demo_c2_check.zig, which has unit tests.
- **Guests.** Four guests boot together through Zigbox's `zigbox_vm`
  (src/demo_c2_vms.zig). Each is an Ubuntu 24.04 guest with 2 GiB and 2 vCPUs, plus `uidmap`,
  `passt` and `nftables`. The demo copies in the stripped `zcube-agent`, `zbx` and
  `ops/demo-c2/guest.sh`.
- **Agents.** Guest *i* runs one `zcube-agent --runtime zigbox --server 10.0.2.2:P` as root
  (M3's gap 2, below). Every `guest.sh` command runs as root; `cube` only owns the copied
  files. Its peer server listens on guest port 7071. The host forwards host port
  H_i to that port (`hostfwd`, Z7), and the agent advertises `10.0.2.2:H_i`. Node4's agent
  starts only in step 4.
- **Waits.** A `zigbox_vm` session moves only while it is pumped, so every wait in the demo
  pumps all four guests.

### Bytes, not time (O4)

Peer traffic goes guest → host → guest, through two QEMU user-mode stacks. The byte counts are
honest about what crossed the network. The timings are not, because a peer on a real LAN would
be far faster than this relay. The demo therefore asserts bytes only (`stats pull`), and the
durations it prints are not claims.

### Steps and what each asserts

0. **Start.**
   - The server comes up.
   - `guest.sh setup-root` on every guest: `root:200000:65536` in `/etc/subuid` and
     `/etc/subgid`, so Zigbox maps the full range through `newuidmap` rather than a single id
     (ZBX-W0201), and `loginctl enable-linger root`, so `user@0.service` gives root the user bus
     at `/run/user/0/bus` that Zigbox's scopes need.
   - The trees of v1 and v2 are learned on guest 4 (see below), and the demo checks that
     node4's own store is empty.
   - Agents 1-3 start. The demo waits for 3 `/node-store/` records, then shows `get nodes`.
1. **python-app v1, 3 replicas, on three empty nodes.**
   - 3 replicas of v1 run, one each on node1, node2 and node3.
   - Each node has a pull record for v1.
   - `registry_once`: exactly one node shows registry bytes. The other two show 0 registry bytes
     and more than 0 peer bytes.
2. **Roll to v2.**
   - 3 replicas of v2 run, and each node has a pull record for v2.
   - Each node transferred at most 1 MiB for v2, from the registry and peers combined. v1 and v2
     differ only in `app.py`, which sits in a layer of its own
     (docs/decisions/2026-11-04-demo-c2-images.md).
3. **node3 cannot reach a registry, and node1 corrupts what it serves.**
   - A new service, `alpine-box` (Zigbox's pinned Alpine, through `mirror.gcr.io`), runs 2
     replicas. Both land on node1 and node2, so node3 is checked to have none.
   - The demo writes the test-only fault `<state>/faults/peer-corrupt` on node1 and restarts
     that agent, because the peer server reads the fault when it starts.
   - As root on guest 3, `guest.sh block-registry` adds an `nft` output rule: loopback and
     10.0.2.2 are accepted, and every other TCP connection is dropped. It lists the rule and
     records a `curl` to `ghcr.io` and to `mirror.gcr.io`, each of which must fail.
   - `alpine-box` is scaled to 3, so its third replica goes to node3. The demo asserts that it
     runs, that node3's pull record shows 0 registry bytes and more than 0 peer bytes, and that
     `bad_peers` names node1.
   - Node3's fetch log must contain ZC-W0601. This is the corrupted-chunk criterion.
   - Finally the fault is removed and node1's agent is restarted.
4. **node4 joins empty.**
   - Agent 4 starts, and the demo waits for 4 node records.
   - A **new service on the same image**, `python-warm` (v2, 1 replica), is applied. Spread ties
     across all four nodes, so locality decides. The demo asserts that the replica is not on
     node4, and that `why replica` has a `place_replica` decision with `locality_bytes > 0` whose
     reason includes "of the image already there".
   - Then python-app is scaled to 4. The new replica must run on node4, because spread comes
     before locality (O2 and SPEC's second criterion).
   - Node4's pull record of v2 is printed, and the demo asserts that v2 came from peers alone.
5. **Summary.** `zcube stats pull` prints every record. The demo passes only if no rule was missed.

A rule that does not hold is a *miss*. The transcript says `MISSED in step ...`, and the demo
carries on so that one run gathers all the evidence; the run fails at the end. A wait whose
result a later step needs, and does not get, ends the run at once. On failure the demo prints,
for each guest, the agent log, the fetch logs and the processes, then the server's log.

### Deviations and cuts

- **The trees are learned, not pinned.** The tree digest Zigbox gives an image depends on the
  host it is pulled on: a root pull on the build host gave a different python tree than the
  guest does. So `guest.sh learn` pulls v1 and v2 on guest 4 as root, into a scratch store
  that it deletes afterwards. Node4's own store stays empty, and `store-empty` checks that.
  Alpine's tree is the one in Zigbox's lock file, which the smoke already uses in this guest
  image.
- **Step 3 uses Alpine, not a third python image.** Node3 must start "its first replica" of an
  image it does not hold while the registry is cut. After step 2, node3 holds both python trees,
  so a new image is needed, and Zigbox's pinned Alpine is one the guests already pull.
- **The firewall rule lives in the guest (O4, decided).** With user-mode networking, the QEMU
  process makes the guest's outbound connections. The rule is therefore an `nft` rule inside
  guest 3, and a failing `curl` is recorded as evidence.
- **Extra check.** Step 1 asserts that the replicas spread one per node, and step 4 asserts that
  spread wins over locality for an existing service.
- **Not covered here.** "Locality never overrides fit" is covered by `sim-c1`/`sim-swarm` and the
  scheduler's unit tests, not by this demo.

### Known gap: "registry once" with simultaneous starts (O5)

O5 (decided 2026-11-03) says: of the nodes fetching a tree, the one with the lowest
`hash(node, tree)` pulls from the registry, and the others wait up to `fetch_peer_wait_ms` for
peers. `fetch_plan` has that wait for chunks.

The Zigbox-mode fetch (slice 8, `zigbox_fetch.find_bundle`) does not have it. It asks each peer
once for a bundle and returns `TreeUnavailable` when none has one, and the supervisor then pulls
from the registry right away.

In step 1 the three replicas start together, so every node may pull v1 from the registry, and
`registry_once` would miss. This is slice 8's code, which slice 9 must not change. The run's
transcript is the evidence, and the fix belongs to a follow-up on the fetch path.

### Blocking gap: the pinned Zigbox cannot serve these images to peers (M3)

Slice 8's M3 (docs/decisions/2026-11-04-c2-slice8-review-fixes.md) records two gaps in the pinned
Zigbox:

- **Gap 1.** A peer server reads `Damaged` for a one-chunk object whose owner on the host is not
  its owner in the container. For a root agent with the full id map, that is any container id
  other than 0. For an agent that is not root, it is every one-chunk object.
- **Gap 2.** A peer server that is not root cannot open an object owned by an id in its range
  when others may not read it.

Either way, the peer fetch fails with ZC-E0601, and the supervisor's pull falls back to the
registry.

The demo's own images hold such objects. The layers were listed from the registries on
2026-11-04 (file entries only):

- **python-app v1** (`c0373ee9...`), base layer `6fc242d221a6`:
  - owned by container gid 42: `etc/gshadow` (364 B, 0640), `etc/shadow` (474 B, 0640),
    `usr/bin/chage`, `usr/bin/expiry` and `usr/sbin/unix_chkpwd` (0 2755);
  - owned by gid 43: `var/log/btmp`, `lastlog`, `wtmp`;
  - mode 0600 or 0640, owned by 0: `etc/passwd-`, `var/cache/debconf/passwords.dat` and the
    dpkg lock files.
- **python-app v1, layers `3eb771151506` and `f574edac59d9`:**
  - `var/log/apt/term.log` (gid 4, 0640, 2388 B and 46999 B);
  - `var/cache/ldconfig/aux-cache` (0600).
- **Alpine 3.20** (step 3): `etc/shadow` (0:42, 0640, 260 B) and `etc/crontabs/root` (0600).

`etc/shadow` and `etc/gshadow` are one-chunk objects owned by a container id other than 0. So
gap 1 applies even to a root agent with the full map.

- **Step 1 fails.** No node can serve v1 to a peer, so every node pulls it from the registry,
  and node2 and node3 show no peer bytes.
- **Step 3 fails.** Node3 cannot get Alpine from a peer, and its registry is blocked, so its
  replica does not start.
- **Step 2 is likely unaffected.** v2's only new object is `app.py`, owned by 0 and world
  readable. The damaged objects are already held from v1, so they are not fetched again.

The fix is Zigbox's, and slice 9 does not work around it. Gap 2 stays open, so the agents run as
root (setup in step 0), which leaves gap 1 alone. Gap 1 is fixed in Zigbox as Z9 (branch
`claude/z9-chunk-owner`); it reaches this demo with a Zigbox release and a move of the pin.

**Until then, steps 1 and 3 are expected to miss, and step 4's "node4 fetched v2 from peers
alone" too** (node4 fetches the whole v2 tree, v1's base layer included, and falls back to the
registry). Every other rule must hold. Each of those misses is followed in the transcript by
`evidence for Zigbox gap 1 (Z9)`, which shows exactly what stands between the demo and green:

- `guest.sh one-chunk-owners <tree>` on node1, which holds the tree: `zbx run <tree> -- find /
  -xdev -type f -size -1025k -exec stat ...`, i.e. every non-empty file of at most one chunk
  (1 MiB) whose owner inside the container is not `0:0`, with its mode, size and path, and the
  count;
- node1's peer-server and fetch log lines that say a chunk did not match (`does not match`,
  `Damaged`);
- the fetching nodes' `ZC-E06xx`/`ZC-W06xx` lines (fetch logs and `agent.log`).

When the pin moves, a run whose only misses are these, each with that evidence, is the gap; a
miss without it, or any other miss, is something else.

**First run as root (CI run 41882361666, fc5491b).** The whole flow ran end to end in about
13 minutes. Steps 0 and 2 held, and so did every rule of step 4 except "from peers alone". The
four misses were exactly those listed above, and each was followed by its evidence. For v1
(`b3:2eb472a4...`), 6 of 4399 one-chunk files are not `0:0`: `/etc/shadow` and `/etc/gshadow`
(`0:42 640`), `/var/log/apt/term.log` (`0:4 640`), and `/usr/sbin/unix_chkpwd`, `/usr/bin/expiry`
and `/usr/bin/chage` (`0:42 2755`). For alpine, 1 of 87 is not: `/etc/shadow` (`0:42 640`). Every
node pulled from the registry with 0 peer bytes, and `stats pull` shows no struck peer.

**The fetch logs stay empty, and that is slice 8's fetch, not the demo.** When a peer answers the
bundle request with an error (node1's 500, "the chunk on disk does not match its hash"),
`find_bundle` in `src/zigbox_fetch.zig` skips that peer without a log line or a strike. With no
peer left it returns `TreeUnavailable`, and the supervisor pulls from the registry, which leaves
no trace in `fetch.log` either. So the only evidence in the transcript is the owner list, and the
peer's refusal is not visible. ZC-W0601 is raised on the chunk path (`fetch_chunks` through
`fetch_worker`), which runs only after a bundle is received. Once Z9 lets node1 serve the bundle,
step 3's corrupting node1 should therefore be struck with ZC-W0601 as designed. A log line for a
peer that refuses the bundle would be a slice-8 change, and slice 9 is not allowed to make it.
