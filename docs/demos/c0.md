# C0 demo: what is demonstrated, and what is not

**`demo-c0` does not exist yet.** It needs `zcube-server`, `zcube-agent`, the `zcube` command,
`FakeRuntime` and the Postgres and SQLite wiring, none of which is built. Nothing here has passed
the demo.

## What exists in its place (C0 slice 5a)

`zig build sim-c0` is a deterministic **simulation** of the demo's steps against the core, a memory
store and a simulated runtime on virtual time ([core.md](core.md) says what it proves). It is
not the demo and is never reported as one.

| Demo step | In the simulation |
| --- | --- |
| 1. apply `hello`, 3 running | asserted |
| 2. `kill -9` one, replacement | asserted (a runtime fault, not a host process) |
| 3. scale to 5, back to 2 | asserted; the three that ran stay when scaling up |
| 4. `broken`, `zcube why service broken` | asserted, including the rendered chain |
| 5. store down, `zcube get`, `zcube bundle --last` | the API's answer with the store down is asserted (503, `ZC-E0201`, a fix); the CLI and the bundle do not exist |
| restart server / agent mid-run | asserted: nothing duplicated, nothing lost |

## What slice 5b added (still not the demo)

`zcube-server` exists (HTTP, the embedded console, the controller driver, SQLite and Postgres
wiring), and the console runs on the real core in WebAssembly. Still **no `zcube` command and no
`zcube-agent`**, so the steps that need a process, `kill -9` or `zcube apply <file>` cannot run:

| Demo step | What now runs for it (not the demo) |
| --- | --- |
| 1. apply `hello` | `POST /v1/apply` against the real server on SQLite; a simulated agent in the test runs the replicas |
| 5. store down | against a real Postgres, stopped and started under a running server: `/v1/status` says `ok: false` with `ZC-E0201`, the API answers 503, the driver reports once and recovers (run by hand, not automated) |
| restart server | automated: `zig build test` restarts the server on a SQLite file and compares every key and revision |
| the console | Playwright (`tools/browser_check.mjs`) against the server and against `?sim=c0`; dev-time, not in CI |

## What slice 6b added (still not the demo)

The `zcube` command ([cli.md](cli.md)) and the diagnostics machinery of DIAGNOSTICS.md exist.
Still **no `zcube-agent`** (slice 6a) and **no `demo-c0`** (slice 6c). What now runs, in
`zig build test`, with a *simulated* agent over the same store:

| Demo step | What runs for it (not the demo) |
| --- | --- |
| 1. `zcube apply hello.zon`, `zcube get service hello` | `src/cli_test.zig`: the command line in-process against a live `zcube-server` on SQLite; `3/3` after the simulated agent has run them |
| 3. `replicas = 5`, back to 2 | the same test: the diff is shown (`replicas 3 → 5`), then applied; `5/5`, then `2/2` |
| 4. `zcube why service broken` | the same test: the chain, byte for byte, with the `ZBX-E0501` block |
| 5. the store is down, `zcube get`, `zcube bundle --last` | the unreachable server (`ZC-E0102`) and the bundle of it are tested; a store that is down behind a running server is the server's own `ZC-E0201`, relayed unchanged (a golden), but **stopping a real Postgres under a running server is not automated here** |
| the diagnostics acceptance | golden tests for every `ZC-` code, the no-stack-trace test, the bundle redaction test and fuzzer, `errors-site-check` |

What was run by hand, with the real binaries (`zcube-server` on SQLite and `zcube`): apply, get, why
in the three output modes, a server that is not there, the bundle of that failure, a server that
accepts and says nothing. `kill -9`, an agent restart and the Postgres outage were **not** run.

## Cuts recorded

- The chain's middle line is api.md's sentence ("replica broken-1 failed to start on node1; it
  was not replaced because a new one would fail the same way"), not HANDOFF's "pending on node1";
  api.md wins where they differ.
- The diagnostic's digest is shortened with `...`, not `…`, and its fix says "the service file",
  not "broken.zon": diagnostics are printable ASCII, and the runtime does not know the file name.
