# C0 demo: what runs, what is asserted, and what is not

**`zig build demo-c0 -Dbackend=sqlite|postgres` is HANDOFF's C0 demo, run for real.** It starts
the processes a deployment runs, drives them through the `zcube` command line as a person would,
asserts every outcome HANDOFF names and prints a transcript. Nothing in it is simulated.

> **Status.** The demo exists and passes locally on both backends (the runs are in
> [Reliability](#reliability)). It is **not reported as demonstrated** until its two CI jobs,
> `demo-c0 (sqlite)` and `demo-c0 (postgres)`, are green on `main`; the README and the site say
> so, not this page. The Postgres job stops its database with `docker stop`, which could not be
> tried here (the development container has no Docker daemon); see [Not covered](#what-is-not-covered).

## What runs

| Process | How it is started | What it is |
| --- | --- | --- |
| `zcube-server` | `--store sqlite:<dir>/store.db` or `--store postgres:<settings>`, a port below the kernel's ephemeral range | the real server: HTTP API, controllers, the store |
| `zcube-agent` | `--node node1 --state-dir <dir>/state` | the real agent with `FakeRuntime`: every container is a command under a supervisor of its own, plain host processes |
| `zcube` | one process per command, in the demo's directory, with its own `HOME`, `XDG_STATE_HOME`, `USER` and `ZCUBE_SERVER` | the real command line: `apply`, `get`, `why`, `bundle` |
| the host | `/proc`, `kill(2)`, `tar` | the demo counts the real processes, sends the real `kill -9`, and reads the bundle with `tar` |

The demo reads the store through the server's HTTP API (`GET /v1/list`, `GET /v1/why`) for what the
command line does not show (the decision records, the raw keys). It never opens the store itself,
except to reset a Postgres schema before the run and to take SQLite's lock in step 5.

## How to run it

```
zig build demo-c0 -Dbackend=sqlite                       # nothing else needed
zig build pg-up                                          # a throwaway Postgres 16 (see AGENTS.md)
zig build demo-c0 -Dbackend=postgres                     # uses it
zig build demo-c0 -Dbackend=postgres -Dtranscript=out.txt   # also writes the transcript to a file
```

- `-Dpostgres=<libpq settings>` or `ZCUBE_TEST_POSTGRES` names another database, as for
  `test-store`. **The demo owns the `zcube` schema of that database**: it drops it before the run and
  after it, so the run starts from nothing and leaves the database as it was found.
- The Postgres run stops and starts its database with `pg_dev stop` and `pg_dev up`
  (`zig build pg-stop`, `zig build pg-up`; `stop` keeps the data). `ZCUBE_DEMO_PG_STOP` and
  `ZCUBE_DEMO_PG_START` replace them with shell commands: CI's service container uses
  `docker stop "$PG_CONTAINER"` and `docker start "$PG_CONTAINER"`.
- Exit 0 only if every assertion held. The first one that does not ends the demo: it prints
  `FAILED in step "…"` with what it expected, the logs of the server and the agent, kills everything
  it started, and exits 1. Every wait is bounded by a named constant (`demo_c0_state.zig`:
  `converge_ms` 20 s, `settle_ms` 3 s, `recover_ms` 30 s, `start_wait_ms` 20 s); a timeout names
  its step and what it waited for. About 25 s per run on SQLite (the refused apply waits 5 s) and 16 s on Postgres.
- **Cleanup.** The agent, the server and every supervisor's process group are killed at the end
  whatever happened, and the demo then scans `/proc` and fails if any supervisor or container
  command of the run is still alive. A Postgres that the demo stopped and did not start again is
  started again.
- CI uploads the transcript of each job as an artifact (`demo-c0-sqlite-transcript`,
  `demo-c0-postgres-transcript`).

## The steps, and what each asserts

Section numbers are those of the transcript.

| HANDOFF | Section | What the demo does and asserts |
| --- | --- | --- |
| 1. `zcube apply hello.zon`, 3 replicas; `zcube get service hello` shows 3 running | **1** | writes `hello.zon` as HANDOFF shows it and runs `zcube apply --yes hello.zon` (`applied service hello: created`); waits (≤ 20 s) until `get service hello -o json` says 3 of 3; asserts the text (`hello 3/3`), the JSON (`desired 3, running 3, generation 1`) and `get replicas -o wide` (3 running on node1); asserts on the host: 3 commands, each the child of a supervisor that leads its own session and group, each supervisor the child of the agent |
| 2. `kill -9` one process; a replacement starts; 3 again | **2** | sends `kill -9` to the command of `hello-1` (a host process); waits until `hello-1` is gone from `get replicas` and 3 run; asserts that the killed process is gone, that 3 commands run and none is `hello-1`, that the other two are the same processes as before, and that `zcube why replica hello-1` says it was killed (`SIGKILL`) |
| 3. 5 replicas: two more start; back to 2: three stop | **3** | edits the file; `apply --dry-run` shows `replicas 3 → 5` and writes nothing; `apply --yes`; waits until `get` says 5 and the host runs 5 commands under 5 supervisors, and asserts that the three that ran were not restarted (same pids); then 2: the host runs 2 commands under 2 supervisors, and the three removed commands are gone |
| 4. an unknown digest; `zcube why service broken` | **4** | applies `broken.zon` (`b3:00ff7be1`, not in `fixtures/images.zon`); waits for, then asserts, the whole text of `zcube why service broken`, line by line (below); asserts `get replicas` (`start-failed`, `ZBX-E0501: image not found`), that `broken-1` is **held, not replaced** after 3 s, that `hello` is undisturbed and that nothing runs for `broken` |
| 5. stop the store backend; `zcube get service hello`; `zcube bundle --last`; restore | **5** | [below](#step-5-the-store-backend-stops) |

The chain of step 4, asserted in full (7 lines, including the `more` and `docs` lines):

```
service broken: 0/1 running
  ← replica broken-1 failed to start on node1; it was not replaced because a new one would fail the same way
  ← error[ZBX-E0501]: image not found
      cause  digest b3:00ff7be1 is not in this node's store
      fix    check the digest in the service file, or pull the image first
      more   zbx explain E0501 · rerun with --verbose for the full cause chain
      docs   https://zigbox.github.io/zigbox/errors/E0501.html
```

### Step 5: the store backend stops

**Postgres** is a server of its own, so it is stopped (`pg_ctl stop -m fast` through `pg_dev`, or
`docker stop`) under the running `zcube-server`. The demo asserts:

1. `zcube get service hello` prints `error[ZC-E0201]: can't reach the store backend`, exits 3 (the
   blame is *external*), names the backend in words (`the Postgres server at … did not accept a
   connection`), has a fix (`start Postgres, or correct the host and port…`), and shows **no**
   connection-library text (no `libpq`, no `PQ`); `--output json` carries the same code with blame
   `external`;
2. `zcube bundle --last` exits 0 and writes a `.tar.gz`; the `MANIFEST.txt` read back from it with
   `tar` is the manifest `zcube` printed; it lists `command.txt`, `diagnostic.json`, `version.txt`
   and `status.json`, says redaction is on, and says which evidence could not be had
   (`*.unavailable.txt`); `diagnostic.json` holds `ZC-E0201`, and `status.json` records the store as
   down with it;
3. `zcube apply` is refused with the same diagnostic;
4. after the database is started again, `zcube get` answers by itself (no server restart), `hello`
   is still 2/2, the refused apply changed nothing (same generation), the workloads ran through the
   outage (the same processes), no decision was made during it, and the same apply now goes
   through and the controllers start the third replica (3 commands on the host, and exactly the
   four decisions of a scale-up).

**SQLite** is a library inside `zcube-server`: there is no backend process to stop, and no way to
make the file unreachable under a running server that fails a read (a file that is moved or deleted
stays open; a permission change does not reach an open descriptor, and the demo may run as root; a
read-mark lock held by another process makes reads hang, not fail). **This is a cut from HANDOFF's
wording, for a reason of SQLite's own.** What really happens to a SQLite store is that another
process holds it (a backup, a stray `sqlite3` session), so the demo takes the write lock from a
second process (`BEGIN EXCLUSIVE`, from the demo's own process) and asserts:

1. `zcube get service hello` **still answers `2/2`**: in WAL mode reads are not blocked. This is the
   truthful behaviour, and the demo asserts it rather than hiding it;
2. every write fails: `zcube apply` waits the server's 5 s busy time and prints
   `error[ZC-E0208]: the store database is busy`, exits 2 (the blame is *environment*), says who
   holds the store (`another connection held the write lock for over 5000 ms`), and has a fix
   (`stop whatever else uses the store file, then retry`);
3. `zcube bundle --last` writes a bundle with the same checks as above, with `status.json` and the
   store keys collected (the store still answers reads);
4. after the lock is released: the same recovery assertions as for Postgres.

## The acceptance criteria, in the same run

| Criterion | Section | Asserted |
| --- | --- | --- |
| Restarting `zcube-server` mid-demo changes nothing | **Acceptance: restarting zcube-server** (after step 2) | before the stop the demo reads `/services/`, `/replicas/` and `/decisions/` (keys, values and revisions) and `get replicas -o json`; the server gets SIGTERM and must exit 0; while it is down `zcube get` prints `ZC-E0102: can't reach zcube-server` with a fix and exit 2; the processes keep running; after the restart (same store) the same reads are **byte for byte the same**, the same processes run, and no decision was added |
| Restarting the agent re-adopts running processes instead of duplicating them | **Acceptance: restarting zcube-agent** | SIGTERM, exit 0; no container stopped; a new agent starts, registers and runs several passes; the same pids run (same supervisors, same commands), the host still has 3 commands under 3 supervisors, the store reads are byte for byte the same, no decision was added |
| Every controller action is recorded with its cause and visible to `zcube why` | after each step, and **Acceptance: every controller action…** | after each step the demo reads the decisions the step added and asserts **exactly** the expected ones, by actor and action (step 1: `apply`, `scale_up`, 3 × `create_replica`, 3 × `place_replica`; step 2: `delete_replica` (cause: the observed `SIGKILL`), `replace_replica`, `create_replica`, `place_replica`; step 3, up: `apply`, `scale_up`, 2 × `create_replica`, 2 × `place_replica`, and down: `apply`, `scale_down`, 3 × `stop_replica`; step 4: `apply`, `scale_up`, `create_replica`, `place_replica`, then `hold_failed_replica`; the restarts and the outage: none); each has a reason and a cause that exists (a decision, a desired key, an observed key); at the end every decision of the run (about 30) is asked of `GET /v1/why/…?decision=<id>`: the chain starts at it and ends at a real key, never at `gone`. The decisions are printed in the transcript |
| The whole demo passes on both backends | | the two CI jobs; five or more local runs of each ([Reliability](#reliability)) |
| The DIAGNOSTICS machinery exists and is used | | covered by CI checks from slice 6b, not repeated here: golden tests for every `ZC-` code in three output modes (`src/cli_golden.zig`), the no-stack-trace test over every failure case (same file), the bundle redaction test and fuzzer (`src/cli_test.zig`, `src/bundle_redact_fuzz.zig`), the build-time registry checks (`src/diag/codes.zig`) and `zig build errors-site-check`. The demo adds what DIAGNOSTICS.md's *Demo assertions* ask: every refusal asserts its **code and summary** (`ZC-E0102`, `ZC-E0201`, `ZC-E0208`; `ZBX-E0501` in the chain), not only a non-zero exit, and each refusal's output shows no stack trace, source location or Zig error name |

## Deviations from HANDOFF's wording

Each is asserted as the actual text, not as HANDOFF's.

1. **The middle line of the chain of step 4.** HANDOFF: `← replica broken-1 pending on node1`.
   Actual (api.md's sentence): `← replica broken-1 failed to start on node1; it was not replaced
   because a new one would fail the same way`. api.md wins where they differ; the actual line says
   more, and says it is held.
2. **The diagnostic block of step 4.** The digest is `b3:00ff7be1`, in full (HANDOFF shortens it as
   `b3:00ff…e1`: diagnostics are printable ASCII, so `...` would be used if it were shortened); the
   fix says `the service file`, not `broken.zon`, because the runtime does not know the file's name;
   two lines are added, `more` and `docs`, which every diagnostic carries.
3. **`zcube apply` is run with `--yes`.** It asks first, and without a terminal on standard input
   and without `--yes` it is `ZC-E0113`; the demo has no terminal.
4. **"Within seconds"** is asserted as at most 20 s (`converge_ms`); the runs take 0.1–0.4 s.
5. **Step 5 on SQLite** is a held write lock, not a stopped database, and the refusal is `ZC-E0208`
   (blame *environment*, exit 2), not `ZC-E0201`; `zcube get` keeps working. See above.
6. **Step 5 on Postgres** runs `zcube bundle --last` right after the failed `get`, as HANDOFF has
   it, and then adds a refused `apply` (also `ZC-E0201`), to show a write is refused and changes
   nothing. HANDOFF's text names `get` only.
7. **Added to HANDOFF's script:** the server restart and the agent restart between steps 2 and 3
   (they are acceptance criteria, which say "mid-demo"); `apply --dry-run` in step 3; a final apply
   after the outage, to show the controllers work again.
8. **`kill -9` is sent to the replica's command**, not its supervisor (the supervisor is not one of
   "the processes" a container is; it is the part that records how the command ended).

## What is not covered

- **C1**: more than one node, scheduling, leases that expire, failover. The demo has one agent.
- **The real Zigbox runtime**: every container is a plain host process under a supervisor
  (`FakeRuntime`); `env` is passed, `limits` are recorded and ignored (docs/agent.md).
- **OrioleDB**: the Postgres run uses the plain-heap schema, which is what Postgres 16 without the
  extension gives (AGENTS.md).
- **Other ways a store can fail:** a Postgres that is slow, partitioned or out of connections; a
  SQLite file on a disk that is full or read-only. Each has its own code and is tested where it is
  raised (the store tests, the golden tests).
- **The Postgres outage in CI.** The local run stops `pg_ctl`'s server; CI stops a service
  container with `docker stop` and starts it with `docker start`. The commands are the demo's own
  hooks, but the development container has no Docker daemon, so **that path ran for the first time
  in CI**, not here.
- **Authentication.** Writes are unauthenticated (api.md); the demo listens on loopback.
- **Platforms other than Linux** (the demo reads `/proc`), **timing**: the bounds are generous and
  say nothing about performance, and **a clean machine** in the sense of a fresh VM: the demo starts
  from an empty directory and an empty schema, and a CI runner is the clean machine.
- **The console** (`web/`) is not driven; it has its own dev-time check.

## What the demo found, and what was fixed

The demo found three real defects in the pieces it ties together, each fixed in a commit of its own
with a regression test that failed before:

1. **`zcube-server` could not be restarted within a minute of any `zcube` command** (`ZC-E0107`):
   whoever closes a connection first keeps it in `TIME_WAIT` on its port, and the server had no
   `SO_REUSEADDR`. The first fix was on the command's side (it now reads by `Content-Length` and
   closes first, as the agent does; test `cli_test.zig`); review showed that was not enough, since an
   idle connection, a browser or `curl` still made the server close first. The server now listens
   with `SO_REUSEADDR` alone (`server_listen.zig`; the standard library's option sets
   `SO_REUSEPORT` too, which would let a second server share the port). Test: `server_test.zig`, "a
   server that closed a connection first can be restarted on its port at once", which fails without
   it; a second live server is still refused (same file). `ZC-E0107`'s cause no longer says another
   process is *listening*: it says the address is in use by another process.
2. **The agent crashed with `ZC-B0001`** ("programmer bug caused syscall error: AGAIN") when the
   server held a request longer than the agent's 10 s socket timeout, which a SQLite lock does: the
   timeout made the standard library's reader panic. Intermittent (about 1 run in 6 before the fix),
   and the agent never started the third replica. Fixed (`agent_http.zig`): it polls before each
   read, as the command does. Test: `agent_http.zig`, "a server that accepts and says nothing is
   ZC-E0503 after the wait, not a crash".
3. **A server port in the kernel's ephemeral range can be taken by the agent itself** while the
   server is down: a connection to a local port with no listener can connect to itself (TCP
   simultaneous open), and the next server is told `another process is already listening`. Not a
   defect of the product (any program that retries against a local port can do it); the demo avoids
   it by choosing its port below `ip_local_port_range`. `agent-smoke` still picks an ephemeral port.

## Reliability

Slice 6c, run by hand on the development container (Postgres 16 without OrioleDB, SQLite 3), each
run in a new directory, on a new port and (Postgres) from an empty schema: **10 of 10 on SQLite and
10 of 10 on Postgres** with the code as first committed, then **5 of 5 on each** after the last change
to the demo. One intermittent failure was seen on the way (the agent crash, item 2 above) and
root-caused, not retried; the demo has no retries. CI is the check on a clean machine.

## History

- **Slice 5a** (`zig build sim-c0`): a deterministic **simulation** of these steps against the core,
  a memory store and a simulated runtime on virtual time ([core.md](../core.md)). It is not the demo
  and is never reported as one. It still runs in CI.
- **Slice 5b**: `zcube-server` (HTTP, the console, the controller driver, SQLite and Postgres) and the
  console running the real core in WebAssembly.
- **Slice 6a**: `zcube-agent` and `FakeRuntime`; `zig build agent-smoke` runs the server and one
  agent as real processes (3 replicas, `kill -9`, an agent restart, a server restart, an unknown
  digest). It is not `demo-c0`: it does not drive the `zcube` command and asserts less.
- **Slice 6b**: the `zcube` command and the diagnostics machinery.
- **Slice 6c** (this): `demo-c0`.
