# B3: relays

## demo-b3 (slice 4)

`zig build demo-b3 [-Dtranscript=FILE]` (`src/demo_b3.zig`, `src/demo_b3_script.zig`,
`ops/demo-b3/guest.sh`) runs on the rig of demo-c2 (`src/demo_c2_vms.zig`, here one guest of
the four): the server on the host with `relays = .{ .botpike = .{ .address = "127.0.0.1:9090" } }`,
one QEMU guest whose agent runs `--runtime zigbox` as root, and on the guest's loopback a test
upstream (a few lines of Python) that logs every request and answers `upstream-ok`. It skips
unless `ZCUBE_REAL_HOST=1` and needs KVM and a GHCR image (demo-c2's `python-app` v1).

1. A bystander job with `--relay botpike` runs, so a second relay exists on the node.
2. The hostile job (`--relay botpike`, the same Python image) tries, each for 3 s: 1.1.1.1:443,
   the node's address, 169.254.169.254:80, zcube-server (10.0.2.2:P), the upstream directly
   (127.0.0.1:9090), a DNS lookup, and a raw ICMP socket sent to 1.1.1.1. Then it requests
   `GET /report?<check>=<failed|REACHED>...` through `ZCUBE_RELAY`. The demo asserts: the job exits
   0 (10: something was reached, 11: wrong answer, 12: no answer), the upstream got that one
   request, and every check reads `failed`.
3. On the node: nothing listens on 8080 in the node's own namespace (this, not a probe from the
   job, is what shows a relay is reachable only inside its own job: from the job any non-loopback
   address fails under `--net none` whatever listens), each job's `relay.log` exists (the check fails without one) and none holds a
   ZC-E07xx line, the bystander ends after its cancel.

The job's output is not captured by the real runtime, so the job reports through the relay: the
upstream's log is the evidence, which also proves the route works.

Not run: the cloud container the slice was written in has no KVM, so demo-b3 was **not run
there**; it runs in CI (`demo-b3` job). Nothing in this file is a passed demo until that job is
green.

### Cuts, gaps and deviations of slice 4

- **Zigbox library gap.** `take_listener` and `forget_listener` exist in Zigbox's
  `runtime/run.zig` but `zigbox.zig` does not export them. The supervisor reaches the descriptor
  through `handle.session.take_listener()` and the public `handle.listen`. Zigbox should export
  the pair (the CLI path uses `host.send_handle`, which is not an in-process route).
- **The relay stops after `zigbox.wait`,** not when the command's process ends: `wait` writes the
  ending record, which is how the agent learns of the ending, so the relay (its listener and any
  open upstream connection) is closed just after the agent can report it. Zigbox gives no hook
  between the reap and the record. The brief's order (close before reporting) is not kept; the
  supervisor must accept this. The container's processes are gone by then, so nothing new comes in.
- **A relay that cannot be served on the real runtime is not a start failure.** The container is
  killed and `relay.log` says ZC-E0702 (a line with a cause, no fix), but the job's ending is
  Zigbox's record, "killed by signal 9"; `docs/api.md` says start failure. Making it one needs the
  runtime to prefer `failed.json` over a run record, a change of the status mapping left to the
  supervisor. The path has a unit test for the log line only.
- **The raw-socket check** passes if creating the socket or sending to 1.1.1.1 fails; the demo
  does not tell which.
- **No `relay.port` file** on the real runtime: the port is always 8080 in the container's own
  namespace.
- **The `ZCUBE_RELAY` pin**: build.zig.zon moved from Zigbox 0.3.1 to commit 843426e (M8b); the
  comment above the url changed with it (the brief said url and hash only).
- **ZC-E0703** stays registered and in the golden; no adapter raises it now.

# Slice 2 notes

This section records what slice 2 (the relay over the fake runtime, #208) cut or deferred, so the
owner can see it.

## Cuts and deferrals

- **ZC-E0701 is not shown in `zcube why job` yet.** The brief wants an unreachable upstream in
  `why job`; slice 2 writes the coded line to `relay.log` in the container's directory only
  (first lines, at most `relay_log_bytes_max`). Where it lands: the slice that makes the agent
  report relay trouble in a job's ending (needs a field on the run record and the job API,
  which is an API change, so it is not done here). `relay.zig`'s header says the same.
- **A hostname or IPv6 upstream can delay the supervisor's ending by up to
  `relay_connect_timeout_ms` (10 s).** The IPv4 literal path connects in `relay_poll_ms` slices
  and honours `stop`; the name and IPv6 paths go through `std.Io` and block until that timeout.
  Consequence: a job that ends while a connection to a black-holed named upstream is connecting
  records `run.json` up to 10 s late (`kill_and_wait` may report "not ended" first). The DNS
  lookup's own use of the timeout is not tested. Left as is because resolving at `open` would
  put the same block in front of the job's start; the fix (a stop-aware resolver) is B4's, with
  mTLS, which replaces `connect_upstream`.
- **`sim_runtime` ignores `spec.relay`**, against the field's doc comment. Harmless until slice 3
  makes simulated jobs relayed; it refuses or models the relay there.
- The `Runtime.Spec.relay` ask is recorded in
  `docs/decisions/2026-11-10-runtime-spec-relay.md`.

## Review fixes made

ZC-E0702 has its own blame (`run.json` `blame: "relay"`), so a relay that cannot be set up is
E0702 with the failed step in its cause, not E0507. The server's relay-address check refuses
`[]:80`. The three bounds live in `relay.Limits` (never above the constants) and each exit path
has a test (idle, bytes, connect timeout). A failing `accept` is logged once and backs off. A
local socket failure is E0705, not the upstream's E0701. The relay test writes `relay.env`
by rename. The lanes fuzzer drives the real `round` over fake sockets (short counts, would-block)
and fails with an end passed to the wrong socket.
