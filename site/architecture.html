Architecture · as of 2026-10-27

How Zigcube is built

Desired state goes into a versioned store. Controllers turn it into replicas and record a decision for every action. A thin agent on each node pulls its replicas and runs them through a runtime interface. C0 builds all of that against a fake runtime on one node. This page says what exists, what C1 adds next, and what is planned after that.

Built: C0, demonstrated in CINext: C1, not startedPlanned: C2 to C8

The shape

Three executables, one store, one contract with Zigbox

zcube (the command line), zcube-server (HTTP API plus controllers) and zcube-agent (one per node) come from one Zig 0.17 build, with no third-party Zig dependencies. The server talks to the store. Everyone else talks to the server over HTTP/1.1 and JSON, and the server never pushes to an agent.

State and authority

Three kinds of state, each with one direction of authority

"The store is the only state" is shorthand, and not quite true: only a process's parent can collect its exit status, so some facts can only come into being on the node. The precise model, the fencing protocol and the rules for believing an observation are in docs/authority.md.

ClassWhereAuthoritative forIf lost
Intent and decisionsthe storewhat should run, and why each action was takenthe cluster is lost: restore the database
Process factseach node's state directory (supervisor records)what happened to that host's processes, and nothing elsethat node's processes are treated as lost and killed: fail safe
Cachesserver and agent memory; later Zigbox's chunk storenothingrebuilt from the other two

Intent flows from the store to the node, facts flow from the node to the store (as /observed), and a node never holds intent: from local files alone an agent may adopt or stop a container, never start one.

Built C0 · Loop

What exists today

Everything here is merged on main and exercised by demo-c0 on both Postgres and SQLite in CI. All of it runs against FakeRuntime, not real Zigbox, and on one node.

Store: a versioned key-value interface

The same semantics as etcd, on databases people already run. Every committed transaction gets one global revision, and the revision is assigned inside the transaction that writes the data.

  • Operations: get, list (at a revision, paged, reversible), txn (compare on mod_revision, then puts and deletes), watch (ordered, gap-free, an explicit error once compacted), leases (grant, keepalive, revoke, list), and compact.
  • Postgres: each writer's first statement is UPDATE store_meta SET revision = revision + 1 RETURNING revision. That serialises writers, so revision order is commit order and a rollback never burns a number. LISTEN/NOTIFY wakes watchers, a bounded poll backs it up, and the reader checks the log has no hole. The schema is plain heap; OrioleDB is optional and has not been run.
  • SQLite: WAL mode, with BEGIN IMMEDIATE as the single writer. For development and single-node use.
  • Memory: the reference implementation, used by the tests and the console.
  • One conformance suite runs on all three backends with a fresh seed on every run.

The core: controllers as steps

A controller is reconcile(ctx) → Wakeup. It reads, does what is due, writes each action with its decision record in one transaction, and returns the time or key prefixes that should wake it next. It never blocks.

  • Level-triggered and idempotent. A converged system writes nothing, so a lost event costs nothing.
  • Partial progress is normal. A transaction touches at most four replicas. A failed compare writes nothing, and the next step plans again.
  • No hidden state. Whatever cannot finish now, such as a stop's grace period or a held replica, is written to the store.
  • WASM-clean. No threads, sockets, files, libc, std.Io, real clock or randomness. CI compiles it to wasm32-freestanding and runs it in Node.

zcube-server

The shell around the core: an accept loop, one task per connection, a driver thread that runs the controllers when their Wakeup falls due, timers for lease expiry and compaction, and a watchdog over the connection table.

  • API (docs/api.md): reads under /v1; POST /v1/apply, with ?dry_run=1 to preview; DELETE /v1/services/{name}; agent endpoints under /v1/agent/nodes/{node}/.
  • Every request has an ID, returned in X-Request-Id: the client's own if it sends one (the CLI does, with a random part), otherwise r-<start>-<counter>, unique across restarts.
  • A failing store is reported once as a diagnostic, not once per step, with backoff.
  • Writes are unauthenticated: listen on a private address.

zcube-agent and FakeRuntime

One single-threaded agent per node. It reconciles the node's desired replicas against what the runtime lists, and reports what it observes. The Runtime interface is the contract with Zigbox: a small serialisable Handle, start, stop with grace, inspect, list, and an event stream. There is no blocking wait.

  • One supervisor per container (the owner's recorded exception): zcube-agent supervise is the command's parent, runs in its own session, and records the exit, so the agent can restart without losing anything.
  • Re-adoption is list: a restarted agent reads the state directory and never starts a duplicate.
  • A container whose supervisor vanished is lost (ZC-E0509). Its process group is killed once.
  • Images come from fixtures/images.zon. Any other digest fails with the placeholder ZBX-E0501. Limits are recorded but not enforced.

zcube, the command line

  • apply shows a diff and asks first. --yes skips the question, and --dry-run only shows the diff.
  • get service|replicas, delete service, and explain <code> (works offline).
  • why <kind> <name> follows decision records back to an observed fact or a desired key.
  • bundle --last writes a redacted .tar.gz of evidence that never leaves the machine.
  • Output is plain, --verbose or --output json. The exit code comes from the blame of the first diagnostic.

Diagnostics, shared with Zigbox

Every failure is a coded diagnostic with a blame, a cause and a fix, never a stack trace or a bare Zig error name. Zigcube's ZC- registry plugs into Zigbox's diagnostic, render and explain modules as a second product. Zigbox is a pinned package.

  • Blame decides the exit code: 1 user, 2 environment, 3 external, 70 bug.
  • Golden tests cover every code in all three output modes. A no-stack-trace test covers every failure path, and the redactor is fuzzed.
  • An error page per code is generated from the registry and checked in CI.

Web console

Plain HTML, CSS and ES modules, embedded in zcube-server. There is no build step and it makes no request to any other host. It lists once, then follows the store's watch, the same way an agent does, and shows the connection state at all times.

With ?sim=c0 it runs the real core, compiled to WASM, over a memory store and a simulated runtime in the browser. That module has exactly one import, env.zc_panic.

How it is checked

  • demo-c0 is the milestone demo. Real server, agent and CLI processes, on Postgres and on SQLite, assert every step and acceptance criterion: kill, scale, an unknown image, server and agent restarts, the store going down, and a bundle.
  • sim-c0 runs the same scenario natively and as WASM on virtual time and compares the reports. It is a simulation, not the demo.
  • agent-smoke is a host check of the server and agent as real processes.
  • Also: test, tidy, test-store on each backend, wasm-check, wasm-test and console-wasm. The WASM jobs run under each V8 tier separately, because Node 22 crashes when tiers mix.

One request, end to end

From zcube apply to a running process, and back through why

  1. zcube apply hello.zon parses the ZON file and asks the server for a dry run, which returns the diff. Once confirmed, POST /v1/apply writes /services/hello with a new generation and an apply decision, in one transaction.
  2. The driver wakes on the change under /services/. The replica controller compares desired with actual and writes scale_up, then a create_replica and a place_replica for each new replica. Every one is a /decisions/<id> record with its cause, indexed under /decisions-by-subject/.
  3. The agent's long-poll returns. It lists its replicas, compares them with Runtime.list, and calls start. FakeRuntime writes spec.json and launches a supervisor, which runs the command.
  4. The agent reports what it sees under /observed/<node>/<replica>. If a start fails, the report carries the runtime's full diagnostic, for example ZBX-E0501. The controller then holds the replica rather than retrying a start that would fail the same way.
  5. zcube why service broken walks from the service through the decisions to that observed diagnostic and prints the chain: service broken: 0/1 running ← replica broken-1 failed to start on node1 ← error[ZBX-E0501]: image not found.

Data model

The key layout

Values are JSON. The full shapes are in docs/keys.md. Decision records are kept per subject: the newest 200 and at most 7 days, whichever is fewer, and 24 hours once the subject is deleted.

/replicas/<service>/<id>controllerdesired replica and the node it is placed on

Guarantees and limits

What holds, and what does not yet

Holds, and is tested

  • Gap-free watch. Revision order is commit order on every backend. The conformance suite checks it under concurrent writers.
  • Restart-safe. Restarting the server or the agent changes no key and adds no decision, and the same processes keep running. The demo compares the store byte for byte and the host by process id.
  • Explainable. Every action has a decision whose cause chain ends at a real key. The demo checks about 30 per run.
  • Store outage. Postgres down gives ZC-E0201, exit 3. Workloads keep running and recovery needs no restart.

Not yet

  • One node, one server. No scheduling, no failover, and no second server on the same store.
  • No real runtime. No isolation and no limits, and the ZBX- codes are placeholders until Zigbox's adapter lands.
  • No authentication on writes.
  • Explanations can be cut short. Retention keeps the newest 200 decisions per subject, so a long crash loop can evict the cause of a chain. why then ends at a gone step; C1 makes this an explicit truncated verdict and stops evicting live chains.
  • Write throughput on Postgres is capped by the serialised writer: hundreds to low thousands of revisions a second. A benchmark is due at C1, and group commit is the fallback.
  • OrioleDB has not been run.

Next C1 · Fleet

Placement and failover

Not started: the brief is the next piece of work, built to docs/authority.md. The goal is that workloads spread across nodes and survive the loss of one, still on FakeRuntime, with several agents and their own state directories on one machine or a few VMs.

What gets built

  • Node registration on a lease. /nodes/<node> is bound to the agent's lease and carries its declared CPU and memory; while it exists, the agent holds tenure. zcube get nodes lists the nodes.
  • A scheduler that filters on resource fit, then scores for spread, and writes the placement as /assigned/<node>/<replica> with its reasons in the decision. Agents watch only their own prefix.
  • A node controller. On lease expiry it marks the node lost in /node-status/<node>, waits a short grace, and marks its replicas lost; the replica controller replaces them on the survivors, with new ids. Nothing moves back when the node returns.
  • Fencing, with a stated window. Exclusive ownership of a replica is guaranteed by the store; exclusive execution only outside a stated window, and not on a wedged node. The agent stops its own workloads a margin before its lease can expire, timed from when it sent its last successful keepalive. Writes from an agent that lost tenure are refused by the store. demo-c1 tests a partition: the agent stays alive but cannot reach the server.
  • Complete or truncated. zcube why says whether its chain reached a terminal, retention never evicts a live subject's newest decision of each kind or its chain, and decisions stay immutable: repetition is counted in a separate summary that is never a cause.
  • demo-c1 (three agents, six replicas, one agent killed, zcube why node node3) and sim-c1, which checks the invariants under partitions, clock skew and kills that fail.

Decided before the brief

  • One writer role per key prefix: the API, the replica controller, the scheduler, the node controller, each node's agent. The scheduler no longer writes into /replicas.
  • The read-set rule: a controller's transaction compares every key whose value justified the action, so a stale plan writes nothing.
  • No phantoms in capacity. A decision over a set compares one authoritative aggregate that every change to the set updates. For capacity that is /allocations/<node>, owned by the scheduler and changed in the same transaction as every placement and release, so no placement overcommits a node.
  • Admissible observations: a controller acts on an observation only under the node's current tenure, the replica's current placement, and a ready node. Older ones may explain, never justify.
  • A lease expiry is not proof of a stop. Stateless replicas accept the stated window. A stateful replica (C7) moves only with a fencing proof: the node confirms, an external fence succeeds, or an operator asserts it, and durable writes check the placement epoch.
  • Still to fix in the brief: what happens to a replica that fits no node (held as pending, with a decision naming the shortfall), the fencing constants, a random part in server-assigned request IDs, and the watch fan-out benchmark.

Planned C2 to C8

Where the architecture goes after C1

From the design doc, Part II. Each milestone waits on specific Zigbox milestones. The real runtime replaces FakeRuntime behind the same Runtime interface once Zigbox M2 ships its exit reasons and cgroup scopes.

MilestoneWhat changes in the architectureNeeds from Zigbox
C2 · SwarmAgents advertise a compact summary of their chunk store, for example a Bloom filter per image tree. The scheduler adds a locality score, which never overrides fit or spread. Nodes fetch chunks from peers before the registry and verify each one by hash. zcube stats pull.M3 chunk store, M4 for the demo
C3 · RolloutReadiness and liveness checks, rolling updates within surge and unavailable limits, automatic rollback to the exact previous digest, and zcube history and rollback.M4
C4 · MeshWireGuard between nodes, cluster DNS, and a workload identity bound to service name and image digest. Grants such as web → db:5432 compile into per-node rules, with default deny.M5 network namespaces and grants
C5 · EdgeAn edge proxy role on chosen nodes, ACME certificates stored encrypted, and public = "…" on a service. Edge traffic enters the mesh through a grant.C4
C6 · TrustA policy check at admission in the server, and again in every agent before exec, using node-local trusted keys that the API cannot change. A compromised control plane cannot run unsigned code.M8 signatures
C7 · StateNamed state volumes pinned by the scheduler, snapshots shipped to object storage, and restore on another node after node loss. A move needs a fencing proof, not just an expired lease, and snapshot writes are conditional on the placement epoch. The recovery point is the snapshot interval.M6 state volumes
C8 · JobsA job object with retries and deadlines, gang scheduling, and Zigbox M7 build steps dispatched across nodes with one shared chunk-store cache.M7 builds

Stretch goals, not scheduled: a Kubernetes API facade (CS1), cells (CS2), tenant isolation on microVMs (CS3) and accelerators (CS4). Out of scope through C8: clusters beyond a few hundred nodes, a custom consensus store, multi-region active-active control planes, and synchronous replication.
