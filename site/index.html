Orchestration for Zigbox

A cluster that only runs what it can verify.

Zigcube schedules Zigbox workloads across a fleet. Images move as chunks between peers, every node checks signatures before it runs anything, and services talk only along declared grants.

Design principles
Kubernetes' good idea, rebuilt around it

    
Declared state reconciled by controllers stays. Most of the plumbing around it goes.

    

      
One thin agent
Each node runs a single rootless agent that links Zigbox directly. No CRI, no containerd, no shims.

      
Store-aware scheduling
The scheduler knows which chunks each node holds, and nodes fetch from peers before the registry.

      
Trust checked twice
Admission checks policy, then every node re-checks before exec. A compromised control plane cannot run unsigned code.

      
Grants, not a flat network
web → db:5432 is the whole rule. Identity-based, encrypted, default deny.

      
Ask why
zcube why prints the causal chain behind any state, so "why isn't it running" takes one command.

      
Boring storage
Desired and observed state live in Postgres, with OrioleDB for the hot, update-heavy tables.
